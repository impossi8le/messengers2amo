# Разработка от тестов и безопасного логирования

Правила действуют для новых изменений проекта. Локальный Telegram-стенд и его текущие тесты уже существовали до введения этого требования; обратное прохождение RED для них не заявляется.

## Цикл изменения

1. Взять задачу с выполненными зависимостями. В issue указать ответственного, план, пути и границы проверяемого поведения.
2. Написать значимый тест конкретного сценария и запустить его до реализации. Зафиксировать RED: ожидаемый сбой утверждения. Ошибка установки, отсутствующий сервис и синтаксическая ошибка не доказывают RED бизнес-поведения.
3. Добавить минимальную реализацию, получить GREEN. Проверить негативный сценарий и восстановление после сбоя, если они относятся к изменению.
4. Провести рефакторинг и повторить затронутые проверки. Указать реальные команды, результаты и ограничения.
5. Опубликовать проверенные изменения и перевести карточку на тестирование; закрывать после выполненных критериев, а не после ответа генератора или успешного exit code.

Схемы проверяются настоящим валидатором. Транзакции, миграции и гонки проверяются на PostgreSQL, а не SQLite или моках. Синтетические fixtures не содержат данные пользователей. Недоступную среду помечать NOT RUN; не выдавать пропущенный тест за успешный.

## Диагностика

Логи — структурированные события со стабильным именем, временем, уровнем, результатом, безопасным кодом ошибки и длительностью. Для связи использовать генерируемые внутренние request/correlation ID, operation ID и event ID; отсутствующее значение не заменять идентификатором клиента.

Полезные точки: получение запроса, сохранение inbox, commit/rollback обработки, допуск к отправке, результат sent/failed/unknown, конфликт версии, восстановление после перезапуска. Лог успеха фиксируется после соответствующего commit; сетевой вызов и его неопределенный исход отличать от локального принятия команды.

Разрешенные поля задаются явным списком. Не писать токены, auth-заголовки, cookies, URL с секретами, SQL-параметры, raw provider errors, payload, тексты переписки, телефоны и внешние имена. Предпочитать исключение поля из логирования попытке замаскировать произвольную строку. Диагностический лог не заменяет отдельный транзакционный аудит.

До добавления логгера написать тесты захваченного вывода: синтетические canary-секреты/тексты не появляются ни в успешном пути, ни в ошибках, rollback и nested exception; ID и коды позволяют связать события. Включить невалидные поля и типовые закодированные значения. Schema whitelist проверяет форму, но сам по себе не доказывает отсутствие чувствительных значений в разрешенных полях. Срок хранения, доступ и ротация логов определяются для окружения отдельно.

## Критичные сценарии

Для соответствующих изменений проверять дубли, тот же ключ с другим payload, timeout/unknown без слепого повтора, перезапуск, старый binding epoch, новое входящее/правку после snapshot и конкурирующие назначения. Сначала выбирать нужный сценарий из документа приемки, затем строить тест и реализацию.

## Smoke-прогон

`apps/api/scripts/smoke.mjs` — одна команда, которая за минуту проверяет, что инстанс живой по всему пути: health, вход, защита операторских маршрутов, приём вебхука, внутренний CRM-контур и метрики. Внешних зависимостей нет, говорит только по HTTP.

### Локальный режим (по умолчанию)

```bash
cd apps/api
npm run smoke            # то же, что node scripts/smoke.mjs --local
```

Поднимает приложение в том же процессе на loopback-порту, создаёт одноразовую схему `t_<hex>` в `TEST_DATABASE_URL` (по умолчанию `postgres://testuser:testpass@127.0.0.1:55440/m2a`), наполняет её минимальным тенантом и удаляет схему в `finally` — даже если проверка упала. Пароли и токены генерируются в процессе и не печатаются.

Проверяются: `health/live` и `health/ready`; вход с неверным паролем (401) и с верным (200 + cookie); операторский список без сессии (401) и с сессией (200); чужой `companyId` в query отвергается; `connections`, `workshops`, `staff/availability`, `notifications`; вебхук Telegram с верным секретом создаёт событие, повторная доставка не создаёт дубль, неверный секрет даёт 401 и ничего не пишет; drain превращает событие в обращение; `internal/crm/bindings` без сконфигурированного токена — 404, с токеном — 200; `/metrics` без токена — 401/404, с токеном — 200.

### Удалённый режим

```bash
node scripts/smoke.mjs --url https://api.example.test \
  [--email <staffId> --password <password>] [--company-id <id>] \
  [--webhook-secret <secret>] [--metrics-token <token>] [--internal-token <token>]
```

Только HTTP, без доступа к базе инстанса. Проверяются health, 401 на операторском маршруте без сессии, 401/404 на `/metrics` без токена и 401 на вебхуке с неверным секретом. С `--email`/`--password` выполняется вход и чтение операторских списков (`--company-id` по умолчанию `default`). Остальные флаги включают дополнительные проверки: 404 на несуществующем подключении, 200 на `/metrics` и `internal/crm/bindings` с токеном. Невключённые проверки печатаются как `SKIP`.

Те же значения читаются из окружения: `SMOKE_URL`, `SMOKE_EMAIL`, `SMOKE_PASSWORD`, `SMOKE_COMPANY_ID`, `SMOKE_WEBHOOK_SECRET`, `SMOKE_METRICS_TOKEN`, `SMOKE_INTERNAL_TOKEN`, `SMOKE_TIMEOUT_MS`.

### Как читать вывод

Каждая проверка печатает одну строку: `PASS` — ожидание выполнено, `FAIL` — нарушено (в строке фактический код ответа, например `login: HTTP 200, expected 401`), `SKIP` — проверка не включена. В конце сводка `N passed, M failed, K skipped`; любой `FAIL` даёт exit code 1, поэтому скрипт годится для CI и проверки после деплоя. Пароли, токены и секреты в вывод не попадают.
