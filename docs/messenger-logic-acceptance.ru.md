# Проектная приемка бизнес-логики мессенджеров

Дата: 21.10.2026. Область: внутренний сервис одной компании, свои подключения WA/TG/MAX/VK и amoCRM. Основа: [архитектура](messenger-platform-architecture.ru.md) и [требования](messenger-platform-requirements.ru.md). Это проектные обязательства реализации, а не результаты испытаний. Фактические возможности, окна, квоты и методы сверки адаптеров подтверждаются отдельно. Числа в сценариях — тестовые данные.

P0 блокирует пилот: потеря обращения, дубли внешних действий, утечка, ложное закрытие ожидания. P1 обязателен до расширения пилота. Given — исходное состояние, When — входное событие, Then — проверяемые изменения БД, jobs, UI и внешних эффектов. Отсутствующий эффект также проверяется. Будущая проверка использует управляемые ответы внешнего стенда.

Статус на 22.10.2026: документ остаётся проектными обязательствами. 31 из 45 сценариев связаны с исполняемыми тестами (`apps/api/src/acceptance/matrix.ts`); AC09, AC16, AC18, AC22, AC28, AC30, AC32, AC34, AC35, AC37, AC38, AC40, AC42, AC45 остаются ручными/live-проверками. Прохождение тестов не заменяет приёмку на боевых аккаунтах.

## Модель ожидания

Новое актуальное входящее и существенная правка получают монотонный `attention_seq` в диалоге и обязательство ответа с причиной. Статус, дубль и доверенный исторический импорт счетчик не увеличивают. Правило существенности правки версионируется; повтор версии не создает нового обязательства. Старый timestamp сам по себе не означает историчность: задержанное live-событие остается значимым.

Ответ ссылается на неизменный серверный снимок, выданный при начале подготовки: точные ID обязательств и версии содержимого. При принятии команды сервер проверяет этот снимок, а не подставляет текущие входящие. Курсор может быть производной проекцией, но не заменяет точные связи покрытия. Фоновое обновление чата не расширяет снимок; обновление покрытия требует явного действия. Только подтвержденный успех отправки закрывает включенные обязательства. `accepted`, прочтение оператором, ошибка и `unknown` этого не делают. Автоответ по умолчанию ожидание не закрывает. Native CRM без доверенного снимка и автора дает неподтвержденное ручное покрытие, а не курсор из текущего состояния.

`waiting_since` соответствует самому раннему открытому обязательству; SLA использует согласованные календарь, паузы и версию политики. Ключи ограничены компанией, подключением и областью адаптера. Identity epoch меняется при смене внешней личности; обычная ротация credentials обновляет отдельную версию доступа и требует повторной проверки задач.

## Сценарии Given / When / Then

### Прием и ожидание

**AC01 · P0. Надежный прием.** Given валидное подключение; When приходит новое входящее; Then ACK следует после commit inbox. Обработка создает одно сообщение, обязательство и CRM-outbox; UI показывает ожидание. Потеря уведомления брокера компенсируется сканером БД, а не потерей события.

**AC02 · P0. Дубли доставки.** Given событие уже применено; When тот же ключ приходит двум workers; Then уникальные ограничения оставляют одно сообщение, обязательство и логическое CRM-намерение. Повтор не сбрасывает SLA и не создает второго внешнего действия.

**AC03 · P0. Непринятое событие.** Given подпись неверна либо commit недоступен; When поступает webhook; Then неподлинное событие не обрабатывается, неподтвержденная запись не получает ACK успешного сохранения. UI ничего не выдумывает; диагностика не раскрывает payload и секреты.

**AC04 · P0. Прочтение оператором.** Given seq=11 открыт; When оператор открывает диалог или CRM отмечает чтение; Then меняется состояние прочтения сотрудника. Обязательство и `waiting_since` сохраняются; CRM не получает фиктивную отправку или закрытие ожидания.

**AC05 · P0. Существенная правка.** Given seq=11 закрыт ответом; When новая версия входящего меняет детали заказа; Then сохраняется версия и создается seq=12 с ожиданием. Повтор версии ничего не добавляет; CRM получает поддерживаемую мутацию либо явное ограничение.

**AC06 · P1. Несущественная правка.** Given обязательство открыто; When правка признана несущественной утвержденным правилом; Then текст и версия обновляются без нового seq и сброса SLA. Аудит хранит версию правила и событие; UI не сигнализирует о новом обращении.

**AC07 · P0. Снимок ответа.** Given при начале подготовки открыт снимок seq=20,21; When seq=22 приходит до принятия команды или после него, а ответ успешно отправлен; Then закрываются только 20,21. БД хранит исходные ID/версии и доказательство; UI продолжает ожидание seq=22, CRM не получает ложного полного закрытия. Принятие команды не расширяет снимок до 22.

**AC08 · P0. Ошибка ответа.** Given ответ покрывает seq=21; When получен отказ или unknown; Then обязательство остается открытым, сообщение имеет достоверный исход. UI объясняет действие; чтение клиентом другого сообщения не закрывает ожидание и не запускает повтор автоматически.

**AC09 · P0. Native CRM.** Given исходящая команда не имеет проверяемого снимка/автора; When отправка успешна; Then факт отправки фиксируется, покрытие получает `coverage_unconfirmed`. Текущий seq не подставляется задним числом; закрытие требует отдельного уполномоченного решения с причиной и аудитом.

**AC10 · P1. Завершение без ответа.** Given обращение не требует ответа; When сотрудник с отдельным полномочием руководителя явно закрывает выбранные обязательства с причиной; Then сохраняются ID и аудит без фиктивного сообщения и метрики человеческого ответа. Обычный оператор без полномочия получает отказ. Автоприветствие не повторяет это действие; новый inbound снова создает обязательство.

### Исходящие операции и конкуренция

**AC11 · P0. Идемпотентность команды.** Given один client key; When одинаковый ответ принят повторно; Then возвращается прежнее сообщение и исходный снимок. Иное содержимое вызывает конфликт, без нового job, пересчета покрытия и запроса провайдеру. Область ключа проверяется сервером.

**AC12 · P0. Семантика статусов.** Given сообщение accepted; When адаптер подтверждает отправку; Then записывается sent по контракту. Delivered/read возникают только из соответствующих доказательств. Callback связывается с provider ID и попыткой; поздний failed старой попытки не портит новую успешную.

**AC13 · P0. Неизвестный исход.** Given запрос мог покинуть процесс; When истекает таймаут; Then попытка получает unknown и job сверки/ручного разбора. Автоматический повтор запрещен без документированной идемпотентности или доказательства отсутствия принятой операции; UI сообщает возможность уже состоявшейся отправки.

**AC14 · P0. Истекший lease.** Given A выполняет запрос, lease истек; When B получает задачу; Then fencing запрещает A перезаписывать актуальное управление задачей. Полученный A внешний результат сохраняется как свидетельство конкретной попытки и проходит сверку, а не теряется. B учитывает уже начатый запрос; новый lease не доказывает отсутствие отправки и не разрешает слепой повтор.

**AC15 · P0. Противоречивые подтверждения.** Given provisional sent закрыл обязательство; When доказан окончательный отказ этой попытки; Then покрытие отзывается, обязательство открывается, если его не покрывает другой ответ. При уже доказанном delivered/read — conflict/manual, без автоматического downgrade и выдуманного повтора.

**AC16 · P1. Порядок диалога.** Given две команды одного диалога; When первая стала unknown; Then очередь явно показывает блокировку второй до решения по порядку. Другие диалоги продолжаются. Снятие блокировки фиксирует основание; часы и UUID не заменяют порядковый номер команды.

**AC17 · P0. Конфликт назначения.** Given assignment_version=7; When руководители одновременно передают диалог с ожидаемой версией 7; Then одна команда создает версию 8, другая получает конфликт и актуального владельца. CRM owner хранится отдельно; старый CRM-job не перетирает локальное назначение.

**AC18 · P0. Отзыв прав.** Given оператор подготовил ответ и файл; When доступ отозван до dispatch fence; Then отправка отменяется, скачивание заново авторизуется, ожидание открыто. Уже начатый remote send может дойти; фиксируются фактический исход и граница отзыва без обещания отмены.

**AC19 · P0. Подмена области.** Given оператор отдела A; When запрашивает чужой диалог, экспорт или файл по ID; Then сервер отказывает до выдачи данных и job. Поле employee ID не меняет автора. CRM-download gateway проверяет разрешенную область, а не только наличие ссылки.

### Клиенты и amoCRM

**AC20 · P0. Неоднозначное совпадение.** Given два контакта соответствуют проверяемому телефону; When приходит обращение; Then сохраняются кандидаты и состояние разбора без автоматического merge. Имя и аватар не доказательство. Сообщение доступно разрешенному оператору, но новый контакт не создается для обхода конфликта.

**AC21 · P0. Ноль контактов.** Given подходящего контакта нет; When два события запускают создание; Then сериализуется одно намерение по проверенному ключу. Выбран один путь: native auto-create Chats либо контролируемый REST, не оба. При таймауте выполняется сверка, а не повторное создание.

**AC22 · P1. Выбор сделки.** Given контакт имеет несколько активных и закрытых сделок; When приходит обращение; Then настроенное правило выбирает допустимую активную либо разбор. Закрытая не переоткрывается неявно; новая создается только с записанной причиной и версией правила.

**AC23 · P0. Эхо интеграции.** Given сообщение уже передано CRM; When возвращается его событие; Then correlation/binding распознает эхо без повторной отправки клиенту и нового обязательства. Текст и близкое время недостаточны; нераспознанный исходящий без снимка не закрывает ожидание автоматически.

**AC24 · P1. Конфликт полей CRM.** Given CRM owner изменен, локально ожидает старое обновление; When выполняется синхронизация; Then действует отдельная политика источника истины поля и версии. Неоднозначность видна поддержке; assignment_version не используется как версия CRM-сущности.

**AC25 · P0. Недоступность CRM.** Given канал исправен, CRM недоступна; When приходит сообщение и ответ через разрешенный интерфейс; Then локальная история и ожидание достоверны, CRM-jobs ждут восстановления. Повтор синхронизации не создает новый лид или повторный ответ; UI показывает задержку проекции.

### Медиа, ограничения и согласия

**AC26 · P1. Pending медиа.** Given входящее содержит файл; When загрузка остается pending; Then текст/placeholder доступны сразу, обязательство существует, media-job имеет deadline. CRM получает поддерживаемое представление состояния; ожидание файла не блокирует весь диалог и не создает повторных обращений.

**AC27 · P0. Небезопасный файл.** Given redirect ведет на внутренний адрес либо файл не проходит проверку; When работает media-worker; Then запрос блокируется/объект карантинируется, публичной ссылки нет. UI показывает ограничение; CRM не получает непроверенный файл, повтор не обходит проверку.

**AC28 · P1. Deadline медиа.** Given подготовка исходящего файла превысила deadline; When планировщик завершает job; Then сообщение требует действия оператора, содержимое не заменяется автоматически. Поздняя загрузка не возобновляет отмененную отправку, не закрывает обязательство и не создает скрытый внешний эффект.

**AC29 · P0. Окно истекло.** Given команда разрешена при приеме; When перед отправкой окно/capability недействительны; Then повторный preflight блокирует запрос, UI предлагает допустимое действие. Шаблон не подставляется автоматически; новая команда заново проверяет содержимое, согласие и снимок.

**AC30 · P0. Отзыв согласия.** Given согласие на конкретные канал/цель версии 9; When отзыв версии 10 закоммичен до dispatch fence; Then запрос не уходит. Уже начатый запрос может завершиться. Неоднозначный отказ клиента переводит соответствующую область в hold/manual до классификации, без универсальных юридических выводов.

**AC31 · P1. Истекшая ссылка.** Given ограниченная ссылка CRM истекла; When файл запрошен снова; Then gateway проверяет объект, область доступа и retention. Обновляется только разрешенная ссылка; удаленный файл не воскресает из кэша. UI отличает истечение ссылки от удаления вложения.

### Жизненный цикл и восстановление

**AC32 · P0. Исторический replay.** Given доверенный import-режим historical; When загружается старая переписка; Then история дедуплицируется без новых лидов, обязательств, SLA и уведомлений. Задержанный live-webhook с тем же старым timestamp сохраняет обычную бизнес-значимость и проходит отдельную дедупликацию.

**AC33 · P0. Ротация и личность.** Given обновлены credentials того же аккаунта; When задачи повторно проверяются; Then identity epoch прежний, разрешенные queued jobs продолжаются. При смене внешнего аккаунта epoch новый, старые задачи на сверке; совпавший номер не переносит историю/согласие автоматически.

**AC34 · P0. Старый epoch.** Given прежнее подключение отозвано и подключен другой аккаунт; When приходит старый webhook; Then сохраняется исходная область и событие идет в карантин/сверку. Переиспользованный внешний ID не связывает его с новой личностью, CRM и ожиданием нового аккаунта.

**AC35 · P0. Backup.** Given копия старше отправки и отзыва согласия; When сервис восстановлен; Then workers внешних эффектов стоят на барьере. Сверяются попытки, согласия, epoch и bindings. Старые queued jobs не выпускаются простым claim; недоказуемое актуальное согласие означает hold.

**AC36 · P0. Удаление вне порядка.** Given tombstone версии 5 сохранен; When приходит исходное сообщение/правка версии 3; Then payload не воскресает, применяется порядок адаптера. Неоднозначная версия требует сверки. Удаление не означает успешный ответ; отдельная политика снимает обязательство с причиной при необходимости.

**AC37 · P0. Retention.** Given истек срок хранения/одобрено удаление; When выполняется purge; Then очищаются payload, медиа, индексы и кэши, сохраняются минимальные разрешенные tombstone/audit. Backup учитывает удаление; аудит не становится бессрочной копией PII. Неочищенный объект отражается как незавершенная задача.

**AC38 · P1. Alert.** Given инцидент просроченной CRM-очереди открыт; When workers повторяют наблюдение; Then incident key создает одно первичное уведомление, последующие только по политике эскалации. Восстановление закрывает поколение один раз; новый сбой создает новое, без подавления нужного оповещения.

**AC39 · P0. Refresh.** Given один исполнитель обновляет OAuth; When внешний результат потерян; Then пара токенов не выдумывается, старый refresh не повторяется бесконечно. Подключение требует восстановления, jobs сохранены. Конкурентный worker не перезаписывает credentials устаревшей версией и не запускает отправку с недоказанным доступом.

**AC40 · P1. SLA.** Given два обязательства и новая версия календаря; When одно закрывается ответом; Then waiting_since указывает оставшееся, расчет воспроизводим по сохраненной политике. CRM-задержка измеряется отдельно. Новое входящее не обнуляет возраст старого открытого обязательства и эскалацию его ответственного.

**AC41 · P0. Переполнение вместимости.** Given у сотрудника один свободный активный слот; When два разных обращения назначаются параллельно; Then общий capacity fence позволяет занять только один слот, второе остается в очереди. Передача, отмена и повтор команды освобождают каждый слот не более одного раза. Возвращение клиента из waiting_customer повторно резервирует активный слот либо возвращает обращение в очередь.

**AC42 · P0. Обратимость профилей.** Given две исходные идентичности объединены в CanonicalProfile; When связь разъединена как ошибочная; Then исходные сообщения сохраняют авторов и адресатов, будущий matching использует новую версию связи. Согласия не копируются, отправленные сообщения не отменяются, автоматическое разъединение слитых сущностей CRM не обещается.

**AC43 · P0. Ручное подтверждение покрытия.** Given успешный человеческий ответ без снимка; When уполномоченный оператор выбирает конкретные обязательства и версии; Then покрытие ссылается на этот ответ и аудит. Без подтвержденного ответа попытка отклоняется либо требует отдельного полномочия завершения без ответа; новые правки не закрываются задним числом.

**AC44 · P1. SLA при правке.** Given непокрытый вопрос уже просрочен; When существенная правка создает заменяющее обязательство; Then оно наследует исходное начало ожидания, просрочка не обнуляется. Если исходный вопрос ранее действительно закрыт, новый вопрос/правка начинает новый цикл по политике, сохраняя историю старого.

**AC45 · P0. Граница доступа amoCRM.** Given локальные отделы изолированы, но выбранная CRM-карточка доступна постороннему отделу; When предлагается публикация переписки; Then несоответствие фиксируется до передачи данных. Публикация блокируется до согласованного безопасного решения; успешная проверка нашего API не считается доказательством защиты уже опубликованных CRM-сведений.

## Две временные гонки

### Гонка A: ответ, новое входящее, потерянное подтверждение

1. T0: открыто seq=41; сервер выдает снимок при подготовке ответа. API затем атомарно фиксирует ответ R с исходным снимком 41 и outbox, не расширяя покрытие на этапе приема.
2. T1: worker A сохраняет попытку и dispatch fence, вызывает провайдера; клиент мог получить R.
3. T2: входящее создает seq=42. Его commit не меняет снимок R.
4. T3: lease A истекает, B получает задачу; запрос A еще выполняется. B назначает сверку, не отправку: fencing защищает локальные записи, но не отменяет внешний запрос.
5. T4: приходит подтверждение с provider ID и связью с попыткой R. Валидируемая сверка сохраняет один успех; устаревший worker не перетирает актуальную версию.
6. T5: закрывается 41, seq=42 продолжает SLA. Повтор подтверждения ничего не меняет. Если связь с R недоказуема, сохраняется unknown и 41 остается открытым.
7. T6: окончательный failed именно этой попытки после provisional sent отзывает ее покрытие. При другом успешном ответе обязательство остается закрытым; при доказанном read возникает conflict/manual вместо downgrade.

### Гонка B: отзыв, смена владельца и внешний dispatch

1. T0: A имеет доступ, согласие версии 9 действительно, epoch=3; команда принята, файл pending.
2. T1: руководитель переводит диалог B, повышая assignment_version; отдельно приходит отзыв согласия версии 10 на канал/цель.
3. T2: media-job готов. Финальный preflight сериализуется с изменениями прав/согласия, проверяет окно и identity epoch, записывает dispatch fence и использованные версии.
4. Ветка I: отзыв или потеря прав раньше fence — blocked/cancelled, обязательства открыты. Новый владелец не получает права молча переотправить команду A.
5. Ветка II: fence и запрос раньше отзыва — отмена не гарантируется. Фиксируются версии разрешения и отзыв; подтвержденный успех закрывает только исходный снимок, последующие отправки запрещены.
6. Падение после fence без сетевого результата означает unknown и сверку. Ротация credentials не доказывает отсутствие запроса; новый identity epoch не превращает старую попытку в безопасный повтор.

## Матрица классификации отказов

| Класс | Доказательство | Jobs/решение | UI и внешние эффекты |
|---|---|---|---|
| До dispatch | Валидация/права/окно отклонены до сети | blocked; исправление | Причина; отправки нет |
| Временный без эффекта | Контракт доказывает отсутствие принятия | Ограниченный backoff, jitter, deadline | Повтор с исходным operation key |
| Ограничение нагрузки | Подтвержденный отказ по контракту | Допустимое отложенное выполнение | Фактические параметры адаптера |
| Постоянный отказ | Подтвержден запрет/невалидное содержимое | failed; исправление человеком | Без ложной доставки |
| Неизвестный исход | Timeout/crash после возможного dispatch | unknown; reconcile/manual | Возможна отправка; без слепого повтора |
| Отзыв доступа | Доказанный revoke/невосстановимые credentials | Блок подключения, восстановление | Очередь сохранена, секреты скрыты |
| Конфликт | Версии, CRM-кандидаты, противоречивые статусы | conflict; разбор | Без merge/downgrade по догадке |
| Опасные данные | Подпись/схема/файл не прошли проверку | reject/quarantine | Без распространения payload |
| Deadline | Срок исчерпан без доказанного успеха | Остановить автоматические попытки | Не переименовывать unknown в failed |

Класс определяется фазой и контрактом операции, а не одним HTTP-кодом. Send, создание CRM-сущности и refresh классифицируются отдельно. Новая попытка не стирает прежнюю; DLQ не разрешает повтор внешнего действия. Для каждого ручного решения нужны субъект, основание, область и связанная попытка.

## Свойства для будущих исполняемых проверок

- **Сохранность:** подтвержденный ingress имеет durable запись и достижимое состояние обработки; после восстановления зависимостей jobs продвигаются либо явно заблокированы с причиной.
- **Идемпотентность:** дубли и перестановки не меняют число логических сообщений, обязательств, CRM-намерений и alert-поколений.
- **Покрытие:** ответ закрывает подмножество неизменного серверного снимка; без подтвержденного успеха покрытие пусто. Native CRM/read/replay сами его не увеличивают.
- **Монотонность:** attention_seq и версии растут; старые мутации не воскрешают tombstone; противоречивый failed не отменяет доказанный read автоматически.
- **Внешняя неопределенность:** unknown не превращается в dispatch без записанного доказательства безопасности; fencing не считается гарантией единственности удаленного запроса.
- **Изоляция:** смена области, личности и epoch не переносит bindings, согласия, файлы и права на другую личность; credential rotation сохраняет проверенные связи.
- **Объяснимость:** назначение, matching, SLA, существенность правки и preflight воспроизводятся по сохраненным версиям правил и доказательствам.
- **Восстановление:** падения вокруг commit/dispatch/reconcile не снимают backup-барьер и не выпускают устаревшую очередь автоматически.

Будущая проверка генерирует перестановки, дубли, задержки и точки падения, затем сверяет БД, jobs, UI/CRM-проекции и журнал внешних вызовов. На 22.10.2026 исполняемые тесты для части этих свойств существуют и проходят; приёмка на боевых аккаунтах и live-проверка внешних каналов не выполнялись, поэтому подтверждение свойств на production-трафике не заявляется.
