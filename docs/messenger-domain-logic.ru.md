# Доменная логика внутреннего сервиса сообщений

Дата: 21.10.2026; статус уточнён 22.10.2026. Статус: доменная спецификация; правила реализованы в `apps/api` и покрыты тестами (см. [сценарии приемки](messenger-logic-acceptance.ru.md)). Возможности внешних API не подтверждены, live-проверка не выполнялась. Значения по умолчанию остаются предлагаемыми, пока не утверждены как политика компании. Область: одна компания, ее отделы и подключения WA/TG/MAX/VK, сотрудники и amoCRM. Документ уточняет [требования](messenger-platform-requirements.ru.md) и [архитектуру](messenger-platform-architecture.ru.md). Все правила ниже — предлагаемые значения по умолчанию; окончательные настройки перечислены в конце. Если конкретный адаптер не подтверждает необходимую возможность, сервис показывает ограничение и использует явно описанный запасной сценарий.

## 1. Агрегаты и границы решений

**Подключение Connection** определяет внешний аккаунт, доверенную идентичность отправителя, возможности, разрешения и эксплуатационное состояние. `binding_epoch` меняется при смене привязанной внешней идентичности. Обычная ротация секрета изменяет отдельный `credentials_version`. Старые задания не получают право отправлять от нового аккаунта автоматически.

**Диалог Conversation** — переписка в области конкретного подключения и внешнего чата. Контакт CRM не является идентификатором диалога. Один человек может обращаться через несколько каналов; несколько людей могут использовать общий номер. Объединение представления не объединяет адресатов, согласия и разрешения на отправку.

**Рабочее обращение WorkItem** — предмет ответственности отдела: вопрос, требующий обработки, со своим исполнителем, очередью и ожиданиями ответа. Для MVP предлагается одно активное обращение на диалог. Повторное обращение после закрытия создает следующее WorkItem, сохраняя историю переписки. Сложные параллельные темы потребуют явного разнесения сообщений между обращениями.

**Сообщение Message** содержит направление, источник, адресата, содержимое и версии; исходящая **операция отправки SendOperation** содержит намерение, идемпотентность и результат внешнего действия. **Обязательство внимания AttentionObligation** фиксирует конкретное необработанное входящее содержание. **CRM-связь Binding** хранит подтвержденное соответствие контактов, сделок и чатов. Эти объекты имеют отдельные версии; обновление статуса доставки не меняет владельца обращения.

Обязательные инварианты предлагаемой модели:

| Код | Правило |
|---|---|
| L01 | Адресат определяется неизменяемой связью подключения и внешнего чата, а не текущим телефоном CRM-контакта. |
| L02 | У обращения не более одного действующего владельца; каждое изменение назначения увеличивает `assignment_version`. |
| L03 | Повтор одной команды с тем же содержимым возвращает прежний результат; другое содержимое с тем же ключом дает конфликт. |
| L04 | Чтение, назначение, автоответ и неопределенная отправка не погашают обязательства внимания. |
| L05 | Подтвержденная отправка погашает только явно покрытые ею обязательства; новые входящие и правки сохраняются. |
| L06 | Внешний факт доставки нельзя создавать вручную; неизвестное значение не равно отрицательному. |
| L07 | Привязка CRM не дает права склеивать идентичности или копировать согласия между каналами. |
| L08 | Изменение доменного состояния, аудит и необходимые задания фиксируются атомарно. |
| L09 | Потеря уведомления очереди не уничтожает намерение: незавершенная операция остается обнаруживаемой в хранилище. |
| L10 | Событие старого binding epoch не исполняет команду для новой идентичности подключения. |

## 2. Независимые состояния

Предлагаемая модель запрещает единый флаг «чат активен», смешивающий техническое здоровье и работу оператора.

| Объект | Состояния и смысл |
|---|---|
| Connection | `setup`, `active`, `degraded`, `auth_required`, `paused`, `disabled`; отдельно разрешение отправки и прием событий. |
| Conversation | `open`, `archived`; отдельно доступность адресата и факт внешней блокировки, если он достоверно известен. |
| WorkItem | `queued`, `assigned`, `in_progress`, `waiting_customer`, `resolved`, `cancelled`. |
| SendOperation | `accepted`, `queued`, `dispatching`, `sent`, `failed`, `unknown`, `cancelled`. |
| Message content | `current`, `edited`, `deleted`; версии сохраняют связь с исходным сообщением. |
| Delivery evidence | `not_available`, `pending`, `delivered`, `failed`; факты связываются с конкретной внешней отправкой. |
| Read evidence | `not_available`, `not_observed`, `read`; прочтение клиентом отдельно от прочтения сотрудником. |

`sent` означает подтвержденный внешний успех согласно проверенному контракту адаптера; принятие нашим сервером означает только `accepted`. Погашение здесь — проектная метрика ответа, не доказательство доставки клиенту. `waiting_customer` допустимо после подтвержденного ответа и при отсутствии непокрытых обязательств. Если доставка впоследствии явно провалилась, покрытие этой отправки признается недействующим; обязательство восстанавливается, только если нет другого действующего подтвержденного ответа или явного решения о завершении. Обращение возвращается в очередь с причиной `delivery_failed`; история погашений сохраняется. Подтверждение прочтения не исчезает после старого события `sent`; противоречащие факты сохраняются для сверки.

`resolved` требует отсутствия открытых обязательств либо отдельного решения «завершить без ответа» с причиной и полномочием руководителя. Это решение не считается ответом клиента. Архивирование диалога не закрывает обращение. Новое входящее восстанавливает видимость диалога и открывает работу независимо от того, прочитан ли чат в CRM.

## 3. Что именно требует ответа

Каждое новое живое входящее сообщение создает AttentionObligation со стабильным ID и локальным возрастающим `attention_seq`. Существенная правка создает новое обязательство для новой версии: например, изменение суммы, адреса, требования или вложения. Для MVP предлагается считать любую содержательную правку существенной; технические изменения метаданных исключаются проверяемым правилом. Прежнее обязательство не удаляется молча: фиксируется его замещение новой версией, сохраняющее происхождение ожидания.

Последнего номера входящего недостаточно. Оператор может готовить ответ на старый вопрос, пока приходит новый; внешнее событие может опоздать. При начале подготовки сервер выдает `compose_snapshot_id`, перечень актуальных outstanding obligation IDs, версии содержимого, обращение, автора и `assignment_version`. Интерфейс позволяет исключить вопросы, на которые ответ не дается. Обновление снимка требует нового явного получения состояния; фоновое обновление списка сообщений не расширяет покрытие черновика.

При подтвержденном внешнем `sent` сервер погашает пересечение заявленного покрытия снимка с еще действующими обязательствами, проверяя версии. Если покрытая версия существенно изменилась после снимка, новое обязательство остается открытым. Ни `accepted`, ни `queued`, ни `dispatching`, ни `unknown`, ни автоматическое «получили ваше сообщение» не меняют ожидание ответа. Несколько ответов могут ссылаться на одно обязательство; повторное погашение идемпотентно.

Если снимка нет, но имеется надежный `reply_to`, предлагается покрывать только обязательство конкретного цитируемого сообщения и конкретной известной версии. Неизвестная версия не покрывает последующие правки. Ответ без снимка и без надежной ссылки получает `coverage_unconfirmed`: он виден в истории, но не закрывает очередь ожидания автоматически. Оператор может отдельно подтвердить покрытие, выбрав обязательства и причину; действие обязательно ссылается на конкретный подтвержденно отправленный человеческий ответ, проверяет версии и полномочия, сохраняется в аудите. Без такого ответа допустимо только отдельное «завершить без ответа» с соответствующим полномочием; выдавать его за метрику ответа нельзя.

В стандартном интерфейсе amoCRM нельзя предполагать наличие снимка подготовки или достоверного автора. Для MVP выбирается явное ограничение: исходящие из штатного чата без этих данных имеют `coverage_unconfirmed`; подтверждение покрытия выполняется вручную в минимальном виджете. Если прототип подтвердит необходимые данные, автоматизация добавляется отдельным решением. При неизвестном авторе контроль персонального назначения через такой путь также недоказуем: отправку направляют в контролируемый интерфейс либо включают отдельно согласованный режим прав отдела.

Пример: в 10:00 поступает A (`seq=41`), в 10:01 — B (`42`). Анна получает снимок {A,B}. В 10:02 появляется C (`43`), а клиент меняет сумму в A, создавая A2 (`44`). В 10:03 ответ Анны становится `sent`: покрывается B; C и A2 остаются. Если результат `unknown`, не покрывается даже B. Поздно доставленное живое входящее D создает новое обязательство независимо от старой временной метки платформы.

Исторический импорт помечается только доверенным заданием импорта с известным происхождением. Возраст сообщения не доказывает, что это история. Импорт не создает оперативные ожидания автоматически, но допускает отдельную контролируемую постановку в работу. Удаление входящего сохраняет обезличенный след связи по политике хранения; предлагаемый порядок требует ручного решения по оставшемуся вопросу, а не автоматического исчезновения ожидания.

## 4. Владение и конкурентные команды

Владелец хранится на WorkItem вместе с отделом и `assignment_version`. Взятие из очереди использует compare-and-swap: сервер сравнивает ожидаемую версию и отсутствие владельца, проверяет право отдела, вместимость и доступность сотрудника. В одной транзакции назначаются владелец, новая версия, слот нагрузки и аудит. Два одновременных запроса дают одного победителя; второй получает актуальное назначение и конфликт, без скрытого перехвата.

Передача между отделами проверяет полномочия передающего, доступ принимающего отдела к подключению и допустимость данных. Передача прямо сотруднику дополнительно проверяет его членство и вместимость. По умолчанию межотдельная передача идет в очередь отдела; ответственному руководителю доступно обоснованное принудительное назначение. Смена ответственного сделки CRM не изменяет владельца обращения неявно: создается предложение переназначения.

Каждая команда изменения требует ожидаемой версии. Черновик не резервирует владение. При начале внешней отправки worker атомарно проверяет актуальные права, назначение, epoch, ограничения канала и согласие; переводит операцию в `dispatching` и записывает dispatch fence: проверенные версии и время допуска. При передаче поставленные в очередь операции прежнего владельца отменяются или требуют повторного подтверждения нового владельца.

Внешний запрос, уже начавшийся после допуска, нельзя гарантированно отозвать передачей или выходом сотрудника. Интерфейс показывает находящуюся в отправке операцию новому владельцу, а аудит связывает результат с прежним допуском. Dispatch fence доказывает момент проверки, но не обеспечивает общей транзакции с платформой. Если отзыв согласия произошел после допуска, незапущенные операции блокируются, а начавшаяся фиксируется как возможная внешняя отправка.

Ниже — запись контрактов; команды реализованы в `apps/api` (`repo/assignment.ts`, `repo/attention.ts`). Запись не описывает endpoints и не заменяет код.

```text
КОМАНДА ClaimWork(item, expected_assignment_version, request_key)
  проверить сессию, права отдела, availability и capacity;
  атомарно: если owner отсутствует и версия совпала,
    занять слот; назначить actor; увеличить assignment_version;
    записать audit и результат request_key;
  иначе вернуть conflict с текущей версией.

КОМАНДА AcceptReply(item, snapshot, selected_obligations, content, key)
  проверить назначение, снимок, версии содержания и разрешения;
  атомарно создать accepted SendOperation с неизменным покрытием;
  сохранить намерение отправки; вернуть существующую операцию при повторе;
  обязательства пока не погашать.

КОМАНДА ConfirmExternalSend(operation, provider_evidence)
  дедуплицировать и проверить принадлежность внешнего подтверждения;
  атомарно записать sent и внешний ID;
  погасить только допустимое неизменившееся покрытие;
  сохранить оставшиеся ожидания, аудит и задания синхронизации CRM.
```

## 5. Очереди, нагрузка и календарь

Предлагаемый маршрут определяется последовательно: подключение → разрешенный отдел → правило темы/источника → общая очередь отдела. Явная ранее подтвержденная связь с обслуживающим отделом имеет приоритет только при сохранении его доступа. Имя отправителя, текстовое совпадение телефона или случайный ответственный старой сделки не достаточны для маршрута. Неоднозначный маршрут поступает в очередь диспетчера, сохраняя исходный канал.

Автоматическое назначение выбирает сотрудников с действующим членством, разрешением канала, рабочей сменой, статусом `available` и свободной вместимостью. Предлагаемая вместимость считает активные обращения в `assigned/in_progress`; ожидание клиента имеет отдельный лимит. Слот резервируется атомарно с назначением под общей блокировкой или версией счетчика сотрудника: CAS разных обращений сам по себе не защищает вместимость. Передача и завершение освобождают прежний слот той же транзакцией; повтор освобождения идемпотентен. Порядок очереди: нарушенный срок, затем приоритет и время самого раннего открытого обязательства; равенство разрешается стабильным ID. Правила повышенного приоритета должны иметь проверяемое основание.

Отсутствие подходящего сотрудника не теряет обращение: оно остается в очереди с причиной `no_capacity`, `off_hours` или `no_eligible_staff`. Истечение lease worker не передает клиента другому человеку автоматически. Потеря присутствия оператора сначала уведомляет руководителя; таймаут и разрешение автоматического возврата в очередь задаются отдельно. Это снижает риск двух параллельных ответов при кратком разрыве интерфейса.

Календарь принадлежит отделу, содержит часовую зону, интервалы, праздники и исключения. SLA считается по рабочему времени этого календаря с сохранением календарной версии. `waiting_since` — начало самого раннего открытого обязательства; чтение и автоответ его не обнуляют. Существенная правка незакрытого вопроса наследует начало ожидания замененного обязательства: изменение версии не обнуляет просрочку. При передаче накопленное ожидание сохраняется, а смена календаря фиксируется явно. Пауза SLA при ожидании клиента допустима лишь при отсутствии открытых обязательств; остановка подключения сама по себе паузой не является.

### Переходы рабочего обращения

Ключевые переходы WorkItem должны быть явными, а не побочным эффектом отображения чата:

| Событие | Условие и переход |
|---|---|
| Новое живое входящее | Нет активного WorkItem → создать `queued`; существующее `resolved` не переписывать, открыть следующий цикл. |
| Взять обращение | `queued` → `assigned` при успешном CAS и резервировании слота. |
| Начать работу | `assigned` → `in_progress` явной командой владельца; чтение само переход не выполняет. |
| Подтвержденный ответ | Нет открытых обязательств → `waiting_customer`, активный слот освобождается, слот ожидания резервируется атомарно. Если остались вопросы — `in_progress`. |
| Клиент вернулся | `waiting_customer` → `assigned`, если прежний владелец допустим и активный слот доступен; иначе `queued` разрешенного отдела. Версия назначения и счетчики обновляются атомарно. |
| Завершить | Нет обязательств и опасной незавершенной отправки → `resolved`; иначе отдельное решение с полномочиями и видимой причиной. |
| Передать | Старое назначение и слот снимаются, новое назначение/очередь создаются одной транзакцией; SLA сохраняется. |
| Unknown отправки | Рабочее ожидание не закрывается; состояние операции показывается отдельно от WorkItem. |

Открытое обращение не закрывается автоматически от тишины без отдельной утвержденной политики. Любое исключительное завершение при `dispatching/unknown` обязано сохранить видимость незавершенной операции и последующее сверочное задание, а не удалить их.

## 6. Сопоставление с amoCRM

Предлагаемая процедура сначала ищет подтвержденную локальную Binding для конкретной идентичности в конкретном CRM-аккаунте. Затем использует разрешенные точные признаки, например нормализованный проверенный телефон, сохраняя происхождение значения. Телефон из профиля мессенджера и телефон, введенный оператором, имеют разные уровни доверия. Совпадение имени никогда не создает автоматическую связь. Один контакт может иметь несколько идентичностей; одна идентичность может требовать ручного разрешения нескольких кандидатов.

Результат поиска имеет отдельное состояние: `matched`, `not_found`, `ambiguous`, `pending_creation`, `creation_unknown`, `manual_review`. Несколько точных контактов — неоднозначность, а не выбор первой строки. Оператор видит кандидатов и основание совпадения в пределах своих прав. Если прав просмотра недостаточно, выбор передается ответственному сотруднику; скрытый контакт не превращается в отсутствие контакта.

После контакта отдельно выбирается сделка. При одной подходящей открытой сделке допускается автоматическая связь по согласованному правилу воронки и отдела. Несколько открытых сделок, несколько связанных контактов, закрытая сделка или другая воронка требуют выбора. Предлагаемое значение: закрытую сделку не переоткрывать; создавать новое обращение и предлагать новую сделку. Связь чата с контактом не означает связь всех сообщений со всеми его сделками.

При нуле совпадений выбирается один путь создания: контролируемый REST с последующей Binding либо подтвержденное прототипом штатное создание через Chats API. Одновременное включение обоих путей запрещено. Предлагаемый MVP использует контролируемое создание и техническую очередь неразобранных обращений в минимальном интерфейсе. При неоднозначности нельзя помещать сообщения в произвольную карточку; staging сохраняет переписку и дает уполномоченному сотруднику разрешить связь до публикации в CRM.

Создание контакта и сделки сериализуется по локальному ключу намерения, с состоянием и внешними ID. После таймаута `creation_unknown` блокирует повторное создание: выполняется доступная сверка или ручной разбор. Универсальный поиск по произвольному TrackingId не предполагается. Если API не позволяет надежную корреляцию, интерфейс прямо показывает ограничение. Разрешение неоднозначности сохраняет автора, кандидатов, выбранные сущности и версию правила.

Слияние контактов в CRM не объединяет автоматически согласия и обращения. Исчезнувшая сделка переводит связь в `broken`, сохраняя сообщения; восстановление требует новой подтвержденной связи. Ошибка CRM не блокирует надежный прием входящего. Отправка разрешается по каналу и правам обращения; обязательность CRM-привязки перед ответом остается отдельной настройкой.

## 7. Источники истины и конфликт изменений

| Поля | Предлагаемый источник истины и реакция |
|---|---|
| Внешний адресат, ID, факты отправки/доставки | Подтвержденные данные канала; CRM не переписывает адресата существующей операции. |
| Владелец, очередь, obligations, покрытие | Домен сервиса; CRM получает проекцию или явную команду через проверенный ingress. |
| ФИО, компания, этап и ответственный сделки | CRM; локальные изменения отправляются как запросы с обнаружением конфликта. |
| Согласия и отзыв по цели | Реестр сервиса с происхождением; пустое поле CRM не снимает запрет. |
| Прочтение сотрудником | Персональное состояние сервиса, отдельно от доступных событий CRM. |
| Текст сообщения | Источник соответствующего сообщения; правка рассматривается как версия, а не новый ответ. |

Конфликт определяется относительно последней синхронизированной версии поля, а не сравнением часов двух систем. Если обе стороны изменили значение, применяется владеющий источник; отвергнутое изменение и причина сохраняются. Для опасной смены CRM-связи требуется ручное решение. Если API не дает версии, гарантировать CAS на удаленной стороне нельзя: нужны повторное чтение и очередь конфликтов.

Эхо подавляется по сохраненным соответствиям операции, сообщения и внешнего события. Совпадение текста и времени не доказывает эхо. Исходящее из родного приложения канала сохраняется как внешний факт; неизвестный автор и отсутствие снимка дают `coverage_unconfirmed`. Повтор статуса не создает сообщение и не расширяет покрытие.

Удаление порождает tombstone со ссылкой и версией, чтобы запоздалое событие не воскресило объект. Tombstone не означает вечное хранение персональных данных: минимальные идентификаторы, сроки очистки и удаление содержимого определяются политикой. После восстановления резервной копии старые исходящие не выпускаются до сверки внешних результатов, согласий и актуальных привязок.

## 8. Ошибки оператора и проектные решения

Предлагаемые сообщения интерфейса должны объяснять действие: «Обращение уже взял Борис; обновите назначение», «Ответ принят сервисом, результат канала неизвестен; повтор может создать дубль», «После начала ответа появились новый вопрос и правка суммы», «Найдено два контакта; выберите подтвержденный», «Отправка началась до передачи; возможен ответ прежнего владельца». Кнопка повторной отправки создает отдельное решение только после классификации исхода; технический сбой не маскируется успешным ответом.

Отзыв согласия хранится по каналу и цели. Неоднозначное «СТОП» предлагает безопасную широкую приостановку исходящих с ручным уточнением области; автоматическое безусловное толкование для всех сообщений и целей не задается. Разрешенные исключения не выдумываются сервисом: правило требует отдельно утвержденного основания и возможностей канала.

До реализации согласуются четыре группы конфигурации:

1. **Обслуживание:** отделы, правила маршрута, вместимость, календари, SLA, таймаут отсутствия, полномочия принудительной передачи и закрытия без ответа.
2. **Ответы:** минимальный виджет amoCRM для снимков/ручного покрытия, допустимые внешние интерфейсы отправки, надежность actor и reply_to, критерии существенной правки, обработка удаления входящего.
3. **CRM и идентичности:** доверенные признаки, правила нескольких контактов/сделок, создание и обязательность привязки, полномочия ручного сопоставления, обработка слияний и недоступных сущностей.
4. **Каналы и данные:** подтвержденные возможности адаптеров, разрешенные цели исходящих и согласия, политика неоднозначного отказа, сроки хранения/tombstone, сверка unknown и восстановление backup.

Приемка этих решений включает конкурентный захват, передачу во время отправки, новое входящее и правку после снимка, позднее живое событие, исходящее без автора из amoCRM, таймаут создания CRM-сущности и восстановление удаленной связи. Проверяется конечное доменное состояние и аудит, а не только внешний вид переписки.

## 9. Фиксация отправки, сроки и границы восстановления

Принятая команда фиксирует адресата, epoch, содержимое/версии вложений, цель, снимок покрытия и исходный deadline. Повтор технической попытки не продлевает deadline и не расширяет покрытие. При смене текста, шаблона, адресата или отправляющего аккаунта требуется новая явная команда; старая операция сохраняет историю. Поступление готового файла после отмены не возобновляет отправку.

Перед внешним вызовом повторно проверяются доступ, согласие, назначение, версия привязки и возможности канала. Предварительная оценка времени подготовки — подсказка, а не доказательство попадания в окно. Если окно закрылось, сервис блокирует несовместимую отправку, не заменяет произвольный текст шаблоном автоматически и не отправляет от другого номера. Для неизвестного исхода истечение deadline прекращает повторы, но не превращает возможную доставку в доказанный отказ.

Предлагаемый строгий порядок исходящих блокирует следующие команды того же диалога за `unknown`. Другие диалоги продолжаются. Руководитель может разрешить продолжение, видя риск перестановки/дубля; это отдельное решение, которое не исправляет и не скрывает исход первой операции. Возобновление очереди после `auth_required` повторяет бизнес-проверки, а не только проверку токена. Обычная ротация credentials не меняет адресата и не инвалидирует все задачи, но версия допуска должна быть обновлена.

Если worker потерял lease, он теряет право управлять актуальным заданием, но полученное внешнее свидетельство остается значимым: оно сохраняется для конкретной попытки и сверки. Запрет устаревшей записи состояния не означает уничтожение доказательства уже состоявшейся отправки.

Объединение клиентских профилей реализуется версионированными связями OriginIdentity → CanonicalProfile; исходные идентичности сообщений неизменяемы. Разъединение меняет представление и будущие правила сопоставления, но не отменяет внешние отправки и не обещает автоматически разъединить слитые сущности amoCRM. Спорная принадлежность общего или переиспользованного номера требует ручного разбора; совпадение номера не доказывает того же человека навсегда.

Локальный RBAC не ограничивает уже опубликованные сведения внутри amoCRM. До проекции переписки проверяется, что права на CRM-сущность соответствуют согласованному доступу отдела. Если штатная CRM не обеспечивает требуемую изоляцию, это блокер публикации соответствующих данных: выбираются другой способ размещения, ограничения пилота или контролируемый inbox, а не обещание защиты только нашим API.

Связанные [45 сценариев приемки](messenger-logic-acceptance.ru.md) проверяют эти правила на уровне ожидаемых состояний и внешних эффектов. Реализация существует в `apps/api`; 31 из 45 сценариев связаны с исполняемыми тестами, приёмка на боевых аккаунтах не проводилась.
