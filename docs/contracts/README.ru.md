# Контракты первого production-среза

Текущий target реализации — [контракт v2](v2.ru.md). V1 ниже сохранен как исходный черновик совместимости; новые события и API вынесены в явный major v2, без изменения опубликованных определений v1.

Статус (актуализировано 22.10.2026): операторский HTTP API и нормализованные события подключены к runtime production-ядра. Маршруты зарегистрированы в apps/api/src/app.ts; операторские чтения и команды смонтированы под /api/v2/operator (v1-пути в runtime не смонтированы), события проходят durable inbox с дедупликацией. Подтверждено кодом и тестами apps/api (306 тестов, все pass) и tsc --noEmit. Диагностика подключена в объёме logger с redaction; полная валидация DiagnosticEvent по схеме в runtime не заявляется. Локальный стенд local-telegram/ по-прежнему использует собственные /api/chats маршруты и SQLite; совместимость его wire-format с v1 не заявляется.

## Артефакты и проверка

- [v1.json](../../packages/contracts/schema/v1.json): именованные JSON Schema 2020-12 определения; валидировать через конкретный $defs, а не корневой объект-библиотеку.
- [api.v1.json](../../packages/contracts/schema/api.v1.json): OpenAPI 3.1.1 с запросами, ответами, ошибками и постраничным чтением.
- [capabilities.v1.json](../../packages/contracts/schema/capabilities.v1.json): стартовые профили возможностей, а не настройки действующих аккаунтов.
- [тесты](../../packages/contracts/test/): Ajv2020 strict, проверка форматов, положительные и отрицательные примеры.

Из корня: npm --prefix packages/contracts ci --ignore-scripts, затем npm --prefix packages/contracts test. Проверяется форма данных и разрешимость ссылок OpenAPI, а не соответствие всего документа метасхеме OpenAPI и не работа HTTP-сервера. Схемы не изменяют входные данные: нет coercion, удаления неизвестных полей или подстановки defaults.

## Операторский API

Все пути имеют префикс /api/v1/operator. Автор и доступ определяются сервером из сессии; идентификатор компании не принимается из тела. Срок сессии и RBAC реализованы (актуализировано 22.10.2026: apps/api/src/auth и apps/api/src/platform/auth.ts); защита CSRF и проверка Origin в runtime не заявляются. Запись security в OpenAPI этого не реализует.

| Метод и путь | Запрос | Успех | Назначение |
|---|---|---|---|
| GET /work-items | after, limit 1..100 | WorkItemList, 200 | Разрешённые обращения |
| GET /work-items/{id} | — | WorkItemDetail, 200 | Обращение, диалог и обязательства |
| GET /work-items/{id}/messages | after, limit | MessageList, 200 | История без изменения внимания |
| GET /connections | — | ConnectionList, 200 | Состояние возможностей без секретов |
| GET /send-operations/{id} | — | SendOperation, 200 | Достоверный исход операции |
| POST /work-items/{id}/snapshot | EmptyRequest | ComposeSnapshot, 200 | Зафиксировать версии покрытия |
| POST /work-items/{id}/claim | ClaimRequest | WorkItem, 200 | Взять через CAS и capacity fence |
| POST /work-items/{id}/transfer | TransferRequest | WorkItem, 200 | Передать в отдел/исполнителю |
| POST /work-items/{id}/reply | SendReplyRequest | SendOperation, 202 | Принять намерение, не обещать доставку |
| POST /work-items/{id}/manual-coverage | ManualCoverageRequest | WorkItem, 200 | Подтвердить покрытие успешным человеческим ответом |
| POST /work-items/{id}/resolve | ResolveRequest | WorkItem, 200 | Завершить при выполненных условиях |

Общие ошибки описаны ApiError: 400/422 — форма, 401/403 — сессия/доступ, 404 — отсутствующий разрешённый ресурс, 409 — версия/epoch/конфликт ключа, 429 — лимит, 503 — недоступность. Конкретное сопоставление code/status реализует сервер. До проверки доступа нельзя раскрывать чужое назначение или существование диалога. requestId — внутренний идентификатор диагностики, не текст запроса.

Постраничный cursor непрозрачен клиенту и привязан к фильтру и разрешённой области. Семантика стабильного порядка и повторной проверки доступа реализована (актуализировано 22.10.2026): apps/api/src/operator/service.ts и покрытие тестами в apps/api/test/operator-routes.test.ts.

## Инварианты L01–L10

| Инвариант | Нормативное поведение и граница схемы |
|---|---|
| L01: адресат | WorkItem → Conversation → неизменяемая пара connection/externalChat. Actor, recipient и connection не принимаются SendReplyRequest. Schema отвергает лишние поля; сервер обязан проверить связь и epoch. |
| L02: владелец | Canonical states: queued, assigned, in_progress, waiting_customer, resolved, cancelled. Claim/transfer проверяют expectedAssignmentVersion и вместимость одной транзакцией. Версия растёт при смене назначения, а не при каждом прочтении/ответе. Schema не реализует CAS. |
| L03: идемпотентность | Область: server company + command type + key. Fingerprint включает route WorkItem, снимок, текст, покрытие и deadline. Повтор того же содержания возвращает прежнюю операцию без нового внешнего действия; другое содержание даёт IDEMPOTENCY_CONFLICT. Авторизация проверяется и при повторе. |
| L04: внимание | Чтение сотрудником, автоответ, accepted, queued, dispatching и unknown не закрывают обязательства. Unknown не разрешает слепой повтор. Отдельное управляемое решение возможно только после доказательства отсутствия отправки или подтверждённой внешней идемпотентности. |
| L05: покрытие | Read DTO Obligation связывает obligationId с обязательным messageId и contentVersion; так оператор видит конкретный вопрос. Снимок сохраняет workItem, conversation, epoch, assignmentVersion и версии обязательств. Выбор — подмножество снимка. Пустой выбор допустим: дополнительная реплика ничего не закрывает. Только подтверждённый человеческий sent покрывает ещё действующие выбранные версии; новые входящие/правки остаются. Полное совпадение повторных refs запрещает schema; повтор одного ID с разными версиями и сверку снимка проверяет сервер. |
| L06: внешние факты | sent — подтверждённый успех по проверенному контракту адаптера. Он не означает delivered/read. EvidenceData ссылается на сохранённое свидетельство, но строка evidenceKey сама не доказывает его подлинность. Crypto-доказательство не требуется универсально и не обещается. Противоречия и поздние результаты попыток проходят сверку, без фиктивного downgrade. |
| L07: CRM и идентичность | CRM binding и объединение представления не меняют исходные идентичности, адресатов и согласия. Версионированное объединённое представление возможно отдельно; автоматический merge идентичностей по имени/телефону запрещён. |
| L08: атомарность | Доменное состояние, аудит и SQL outbox фиксируются одной транзакцией БД. Внешний брокер, CRM и канал не входят в эту транзакцию; уведомление брокера может потеряться, durable outbox остаётся. |
| L09: намерение | SendOperation создаётся до сетевого вызова. Worker повторно проверяет права, назначение, epoch, согласие, deadline и возможности на dispatch fence. Смена владельца не гарантирует отзыв уже начатого внешнего запроса. |
| L10: epoch | Смена внешней личности подключения меняет bindingEpoch; старые события сохраняются в прежней области и уходят в quarantine/reconciliation. Их нельзя применять к новому аккаунту. credentialsVersion меняется при ротации секрета той же личности; смена webhook URL сама по себе не меняет epoch. |

Значение expectedAssignmentVersion >= 0 — только форма. Схема не может определить, устарела ли положительная версия относительно БД. Аналогично строка snapshotId не доказывает принадлежность снимка сессии.

## Нормализованные события и профили каналов

EventEnvelope — внутренний факт после применения durable inbox, не публичный webhook провайдера. Пара connectionId/bindingEpoch ограничивает внешние ID. providerEventKey хранит адаптерный ключ, если он есть; domain assignment events могут иметь null. sourceMode historical устанавливает только доверенное import-задание с importJobId и без нового оперативного obligation. Возраст timestamp не позволяет объявить live-событие историей. Правки и удаления сохраняют версии; удаление не считается ответом. Обработка и дедупликация реализованы транзакционно (актуализировано 22.10.2026): apps/api/src/channels/inbox.ts и apps/api/src/telegram/inbox.ts используют ON CONFLICT по (company, connection, bindingEpoch, providerEventKey), повтор с иным содержимым даёт конфликт; покрыто тестами apps/api/test/e2e-flow.test.ts и telegram-*.

Реестр различает Telegram bot, personal и business, WhatsApp Cloud и QR, MAX bot и VK community. Только textReply Telegram bot отмечен supported в области local-prototype по результату локального стенда. Это не подтверждает production-доступность. Все остальные значения — unknown до отдельного PoC и проверки аккаунтов. Неизвестная capability не даёт разрешение на отправку; effective policy должна блокировать неподтверждённое действие.

## Диагностика без содержимого переписки

DiagnosticEvent — whitelist: schemaVersion, timestamp, level, фиксированные event/outcome/errorCode и correlation requestId/operationId/eventId; необязательный durationMs — конечное неотрицательное число миллисекунд. Неизвестные operationId/eventId передаются null, а не фиктивными значениями. Поля text, token, authorization, rawPayload, errorMessage и customerPhone отвергаются; произвольный errorCode запрещён. Correlation заполняется **только сгенерированными внутренними ID**, не внешними chat ID, именами, телефонами или пользовательским текстом. Тесты формы не доказывают отсутствия PII внутри ошибочно подставленного похожего ID.

Runtime logger, преобразование ошибок и redaction реализованы (актуализировано 22.10.2026): apps/api/src/platform/logger.ts выполняет key-based redaction, общий error handler — в apps/api/src/app.ts, отсутствие токена и текста в логах проверяет apps/api/test/telegram-privacy.test.ts перехватом stdout. Полная валидация DiagnosticEvent по схеме в runtime не заявляется. Передавать произвольный объект провайдера в лог и считать одну schema защитой по-прежнему нельзя. События ingress/dispatch/completion связываются корреляцией; метрики не содержат текста и персональных labels.

## Совместимость и приёмка

Версия 1.0.0 — черновой новый wire-контракт. Имя schemaVersion=1 определяет major для событий; будущий HTTP major находится в URL. С strict additionalProperties:false добавление поля, enum-значения или нового event-kind может сломать старого потребителя и требует major либо явного согласования отдельной версии схемы. Minor не означает автоматическую совместимость. Используется Ajv 8.20.0: первоначальный pin 8.17.1 заменён после npm audit (GHSA-2g4f-4pwh-qvx6, ReDoS с $data; опция в пакете не включена). Patch контракта допускает исправление документации/описания без изменения принимаемого множества данных.

| Сценарии | Что уже проверяется | Что остаётся runtime-проверкой |
|---|---|---|
| AC07, AC43 | Снимок, refs с версиями, отсутствие точных дублей; отдельная manual coverage command | Новое входящее/правка после снимка; успешный человеческий ответ и аудит |
| AC08, AC12, AC13 | Enum статусов, раздельные evidence; недопустимые поля/исходы отвергаются | Unknown без повтора, классификация ошибок и последствия доставки |
| AC11 | Форма idempotencyKey и команды | Атомарное равенство fingerprint, возврат предыдущего результата, конфликт |
| AC17, AC18, AC41 | Форма assignmentVersion, отсутствие подставного actor | CAS, отзыв прав, capacity fence и гонка dispatch |
| AC29, AC33, AC34 | Режимы каналов, epoch отдельно от credentialsVersion | Preflight возможностей/согласия, смена личности и карантин старых событий |
| Диагностика | Whitelist и отрицательные примеры секретных/текстовых полей | Реальный logger/redaction, недоверенные исключения, PII в значениях |

Актуализировано 22.10.2026: перечисленные runtime-проверки в значительной части реализованы в apps/api (идемпотентность и конфликт fingerprint, CAS/capacity fence, manual coverage, стабильная пагинация) и покрыты тестами operator-routes, e2e-flow, connections и telegram-send; сквозная проверка с реальными каналами и доступами провайдеров остаётся.

Для начального draft файлы получены от Antigravity до нового требования TDD; исходный RED для них не заявляется. Новые review-тесты написаны до соответствующих исправлений: реальный npm test дал 15 tests / 10 pass / 5 fail, затем после исправлений — 15/15. Для durationMs и статического ограничения confirmed coverage → sent отдельно получен RED 17 tests / 15 pass / 2 fail до реализации. Для обязательной связи Obligation → messageId получен RED 20 tests / 19 pass / 1 fail, затем GREEN 20/20. После добавления регрессий исторического импорта и реестра итог — 20/20. Дальнейшие тесты расширяют регрессии и не выдаются за прежний RED. Актуальный прогон на 22.10.2026: apps/api — 306 тестов, 306 pass, 0 fail; npx tsc --noEmit — exit 0.

Последующее уточнение спецификации #2 выполнено в [v2](v2.ru.md): lifecycle/health, отдельные native outbound/delivery/read facts, CRM/media/staff/notification границы и mapping PostgreSQL. Актуализировано 22.10.2026: runtime API, auth, logger и durable effects реализованы в apps/api и покрыты тестами. Матрица приёмки 45 AC строится (apps/api/src/acceptance/matrix.ts), но без прогона результатов сценарии остаются NOT RUN; сквозная приёмка с реальными каналами не заявляется. Решение о приёмке #2 принимает независимая проверка согласованности контрактов, а не наличие работающего HTTP-сервера.
