# Входящие файлы Telegram → amoCRM

## Режим действующего REST-пилота

Если для подключения включён `AMOCRM_LEAD_CAPTURE_*`, но Chats API ещё не
зарегистрирован, `AMOCRM_CAPTURE_FILES_ENABLED=true` включает доставку оригинала
в раздел «Файлы» связанной сделки через официальный Files API amoCRM. Необходим
уже выданный OAuth scope «Доступ к файлам». S3 для этой ветки не требуется:
байты сохраняет amoCRM. Это явный режим REST-пилота, а не эмуляция сообщения чата.

Сначала проверяются маршрут, активность аккаунта/подключения, epoch и политика;
затем Telegram скачивается с существующими ограничениями и проверкой MIME.
Используется сделка, которую вернула текущая синхронизация этого диалога.
Исходное имя, MIME и размер передаются при создании файловой сессии; байты
отправляются последовательными частями в проверенный файловый origin amoCRM.

Миграция 18 добавляет `amocrm_file_deliveries`: одна запись на компанию, аккаунт
и сообщение. UUID загруженного файла сохраняется до привязки к сделке. Повторы
проверяют существующую связь и используют тот же UUID. Неопределённый исход
загрузки фиксируется как `unknown` и требует ручной сверки; автоматическая
повторная загрузка запрещена. Истёкший lease также не создаёт второй файл.
Исходящие сообщения Telegram и настройки существующего Wazzup эта опция не меняет.

Нативный чат по-прежнему требует отдельной регистрации канала Chats API в
поддержке amoCRM. Добавление телефона/username к контакту не заменяет регистрацию.

## Ветка зарегистрированного Chats API

Путь использует Telegram Bot API и amoCRM Chats API: durable inbox → сообщение и
outbox → скачивание `getFile` → проверка MIME/байтов и закрытый S3 → импорт сообщения
с `type`, `media`, `file_name`, `file_size` и подписью исходного сообщения.
Поддерживаются документы, фотографии, видео, аудио и голосовые сообщения в пределах
существующего allowlist MIME; лимит скачивания Bot API — 20 МиБ. Неизвестные типы и
отклонённые вложения не подменяются успешным сообщением с одной подписью.

## Настройка

- Настроить существующие Telegram, OAuth и Chats channel/scope, CRM-маршрут и политику импорта.
- API и worker должны использовать один S3 bucket, БД и одинаковый `SESSION_SECRET`.
- Задать `AMOCRM_MEDIA_BASE_URL` как публичный HTTPS origin API, например
  `https://messengers.example.com`, без пути, query, fragment или credentials.
  Compose уже передаёт общий `.env` обоим процессам. Значения секретов в документацию не копировать.
- Reverse proxy должен пропускать GET/HEAD `/api/v2/amocrm/media/:attachmentId/content`
  без Basic Auth/операторской сессии и не логировать query strings. Существующий
  nginx-шаблон использует безопасный формат логов. Реальный proxy требует отдельной проверки.

В поле `media` передаётся стабильная HMAC-SHA256 ссылка на один файл в одной компании
и CRM-аккаунте. Она переживает перезапуск и отложенное открытие, не содержит Telegram
токен или S3 grant. Получатель ссылки может скачать файл; её нельзя публиковать или
логировать. URL не сохраняется в outbox/версии сообщения и строится из архивных данных.

Каждое скачивание проверяет подпись, активность аккаунта и подключения, текущий
binding epoch, принадлежность CRM-маршруту, политику импорта и состояние архива.
Архивные группы без CRM-допуска недоступны. API возвращает сохранённые имя и MIME,
проверяет длину и SHA-256 байтов, запрещает кеширование. Чтение S3 ограничено
ожидаемым числом байтов и 15 секундами с отменой запроса и потока. Одновременно
допускаются два скачивания на процесс. Чужие/подменённые/отозванные ссылки дают 404;
недоступность или повреждение хранилища — 503 с `retryable:true`.

Срок действия ссылки определяется сохранностью архива и допуском в БД. Отзыв
политики/маршрута, смена epoch или отключение аккаунта/подключения прекращают доступ.
Смена `SESSION_SECRET` также инвалидирует старые ссылки; восстановление доступа к
уже импортированным сообщениям потребует отдельного обновления `media` в amoCRM.
Изменение публичного origin также требует сохранения старого адреса либо обновления ссылок.

## Сбои и повторы

Уникальные ключи inbox/сообщений/outbox и детерминированный ID вложения сохраняют
одну архивную запись при повторной доставке. Временный сбой Telegram не создаёт
необратимый placeholder: outbox повторяет задачу с backoff. Размер/тип/подмена MIME
оставляют placeholder и один deduplicated alert для ручной проверки.
При потере ответа Chats повтор использует тот же `msgid` и `conversation_id`;
локальный `amocrm_message_links` исключает повтор после подтверждённого импорта.
Новый URL не нужен при каждом повторе. Подключение с выключенной CRM-проекцией
по-прежнему архивирует оригинал отдельной задачей без выдачи CRM-ссылки.

Без `AMOCRM_MEDIA_BASE_URL` CRM-задача вложения завершается ошибкой и остаётся для
повтора; текстовые сообщения и отдельное архивирование не требуют этой настройки.
Изменение не чинит автоматически ссылки, уже отправленные старой версией кода.
