# Проверка API amoCRM и MAX по первичным источникам

Дата проверки: 21.10.2026. Только публичная официальная документация; это desk verification, не sandbox/live приёмка. Секреты, настройки аккаунтов, DNS и текущие подключения не исследовались. Регистрации, обращения в поддержку и принятие соглашений не выполнялись. Статусы ниже относятся к проверяемому утверждению, а не готовности реализации.

## amoCRM: регистрация и идентификаторы — подтверждено

Канал Chats предварительно регистрируется через поддержку, изначально приватен и доступен ограниченному списку аккаунтов. Нужны публичный webhook URL с подстановкой scope_id и параметры интеграции. Это отдельный процесс от OAuth-приложения. account ID в CRM и строковый amojo_id различаются; второй получается через GET /api/v4/account?with=amojo_id. Канальный секрет используется только backend; OAuth Access Token для Chats-запросов не требуется. [Начало работы](https://www.amocrm.ru/developers/content/chats/chat-start).

Подключение зарегистрированного канала: POST /v2/origin/custom/{channel.id}/connect с account_id сервиса чатов, явным hook_api_version=v2; ответ содержит scope_id. После повторной установки требуется переподключение. Это не API самостоятельной регистрации нового канала. [Методы Chats API](https://www.amocrm.ru/developers/content/chats/chat-api-reference).

## Исходящие запросы к Chats API — подтверждено

Нормализованная запись алгоритма:

```text
checksum = lowercase_hex(MD5(raw_body_bytes))
canonical = METHOD_UPPER + LF + checksum + LF + Content-Type + LF + Date + LF + URL_PATH_WITHOUT_QUERY
X-Signature = lowercase_hex(HMAC-SHA1(channel_secret, canonical))
```

Content-MD5 — hex, не base64. Для GET берётся пустое тело; Date имеет RFC 2822 формат и окно действительности подписи 15 минут. Пробелы и завершающий newline входят в байты MD5; JSON нельзя пересериализовать после подписания. Query не включается в подписываемый path. [Правила подписи](https://www.amocrm.ru/developers/content/chats/chat-start), [пример метода](https://www.amocrm.ru/developers/content/chats/chat-api-reference).

## Webhook amoCRM → интеграция — подтверждено с нюансом raw bytes

Этот X-Signature вычисляется HMAC-SHA1 канальным секретом **только от тела**; исходящая canonical-строка с Date/path здесь неприменима. Документация прямо указывает однократную отправку без повторов при ошибке получателя и рекомендует фоновую бизнес-обработку. v1 устарел; v2 допускает отсутствующие необязательные поля и несколько хуков для медиагруппы. [Форматы вебхуков](https://www.amocrm.ru/developers/content/chats/chat-webhooks).

Неоднозначность: PHP-пример применяет trim к входу, текст описывает подпись тела. Сохранение raw body без JSON-перепаковки необходимо для нашей реализации, но поведение внешних пробелов/перевода строки следует подтвердить настоящим подписанным fixture до production, а не объявлять проверенным. Date/path не добавлять к webhook-подписи по аналогии с запросом в API.

Наш вывод для тестов: signature → durable inbox commit → быстрый ответ, затем обработка; не ждать ретрая amoCRM. При валидной подписи проверять также соответствие подписанного account_id выбранному scope/account, а не доверять только URL. Точное время deadline в этой странице числом не задано.

## Доставка в amoCRM — подтверждено

Метод: POST /v2/origin/custom/{scope_id}/{msgid}/delivery_status. status_code: 1 означает доставлено, 2 — прочитано, -1 — ошибку; отправлено показано без отдельного числового enum. Для ошибки требуются error_code и безопасный текст error, видимый пользователю. Коды 901–905 различают причины. Следовательно, маппинг 1→sent или 2→delivered неверен. [Статусы Chats API](https://www.amocrm.ru/developers/content/chats/chat-api-reference).

Проверки нашей реализации: не выпускать delivered/read без факта адаптера; HTTP 200 не является доказательством прочтения клиентом; неизвестный исход не выдавать за -1. Scope/msgid и повторное обновление сверить на sandbox.

## OAuth CRM — подтверждено; setup требует отдельного решения

Для REST CRM используется Bearer Access Token. Обмен/обновление выполняются через POST /oauth2/access_token; redirect_uri должен совпадать. Refresh token одноразовый, заменяется новой парой и действует до трёх месяцев без обновления; сохранять новую пару надёжно. Пример expires_in=86400 не заменяет чтение expires_in ответа. Долгосрочные токены для небольших внешних/приватных интеграций существуют отдельно, без refresh_token. [OAuth по шагам](https://www.amocrm.ru/developers/content/oauth/step-by-step).

Та же страница сейчас описывает для приватной интеграции в нетехническом аккаунте необратимое заявление об отказе от части технической поддержки. Это реальное условие onboarding, не разрешение его принять; до действий подтвердить тип тестового аккаунта и вариант установки.

Webhook отключения OAuth — иной протокол: HMAC-SHA256 по client_uuid|account_id и секрету OAuth-клиента. Не смешивать его с Chats HMAC-SHA1. Наши тесты: атомарная ротация/конкурентное обновление, отозванный доступ и раздельные секреты.

## Sources API и виджет — подтверждено, нельзя упростить до любого OAuth

Источниками управляет их интеграция, идентифицируемая Access Token; external_id уникален, активных источников не более 100. Для Sources API нужен загруженный архив виджета с manifest locations=[lead_sources]. Тип внешней интеграции исключён. Для работающего с чатами канала должны быть заданы код виджета и ID интеграции. [Источники](https://www.amocrm.ru/developers/content/crm_platform/sources-api).

Требование архива именно для Sources нельзя безусловно переносить на все Chats-only сценарии: регистрационная инструкция позволяет не указывать отсутствующий код виджета. Наличие REST токена само по себе не доказывает готовность Sources. Наши проверки: onboarding gate для archive/widget/channel binding; source external_id относится к выбранной интеграции; отсутствие readiness не обходить фиктивным source.

## MAX Bot API — подтверждён отдельный официальный путь

Документированный HTTP API обслуживает ботов; токен выдаётся при создании бота. Текущий адрес — platform-api2.max.ru, авторизация заголовком Authorization; query-токен больше не поддерживается. Старый GET /chats с июня 2026 не поддерживается. [Обзор API](https://dev.max.ru/docs-api).

Профиль организации/ИП/самозанятого, его проверка и модерация бота входят в процедуру платформы; это не эквивалент подключения обычного телефонного аккаунта. [Платформа MAX](https://dev.max.ru/docs).

POST /messages поддерживает диалог/группу/канал; для адресации используются user_id или chat_id. Текст ограничен 4000 символами, на один адресат-диалог/группу/канал указано не более двух сообщений в секунду. Успешный ответ содержит созданное Message, но это не универсальное read receipt. [Отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages).

## MAX webhooks — отличаются от amoCRM

POST /subscriptions требует HTTPS endpoint на 443, нормальную TLS-цепочку и совпадающее имя сертификата. Нужен HTTP 200 за 30 секунд. При сбое указаны до десяти повторов с растущими интервалами; после восьми часов без успеха подписка снимается. Опциональный secret рекомендуется и проверяется по X-Max-Bot-Api-Secret; это не Chats HMAC-SHA1. [Подписки](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Наши проверки: body сохраняется до ACK, дубли обрабатываются идемпотентно; неверный secret отвергается; снятая подписка видна в health; единоличное владение ingestion проверяется отдельно. Не переносить утверждение amoCRM о единственной доставке на MAX.

## MAX Open Client API и обычный аккаунт — важное уточнение

Утверждение об отсутствии вообще любого официального клиентского API неверно: существует отдельная программа Open Client API для альтернативных клиентских приложений. [Официальная точка входа](https://dev.max.ru/docs/open-api), [описание программы](https://go.max.ru/openclient).

Публичные условия требуют одобрения программы, сертификата и App-ID; полный доступ к методам определяется отдельно. Описана архитектура прямого взаимодействия устройства пользователя с MAX, без backend/proxy/gateway разработчика и без передачи полученных данных на стороннюю инфраструктуру. Open Client отделён от платформы ботов. [Условия и архитектура Open Client](https://legal.max.ru/openclient-docs).

**Вывод для нашего проекта:** наличие Open Client не подтверждает допустимость серверного CRM-шлюза для обычного аккаунта. Такой headless/personal server сценарий остаётся UNKNOWN и требует отдельного подтверждения MAX. Это не доказательство технической невозможности, но текущая публично описанная программа не обосновывает выбранную серверную архитектуру. Нельзя автоматически подменить требуемый personal режим ботом.

Официальная ссылка технической документации ведёт на ZIP; web-reader вернул unsupported application/zip. Архив не скачивался и его код не запускался; методы обычного аккаунта по нему не верифицированы. [Публичный ZIP](https://st.max.ru/docs/tekhnicheskaya-dokumentatsiya.zip).

## Групповые чаты: собственная политика, не функция amoCRM

Речь о внутренних групповых чатах мессенджеров, а не группах сотрудников CRM. Запрет по умолчанию и allowlist стабильных external chat IDs до любой CRM-проекции — требование нашего контура; в просмотренных Chats API документах оно не подтверждено как готовый серверный фильтр amoCRM.

В MAX объект Chat различает chat (группа), channel и dialog, содержит chat_id; title может меняться/быть null. [Объект Chat](https://dev.max.ru/docs-api/objects/Chat). Наши тесты: незнакомый тип и неизвестная группа не создают CRM-проекцию; переименование не меняет доступ; явный allowlist применён до создания контакта/сделки/сообщения. Telegram-режим и классификацию проверить в отдельной задаче, не переносить сюда bot-схему без проверки.

Ни чтение документации, ни unit-тесты не подтверждают эти пункты автоматически.
