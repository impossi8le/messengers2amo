## 1. Решения, которые нужны от вас

### 1.1 amoCRM: нажать «Разрешить» — блокирует #10, #11, #12

Интеграция создана, ключи на сервере. Осталось одно действие в браузере: открыть ссылку авторизации и подтвердить доступ.

**Что произойдёт:** токены обменяются и сохранятся в зашифрованном виде, после этого заработает синхронизация контактов, сделок и чатов.

**Почему без вас нельзя:** OAuth требует подтверждения владельца аккаунта. Пароль не нужен, только нажатие кнопки.

**Ссылка** — в отдельном файле, что я присылал ранее. Если истекла, скажите — выпущу новую.

### 1.2 Регистрация канала Chats API — блокирует сквозной сценарий с нативным чатом

OAuth-доступ **не позволяет** подключить собственный чат в amoCRM. Нужна заявка в поддержку amoCRM на регистрацию канала.

**Данные для заявки** (уже подготовлены, в `access-response.ru.md`):

| Параметр | Значение |
|---|---|
| Название канала | Messengers2amo |
| Символьный код | messengers2amo |
| URL вебхука | `https://messengers.example.com/webhooks/amocrm/{scope_id}` |
| Функции | текст в обе стороны, вложения, статусы доставки и прочтения, история |

**Что нужно от вас:** подать заявку (это делается от аккаунта компании) и передать полученные `channel_id`, секрет канала и символьный код.

**Без этого:** сообщение из мессенджера не появится в нативном чате amoCRM. Всё остальное — приём, обработка, ответ — работать будет, но связка с CRM останется непроверенной на живых данных.

### 1.3 Копии пока на основном VPS; внешний backup остаётся критерием #31

Сейчас бэкапы пишутся на тот же сервер. Если сервер потеряется, потеряются и копии.

**Решение 26.10.2026:** пока основной VPS, путь `/opt/messengers2amo/backups`.
Текущая политика — `ops/deploy/messengers2amo/BACKUP-POLICY.ru.md`.
Для выполнения внешнего критерия позже потребуется отдельный ресурс хранения; это не
согласованный сейчас бакет и не поручение менять существующую инфраструктуру.

Численные RPO/RTO нужно отдельно согласовать и подтвердить восстановлением.

### 1.4 Медиа-бакет и ключ — блокирует живую проверку #8

Нужен закрытый бакет для вложений: `endpoint`, `bucket`, `access_key`, `secret_key`. Ключ должен быть ограничен этим бакетом — префикс папки границей доступа не является.

### 1.5 Выпуск сертификата — уже сделан, но нужно ваше подтверждение на будущее

Сертификат Let's Encrypt выпущен и работает. Автопродление настроено. Подтвердите, что это приемлемо, и что домен остаётся за нами.

## 2. Решения по каналам: с чего начинаем

### 2.1 Telegram — тестовый бот, решение принято

Бот `@LenTestWazzup_bot` работает: webhook установлен, события принимаются, подпись проверяется.

**Решено (22.10.2026):** бот остаётся **тестовым**. Он нужен, чтобы проверить связку целиком — Telegram → наш продукт → amoCRM и обратно — до того, как к системе подключат реальные каналы и живых клиентов.

**Что это значит:**

- на нём проверяется сквозной сценарий: входящее сообщение, ожидание ответа, ответ оператора, проекция в нативный чат amoCRM;
- он не обслуживает клиентов и не заменяет рабочий канал;
- реальные Telegram-подключения переносятся отдельно (#19), со своим ботом и проверенным откатом.

Доступ к тестовому боту ранее был проверен. Уточнение 26.10: запуск живых проверок пока
отложен владельцем; сначала завершить разработку, затем предупредить сотрудников и выбрать
окно тестов. Перевыпуск токена не требуется для локальных проверок.

### 2.2 WhatsApp — блокирует #14 и #20

**Нужно ваше решение:** какой тип подключения используется сейчас?

| Вариант | Что это значит | Возможен ли серверный шлюз |
|---|---|---|
| WABA (официальный API) | номер подключён к бизнес-аккаунту Meta | да |
| QR-привязанное устройство | телефон привязан как WhatsApp Web | **нет**, официального серверного API не существует |
| Coexistence | гибридный режим | требует проверки |

**Почему это критично:** если у вас QR-режим, полноценная замена Wazzup для WhatsApp невозможна официальным путём. Это не техническое ограничение нашего сервиса — это ограничение WhatsApp. Решение нужно принять до разработки адаптера, иначе мы построим неработающее.

**Не отвязывайте устройство ради теста** — это сломает текущую переписку.

### 2.3 MAX — блокирует #15 и #20

**Нужно ваше решение:** какой у вас аккаунт?

Публичная документация MAX не подтверждает, что обычный рабочий аккаунт можно подключить к серверному шлюзу. Open Client API существует, но его ограничения (device-only) не подтверждают сценарий «сервер получает и отправляет от имени обычного аккаунта».

**Что нужно:** тип аккаунта (обычный / бот / партнёрский) и доступ к тестовому. Если это обычный аккаунт — письменное подтверждение от MAX, что серверная интеграция допустима. Без этого адаптер будет работать только с ботом.

### 2.4 VK — блокирует #16 и #20

**Что нужно:** отдельное тестовое сообщество (не рабочее) и ключ доступа с правами на сообщения, плюс строка подтверждения Callback API.

## 3. Инвентаризация Wazzup — блокирует #17

Форма готова: `docs/migration/inventory-form.ru.md`. Заполняется за 15–20 минут.

**Что нужно:** заполнить по каждому каналу — как подключено, чей аккаунт, куда приходят сообщения, кто отвечает, используются ли группы, файлы, шаблоны, исходящие первыми.

**Альтернатива:** дать доступ на чтение к кабинету Wazzup, и я сниму данные сам.

**Зачем:** без этого нельзя обещать, что перенос не потеряет обращения. И нельзя гарантировать отсутствие двух отправителей на одном номере.

## 4. Порядок, который предлагаю

1. **Сейчас:** заканчиваем разработку и локальные проверки без реальных сообщений.
2. **Параллельно:** отвечаете по типам подключений WhatsApp и MAX (п. 2.2, 2.3) — от этого зависит, реализуемы ли эти каналы вообще.
3. **До живой приёмки:** проверить наличие OAuth и зарегистрированного Chats-источника,
   приватного медиа-хранилища. Внешний backup остаётся отдельной открытой задачей.
4. **Потом:** заполняете форму инвентаризации (п. 3) или даёте доступ к Wazzup.
5. **После предупреждения сотрудников владельцем и согласования окна:** проверяем связку
   на тестовом боте — Telegram → продукт → amoCRM и обратно.
6. **Только потом:** параллельный пилот и переключение реальных каналов (#18–#20).

## 6. Риски, которые стоит знать

| Риск | Что это значит |
|---|---|
| WhatsApp в QR-режиме | замена официальным путём невозможна, нужен другой подход |
| MAX обычный аккаунт | серверный шлюз может быть недопустим по правилам MAX |
| Регистрация канала amoCRM | может занять время, зависит от поддержки amoCRM |
| Нет внешнего бэкапа | потеря сервера = потеря данных |
| Доступ «Все» в amoCRM | токен может менять любые сущности; после приёмки ключи стоит перевыпустить |
