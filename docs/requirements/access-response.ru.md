# Ответ на запрос доступов: что нужно от разработчика

Документ для передачи ответственному за доступы. Дата: 21.10.2026.
Согласованный объём первого запуска: **отдельная интеграция amoCRM + тестовый Telegram-бот + изолированное S3**. Рабочие Wazzup, MAX, WhatsApp, VK и архив не трогаем.

---

## 1. OAuth Redirect URI (точное значение)

Зарегистрировать в новой интеграции **байт-в-байт**:

```
https://messengers.example.com/api/v2/integrations/amocrm/oauth/callback
```

Требования:

- Только `https`, без завершающего слэша, без query-параметров.
- Домен должен быть уже доступен по HTTPS к моменту авторизации — иначе amoCRM не сможет доставить код. На 22.10.2026 сертификат выпущен и домен отвечает по HTTPS, это условие выполнено.
- Приложение принимает только этот зарегистрированный адрес и только ожидаемый домен аккаунта; произвольный redirect отклоняется.

## 2. URL вебхука amoCRM Chats API

```
https://messengers.example.com/webhooks/amocrm/{scope_id}
```

`{scope_id}` подставляется после подключения канала — это идентификатор привязки аккаунта, а не секрет. Проверка подлинности идёт по raw-подписи тела запроса (HMAC-SHA1), поэтому вебхук не защищается Basic Auth и не должен изменяться прокси: тело принимается ровно в тех байтах, в которых пришло.

Важно: amoCRM **не повторяет** доставку вебхука. Поэтому событие сначала сохраняется в БД и только потом подтверждается. Потеря при недоступности сервиса не восстанавливается со стороны amoCRM — это надо учитывать при планировании окна работ.

## 3. Email для отдельного тестового пользователя

Нужен отдельный пользователь amoCRM **без прав администратора**, без экспорта и удаления, с доступом только к тестовым данным.

Просьба прислать на этот адрес приглашение и указать, какой email использовать. Разработчик передаст его ответным сообщением в защищённом канале.

Тестовые сущности создаются заново с названием `ТЕСТ messengers2amo — НЕ КЛИЕНТ`. Старые тестовые карточки не переиспользуются.

**Ограничение, которое берём на себя:** API-токен не ограничивается одной сделкой. В коде будет явный allowlist разрешённых тестовых ID и запрет массовых изменений; любые операции вне allowlist отклоняются. Это компенсирующая мера, а не замена отдельному тестовому аккаунту.

## 4. Публичный SSH-ключ разработчика

Вместо общего доступа — отдельный ключ и отдельный пользователь:

```
ssh-ed25519 <YOUR_PUBLIC_KEY> operator@example.com
```

Просьба:

1. Создать отдельного пользователя (не `root`) и добавить этот ключ в его `authorized_keys`.
2. Сервис запускать отдельным системным пользователем, без прав на чужие каталоги.
3. Административные операции — через `sudo` с ограниченным набором команд, если это возможно.
4. Общий ключ, выданный ранее, после проверки нового доступа можно отозвать — по вашему решению, не автоматически.

Приватный ключ остаётся только на рабочей машине разработчика, на сервер и в Git не попадает.

## 5. Операции с S3, которые нужны

Для медиа-бакета достаточно:

| Операция | Зачем |
|---|---|
| `PutObject` | Загрузка вложения |
| `GetObject` | Выдача по short-lived ссылке |
| `HeadObject` | Проверка наличия и размера |
| `DeleteObject` | Удаление по политике хранения (опционально) |
| Presigned URL (GET/PUT) | Доступ без раскрытия ключей клиенту |

Не нужны: `ListAllMyBuckets`, доступ к другим бакетам, управление политиками, версионированием и жизненным циклом.

**Изоляция:** ключ должен быть ограничен конкретным бакетом. Если провайдер так не умеет — нужен отдельный бакет в отдельном аккаунте/проекте; префикс папки границей доступа не является.

Разделение, как вы предложили:

- медиа — отдельный закрытый бакет и ключ только к нему;
- резервные копии — отдельный бакет, независимые права;
- действующий архив — полный доступ не выдаётся, сначала только описание интерфейса и тестовый доступ.

**Как передать секреты:** не в переписке и не в Git. Предпочтительно — запись в защищённом хранилище (менеджер паролей компании) с указанием, что значения доступны; либо ввод напрямую в `.env` на сервере человеком, у которого есть доступ. Приложение читает секреты только из окружения, в логи и API они не попадают.

## 6. Заявка на регистрацию канала чатов

Данные для заявки в поддержку amoCRM:

| Параметр | Значение |
|---|---|
| Название канала | `Messengers2amo` |
| Символьный код канала | `messengers2amo` |
| URL вебхука | `https://messengers.example.com/webhooks/amocrm/{scope_id}` |
| Иконка | нужен файл; разработчик подготовит PNG 128×128 и передаст отдельно |
| Поддерживаемые функции | текст в обе стороны, вложения в обе стороны, статусы доставки и прочтения, история сообщений |

После регистрации требуются `channel_id`, секрет канала и символьный код. `scope_id` появляется после подключения аккаунта; `amojo_id` получается через REST API (`GET /api/v4/account?with=amojo_id`) уже после OAuth-авторизации.

**Это признаётся потенциальным блокером:** обычный OAuth-доступ не позволяет подключить собственный чат. Без регистрации канала сквозной сценарий «сообщение в мессенджере → нативный чат amoCRM → ответ» проверен не будет. Реализация при этом не блокируется: она тестируется на синтетических данных, а live-проверка ждёт регистрации.

## 7. Telegram

Тестовый бот создаётся вами через `@BotFather` под аккаунтом компании — владение остаётся у вас. Передаётся **только токен этого тестового бота**, без доступа к аккаунту Telegram.

`secret_token` вебхука разработчик генерирует сам и хранит на сервере — от вас не требуется.

Рабочие боты и подключения Wazzup не изменяются.

## 8. Сертификат и публикация

Порядок, который предлагаю:

1. Развернуть сервис на `127.0.0.1:18767`, наружу не публиковать.
2. Добавить отдельный `server`-блок nginx только для `messengers.example.com`.
3. Выпустить сертификат Let's Encrypt только на это имя (certbot, nginx-плагин).
4. Проверить `nginx -t` до каждого reload; чужие сайты не останавливать и не менять.

Ранее запрос на домен попадал в vhost `other-service.example.com`, из-за чего браузер показывал ошибку имени в сертификате. На 22.10.2026 это устранено отдельным vhost'ом и сертификатом на нужное имя, без отключения проверки TLS.

Доступ к панели Beget и ко всем DNS-записям не требуется: A-запись уже указывает на нужный сервер.

## Что нужно от вас, чтобы начать

1. Создать интеграцию amoCRM с Redirect URI из п.1 и передать `client_id` / `client_secret` в защищённое хранилище.
2. Пригласить тестового пользователя (п.3) — нужен email.
3. Создать тестового Telegram-бота и передать только его токен.
4. Создать медиа-бакет и ключ, ограниченный этим бакетом (п.5).
5. Добавить публичный SSH-ключ из п.4 отдельному пользователю.
6. Подать заявку на регистрацию канала чатов (п.6) — данные выше.
7. Подтвердить выпуск сертификата на домен (п.8).

После п.1–2 можно проверять OAuth и REST-часть amoCRM. После п.6 — сквозной сценарий с нативным чатом.
