# Уточнения бизнес-требований к интеграции amoCRM

Дата: 21.10.2026. Основание — предоставленная пользователем спецификация «Собственный сервис мессенджеров для amoCRM», разделы 1–18. Это анализ новых требований, не подтверждение внешних API, подключений или готовности сервиса. Содержимое исходного документа, адрес рабочего аккаунта и домены инфраструктуры здесь намеренно не воспроизводятся.

Принятые схемы v1/v2 и их тесты сохраняются. Новые требования требуют отдельного контрактного расширения и уточнения #3, #8, #10–17; это не основание молча менять опубликованные strict DTO. Текущие статусы задач проверять на доске: локальный backlog-файл может отставать.

## 2. Уточнения контрактов и DDL до замораживания #3

Это предлагаемые внутренние сущности, а не описание неизвестной БД существующего архива. Прямого подключения к ней не требуется и не выполнялось.

| Область | Добавить/проверить в модели | Инвариант |
|---|---|---|
| Business units | business_units; connection routing config с business_unit_id, crm_account, funnel/pipeline, default responsible, technical source, config version | Company, workshop, department и CRM account имеют разные идентичности; невозможны cross-company/cross-workshop связи без явного разрешения |
| Полномочия | Явные read/send permissions на connection, подтвержденное соответствие amoCRM user и внутреннего сотрудника | При отзыве проверять право до dispatch и до CRM-проекции. Локальный API не скрывает уже опубликованное содержимое от прав самой CRM |
| Источники | Технический source/origin binding отдельно от marketing-origin/custom field; история версии маршрута | Новое обращение через мессенджер не меняет исходный рекламный атрибут; внешние ID источника проверены в нужном CRM account |
| Chat policy | chat kind private/group/channel/unknown; immutable provider chat ID в connection/epoch scope; policy decision/version/reason и allow/deny registry | Explicit deny имеет приоритет. Group/unknown запрещены для CRM по умолчанию. Имя не определяет разрешение |
| CRM outbox | CRM projection intent хранит контекст маршрута/политики; проверка текущего запрета перед исполнением | Ни contact, lead, chat/message, ни событие по запрещенной группе не создаются до фильтра. Конфигурационное создание source подключения — отдельная операция, не эффект группового события |
| Архив | Приватный media object/provenance отдельно от archive index intent, состояния pending/unknown/acknowledged/error, external archive reference только после подтверждения | Объект записан != индекс подтвержден != целостность проверена. При неизвестном исходе индексирования — сверка/ограниченный retry по согласованному контракту, не слепой дубль |
| Provenance | connection/chat/message original IDs, версия, original name, MIME, size, sha256, object reference; nullable CRM chat/message/contact IDs до подтверждения | Файл не теряет происхождение при переименовании контакта/группы и временном отсутствии CRM-сущности |
| Сделки и история связей | conversation_leads и связи archive entry↔lead/contact с версией/историей, не только один scalar leadId | Несколько активных заказов требуют согласованного выбора. Merge/delete изменяет текущую связь, сохраняя доказуемое происхождение файла |
| Удаления | Soft tombstones/broken bindings и отделённая retention policy | CRM delete не каскадирует в provider delete, S3 DeleteObject или archive deletion. Messenger deletion также не является командой уничтожения архива |

Фильтр применяется после аутентификации и устойчивого приёма/дедупликации, но до планирования CRM эффектов. При изменении policy уже поставленные, но не начавшиеся эффекты перепроверяются. Отозвать начавшийся внешний вызов нельзя обещать: сохранить факт допуска и сверить результат. Для исключённой рабочей группы архивирование отдельно от CRM возможно только как явный archive-only режим с собственными правами; оно не включается автоматически вместе с deny. Политику хранения raw inbox для исключённых групп определить отдельно; отсутствие CRM-проекции не означает разрешение бессрочно хранить весь контент.

Реестр архива, его версия, владелец и интерфейс пока UNKNOWN. До получения контракта допустимы только абстрактный adapter port, синтетический fake для тестирования нашей границы и состояния намерений. Такие тесты не подтверждают совместимость с существующим плагином. Новые миграции нашей БД не должны создавать или изменять таблицы внешнего архива.

## 3. Native amoCRM workflow

Менеджер читает и отвечает в штатном чате amoCRM. Настройки, ACL, группы, подключения и журнал ошибок находятся в административном контуре собственной интеграции. Тестовый отдельный Telegram UI остается диагностическим стендом.

Безопасная обработка native outbound: проверенный raw webhook → durable inbox/ack → определение scope/connection/immutable recipient и версии workshop route → проверка actor и read/send ACL → dispatch gate → адаптер → реальный результат → доставка/ошибка в CRM. При неизвестном actor нельзя объявить персональный ACL выполненным: PoC должен подтвердить нужные данные или потребовать явного продуктового решения. Автоматически заменять native chat отдельным рабочим inbox либо режимом общего отдела нельзя.

Compose snapshot в native CRM пока не доказан. Сохраняется coverage_unconfirmed без ложного закрытия внимания; минимальный виджет/ручное подтверждение возможны как дополнение основного чата. Правила разрешения и учёта ответа не следует смешивать: отсутствие snapshot не доказывает отсутствия права отправки, а наличие CRM доступа само по себе не доказывает конкретный channel ACL.

## 4. Что изменяется в задачах

- **#3:** учесть business units, версии routing/source, group policy/gates, archive index/provenance и историю M:N CRM-связей до приёмки DDL. Проверить миграции/изоляцию/отсутствие опасного cascade на реальном PostgreSQL.
- **#8:** поднять раннее исследование существующего архива до P0. Разделить контрактный spike (можно сейчас) и реализацию файлов после #4/#6. Приёмка включает plugin index, права, SSRF/redirect guard, оригиналы и повторное открытие в native CRM.
- **#10:** разделить контрактное исследование/подготовку от установки. Не ждать всего RBAC для чтения актуальной спецификации/макета регистрации, но реальную регистрацию/секреты/поддержку выполнять по отдельному доступу и разрешению. Проверить claims из раздела 5 ниже.
- **#11:** технические sources != marketing origin; один механизм создания неразобранного/сделки; group filter раньше projection; архивные связи переживают merge/delete; внешние IDs без потери точности.
- **#12/#7:** уточнить amoCRM-first UX вместо обязательного отдельного рабочего inbox; per-workshop/connection ACL и ошибки в native workflow.
- **#13:** техническая осуществимость ordinary MAX и официального WA до обещаний полного решения. Документацию/PoC-план начинать независимо от готовности Telegram #4; реальные тесты требуют активов и разрешения. Для MAX отдельно рассматривать Bot API, OpenClient и серверный personal/partner доступ; их пригодность не взаимозаменяема.
- **#15:** критерий — нужный обычный рабочий MAX-аккаунт, если он фактически используется; не закрывать задачу результатом max_bot.
- **#17:** учесть минимум две логические мастерские, все каналы/режимы, пользователей, funnel/owner/source mapping, архив, нужную историю и существующие группы. Не менять текущий маршрут при обследовании.
- **#18–21:** пилот включает native chat, файл+индекс архива, отрицательные group/ACL/delete проверки; Wazzup отключается только после фактической приёмки.
- **Новая отдельная задача SPEC-EXT:** версионированное расширение принятых контрактов business routing/chat policy/archive port и соответствующие fixtures. Не переписывать принятую #2 задним числом и не добавлять поля в strict v2 без явного решения о совместимости.

## 5. Внешние API: что подтверждено и что остаётся проверить

Публичные официальные документы amoCRM и MAX проверены 21.10.2026: [результат с первичными ссылками](api-verification-2026-10-21.ru.md). Это проверка описанного протокола, а не работоспособности нашей интеграции в конкретном аккаунте. Регистрация, авторизация, подписанные реальные события и сквозная приёмка не выполнялись. Для Telegram и WhatsApp в этом исследовании проверка API не проводилась.

Для MAX утверждение «есть только Bot API» неверно: опубликована отдельная программа [Open Client](https://dev.max.ru/docs/open-api) с [условиями и архитектурой](https://legal.max.ru/openclient-docs). Наличие программы не означает, что разработчику уже предоставлен допуск или что серверный CRM-шлюз одобрен. Это не юридическая оценка и не доказательство технической невозможности обычного аккаунтного доступа.

Инструкция содержит действия «создать интеграцию», «обратиться в поддержку», «настроить домен». Сам документ не служит разрешением посылать сообщения, регистрировать OAuth/Chats, принимать необратимые условия, менять DNS, размещать сервис или перенастраивать архив. В рамках этой проверки такие действия не выполнялись.

## 6. Новые TDD-сценарии

Сначала failing tests для внутренней модели/границ, затем реализация и интеграционные проверки. Ниже план тестов, а не уже выполненные испытания.

| Case | Проверка | Уровень и задачи |

## 7. Неизвестное и необходимые входные данные

- Реестр всех фактических подключений, тип MAX/Telegram/WA, владельцы и требуемая история; подтверждение двух мастерских и остальных business units.

- Согласованный read-only контракт/документация или исходники существующего плагина «Архив файлов», владелец, схема IDs/индекса/ACL/операций, idempotency/lookup и recovery возможности. Его API и физическая схема пока UNKNOWN.
- Доступы выдавать локально/через защищенное хранилище с отдельной ролью разработчика; реальные токены/сессии не присылать в issue или этот документ.
- Согласованные тестовые активы/контакты и разрешение на account-specific PoC; подтвержденный способ обратного перехода.
- Решения по native actor/ACL и snapshot/manual coverage, архив-only группам, retention и измерению регулярных расходов.

Без этих данных продолжаются модели, fake-boundary тесты и документация, но не объявляется совместимость с существующим архивом, доступ к ordinary MAX или готовность отказа от Wazzup.
