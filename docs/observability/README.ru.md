# Безопасное структурированное логирование

Задача #25. Реализован самостоятельный Node.js 24 модуль JSON Lines в packages/observability/src/logger.mjs. Это исполняемый код с тестами захваченного вывода, а не только JSON Schema. Он ещё не встроен в локальный Telegram-стенд или будущий NestJS API. Интеграция в обработчики и эксплуатационные метрики потребует отдельного изменения.

## Запуск проверок

Из корня checkout:

```powershell
npm --prefix packages/observability ci --ignore-scripts
npm --prefix packages/observability test
```

Runtime-зависимостей нет. Dev-зависимости Ajv 8.20.0 и ajv-formats 3.0.1 закреплены в lockfile. Один из тестов читает соседнюю packages/contracts/schema/v1.json и валидирует реальные выходные записи через Ajv2020 strict. Пакет тестируется внутри checkout проекта, а не отдельно скопированной папкой.

## Контекст и отправка события

```javascript
import { createLogger, DiagnosticError } from './packages/observability/src/logger.mjs';
const logger = createLogger();
const request = logger.createContext();
const event = logger.withEvent(request);
const operation = logger.withOperation(event);
logger.emit(operation, {
  event: 'send.result_recorded',
  outcome: 'unknown',
  errorCode: 'UPSTREAM_TIMEOUT',
  durationMs: 1250,
});
```

Контексты — непрозрачные замороженные handles, связанные с приватным WeakMap конкретного экземпляра логгера. Создание request, operation и event генерирует собственные внутренние UUID с префиксами req_, op_, evt_. Недоступные operation/event имеют null. Добавление operation сохраняет triggering event, а добавление event сохраняет operation. Подделанный объект, контекст другого логгера и внешние идентификаторы в аргументах не становятся источником correlation. Метод logger.correlation(handle) возвращает замороженную копию только сгенерированных ID: доверенный сервер может сохранить её для диагностики в своей записи. Эти ID не автоматически являются domain Message/SendOperation IDs. Импорт контекста из произвольного объекта или восстановление handles между процессами пока не поддерживаются.

Входящие HTTP-заголовки, Telegram chat/message IDs, имя пользователя и CRM phone нельзя подставлять вместо внутренних ID. Сопоставление внутреннего event/operation с хранимой доменной сущностью делает доверенный серверный код и аудит; логгер сам не читает клиента или БД. wallClock, monotonicClock и idFactory внедряются только доверенным кодом/тестами, не из HTTP-параметров. Некорректный UUID фабрики отвергается постоянной безопасной ошибкой. Формат UUID сам по себе не доказывает, что доверенный caller не закодировал туда чувствительные данные.

## Разрешённые поля

Запись строится заново из whitelist: schemaVersion=1, timestamp ISO, level, event, outcome, errorCode, correlation и необязательная конечная неотрицательная durationMs. Остальные поля не копируются, не обходятся и не сериализуются. Это исключение данных, а не попытка regex-редактирования произвольного объекта.

- event: request.completed, inbox.persisted, send.result_recorded, assignment.changed, projection.failed.
- outcome: accepted, succeeded, failed, unknown, blocked.
- errorCode: null либо UPSTREAM_TIMEOUT, VALIDATION_FAILED, FORBIDDEN, VERSION_CONFLICT, STALE_EPOCH, UPSTREAM_UNAVAILABLE, INTERNAL_ERROR.
- failed получает level=error; unknown/blocked — warn; остальные — info.

Вызов emit с неизвестным event/outcome/code или недопустимой durationMs отвергается без включения значения в сообщение ошибки. Параметры события должен формировать внутренний код обычным объектом; не передавайте объект провайдера как options. Пакет не является sandbox для произвольных getter/proxy в разрешённых полях или внедрённых зависимостях.

## Ошибки и unknown

```javascript
logger.failure(operation, {
  event: 'send.result_recorded',
  outcome: 'unknown',
  error: new DiagnosticError('UPSTREAM_TIMEOUT'),
});
```

DiagnosticError содержит только разрешённую категорию. Для распознавания используется приватное брендирование, а не instanceof или произвольное поле error.code: подделка прототипа не придаёт внешней ошибке доверенную категорию. Неизвестная ошибка превращается в INTERNAL_ERROR без чтения message, stack, code, cause, raw response или URL. Исходная ошибка не попадает в JSON. failure разрешает только failed/unknown/blocked; accepted и succeeded отвергаются до вывода, чтобы ошибка не объявлялась успехом. Для неизвестного исхода отправки caller явно выбирает outcome=unknown; логгер не меняет его на успех и не повторяет сетевой запрос.

Текст переписки, токены, auth-заголовки, cookies, SQL-параметры и provider payload никогда не следует передавать в логи. Тесты дополнительно подсовывают синтетические canary-значения, их URL/base64-представления, вложенные ошибки, getter и toJSON в неизвестных полях; записанный вывод не содержит этих значений, а вложенные объекты не исследуются.

## Лог после успешного завершения и отката

```javascript
const result = await logger.run(request, { event: 'inbox.persisted' }, async () => {
  // Этот promise обязан разрешиться только ПОСЛЕ успешного commit.
  return await saveInboxInTransaction();
});
```

run проверяет контекст и имя события до запуска action. Он ждёт promise action: после разрешения записывает succeeded с монотонной длительностью, если она доступна; после отклонения записывает безопасный failed и пробрасывает ту же исходную ошибку. Отказ monotonicClock не блокирует action. Нефинитная, недоступная или обратная разность часов не превращается в выдуманную длительность: durationMs опускается. Сбой часов/форматирования/записи после успешного action не подменяет уже зафиксированный результат ошибкой и не провоцирует повтор со стороны caller. Исходная ошибка отката также сохраняется. Пакет не выполняет SQL, commit или rollback и не проверяет, что caller действительно дождался commit. Это контракт места вызова, который в #3–#5 проверяется реальным PostgreSQL-тестом. run разрешён только для локального успешного завершения request.completed/inbox.persisted/assignment.changed. Для send.result_recorded и projection.failed он отклоняет вызов ДО action: исход необходимо явно выбрать через emit/failure. Это предотвращает ложный succeeded при разрешённом promise с {state:unknown}. Содержимое возвращённого объекта не исследуется: доказательства sent/delivered интерпретирует адаптер, а не логгер.

Тест с отложенным promise подтверждает отсутствие ранней записи успеха; тест отклонения проверяет failed, длительность и неизменность проброшенной ошибки, без утечек nested cause. Это не интеграционный тест БД и не замена транзакционному аудиту.

## Запись и ограничения транспорта

По умолчанию используется защищённый адаптер actual process.stdout, захваченного при создании логгера. Он передаёт одну JSON-строку с newline в Node Writable и обрабатывает как синхронный отказ, так и ошибку write callback / событие error. Содержимое ошибки не читается, не хранится в состоянии и не печатается в stderr или fallback. Асинхронный отказ не становится необработанным error event и не завершает процесс.

Для каждого stdout stream в экземпляре загруженного модуля создаётся один общий error listener и одно состояние транспорта в WeakMap. Сотни созданий логгера не добавляют сотни listeners. Listener намеренно живёт вместе с process-wide stream, без per-logger dispose: его раннее удаление могло бы оставить уже начатую запись без error handler. Существующие чужие listeners не удаляются; их собственный вывод библиотека не контролирует. Отдельный тест изолированного процесса создаёт 500 логгеров и подтверждает постоянное количество listeners=1.

Метод logger.transportState() возвращает замороженный снимок {failed:boolean}, без raw error. После синхронного или асинхронного I/O-отказа состояние failed защёлкивается; последующие emit/failure этого транспорта возвращают false без повторной записи. Другой логгер на том же stdout видит то же состояние. Восстановление транспорта и повторная отправка старых записей автоматически не выполняются. Нельзя полагаться на текст исключения для контроля здоровья.

emit и failure возвращают true, если запись принята адаптером и к этому моменту отказ не известен. После асинхронного отказа первоначальное true не превращается задним числом в доставку: наблюдайте transportState().failed. Результат true не означает централизованное хранение или durable flush. false от самого stdout.write означает backpressure, а не отказ принятия в буфер; он не выдаётся за потерю записи. При отказе часов/форматирования emit возвращает false; это не обязано означать I/O-отказ транспорта.

Можно внедрить собственный синхронный write(line). Его синхронное исключение безопасно превращается в false и failed, без raw fallback. Произвольные асинхронные custom sink/Promise этим интерфейсом не поддерживаются: такой внешний адаптер сам обязан обработать отложенные ошибки и backpressure. Асинхронная защита стандартного stdout не даёт этой гарантии произвольной пользовательской функции.

run возвращает бизнес-результат, а не статус записи. Ошибка логирования не подменяет committed result и не провоцирует повтор бизнес-действия; исходная ошибка отката также сохраняется. Для эксплуатации проверяйте безопасный transportState и дополняйте адаптер отдельным счётчиком/health без raw exception. Пакет пока не реализует очередь логов, flush при shutdown, ограничение буфера, ротацию, retention, сбор метрик или централизованный доступ. Это интеграция/эксплуатация (#9). Логи не являются единственным хранилищем важного бизнес-факта.

## Доказательства разработки

До реализации был создан no-op каркас с тем же API; финальный начальный запуск дал 14 тестов / 0 pass / 14 fail. Реальный вывод сохранён локально в work/observability-red-final.log. Antigravity Medium с --mode accept-edits действительно заменил src/logger.mjs. После этого его WriteFile был отклонён для одной последующей операции, итоговый JSON оказался пустым; поэтому код и проверки оценивались по фактическим файлам, а не SUCCESS.

Независимая проверка нашла потерю eventId при withOperation(eventContext). Сначала добавлен тест и получен RED: 15 тестов / 14 pass / 1 fail (work/observability-review-red.log); затем сохранение ID исправлено. Исправление настройки тестовой подделки getter не выдаётся за продуктовый дефект. Тест реальной Ajv-валидации добавлен как дополнительная регрессия без заявления отдельного RED. Ревью родителя выявило ещё четыре требования: сохранить committed result при сбое часов/форматирования, не блокировать action отказом монотонных часов, сохранить исходную ошибку и предоставить неизменяемую проекцию внутренних ID. Сначала получен RED 20 тестов / 16 pass / 4 fail (work/observability-parent-review-red.log), затем внесены исправления. Отдельный RED 21 тест / 20 pass / 1 fail (work/observability-explicit-outcome-red.log) подтвердил необходимость запретить auto-success run для событий отправки; добавлен guard до action. Независимое ревью обнаружило необработанный асинхронный error стандартного Node Writable. Сначала добавлен реальный child-process тест: до исправления child завершался с exit 1 и canary/stack в stderr. Общий RED 24 теста / 21 pass / 3 fail сохранён в work/observability-async-stdout-red.log. Затем добавлены общий listener/failed-state stdout и запрет успешных исходов failure. GREEN подтверждает отсутствие raw canary/stderr, сохранение процесса, failed-state, false для следующих записей и один listener для 500 логгеров. Финальный запуск: 24/24 PASS. Локальные сырые выводы находятся в work/ и не публикуются вместе с кодом.
