# Доска №7: runtime и локальная приёмка 26.10.2026

Рабочая ветка: `feat/board-runtime-completion-20261026`.
Изменения подготовлены локально. Выкладка, переключение и реальные сообщения не выполнялись.

## Что изменено

- RT01/RT02: исправлено тело создания Chats API (`conversation_id`, `user`), добавлены
  реальная привязка чата к контакту и импорт текста с устойчивым `msgid`. Пустой или
  некорректный успешный ответ API считается ошибкой. Канал Chats выбирается по конкретному
  диалогу, подключению и эпохе, а не первым в аккаунте.
- RT03: Telegram-процессор ставит CRM-проекцию в одной транзакции с обработкой входящего.
  Дедупликация сохраняется. Процессор больше не забирает события `chats.*`, принадлежавшие
  другому обработчику. CRM-проекция использует фактический ID уже сохранённого сообщения.
- RT05: поиск сделок использует документированную связь `contacts/{id}?with=leads`, затем
  состояния связанных сделок; неподтверждённый фильтр по контакту удалён. Закрытая прежняя
  сделка не переоткрывается. Для нового цикла после закрытия ключ создания получает
  суффикс `:after:<previousLeadId>`; прежний intent сохраняется.
- Native-ответы Telegram: подписанный v2 webhook → отдельный обработчик inbox →
  транзакционный outbox → существующий Telegram-воркер → исходный чат. Есть подавление
  эха, проверка аккаунта/чата/подключения/эпохи и разрешения проекции. При выключенном
  `OUTBOUND_ENABLED` ответы остаются в inbox. Исходящие медиа из CRM и неоднозначные маршруты отправляются
  на разбор с алертом; подпись или текст вложения не подменяют само вложение.
- RT06: мастер Telegram Bot в три шага; проверка `getMe` до записи; токен хранится
  зашифрованно с привязкой к компании и подключению, имеет отдельный webhook-secret.
  Воркер использует токен конкретного нового подключения. В браузере секретные запросы
  обходят Redux-кэш. Новые каналы сохраняются в `setup` с выключенными приёмом,
  отправкой и CRM-проекцией. Добавлено имя канала, справочник воронок на странице CRM,
  выбор получателя алертов. Кнопка обновления сбрасывает серверный кэш. Сохранение
  маршрута больше не сбрасывает получателя алертов. Ошибка чтения маршрута отличается от 404.
- RT07: durable-алерты выбранному сотруднику при отключении, подтверждённом отказе,
  неизвестном исходе/разборе, трёх последовательных ошибках refresh. Нет получателя —
  пропуск без ошибки. Есть дедупликация, фильтры компании/мастерской, персональная лента,
  счётчик и переход к подключениям. Изменения не превращают `unknown` в повторную отправку.
- RT09: владелец подтвердил «Неразобранное» и отсутствие автоматического назначения.
  `status_id = null` использует native Unsorted (`silent: false`), без `responsible_user_id`.

Дополнение после ответов владельца 26.10.2026:

- RT09: подтверждено **«Наше хранилище + вложения в чате amoCRM»**. Оригинал хранится
  приватно, обязательной копии в файловом хранилище CRM нет. Фото, документы, видео,
  голосовые и аудио Telegram Bot нормализуются до обработки подписи. Отдельная durable-очередь
  `telegram.media` сохраняет оригиналы независимо от OAuth и разрешения CRM-проекции.
  Отдельное задание архива не выдаёт ссылку и не вызывает CRM. Импорт использует готовый
  проверенный объект и временную HTTPS-ссылку на час; при повторе ссылка обновляется,
  исходный файл не скачивается заново, `msgid` сохраняется. Подпись остаётся у вложения.
  URL Telegram с токеном не сохраняется в сообщении/очереди и не передаётся в CRM.
- Загрузка через облачный Bot API ограничена 20 МиБ, поток и время ограничены, редиректы
  запрещены, путь от `getFile` проверяется. MIME/содержимое/размер/хеш проверяет существующий
  MediaService. Отклонение оставляет placeholder и дедуплицированный алерт для разбора.
  Без постоянного S3-хранилища архивная очередь не запускается; память процесса не считается
  production-хранилищем. Сохранение оригинала не означает подтверждение доставки в Архив.
- RT03: и Telegram, и остальные адаптеры выбирают CRM-аккаунт из маршрута подключения,
  а не первый активный аккаунт компании. Без маршрута история сохраняется, CRM-задания нет.
  Воркеру оставлены два соединения PostgreSQL: второе требуется для независимого commit
  creation intent, пока основная транзакция проекции открыта. Потерянный ответ и повтор
  проверены также на пуле из двух соединений.
- RT06: добавлены вкладки «Привязка», «Дополнительно», «Диагностика», roving focus,
  стрелки/Home/End, сохранение черновика при смене вкладки. OAuth показывается по состоянию
  CRM-аккаунта, независимо от наличия диалогов; доступ и ошибки refresh не выводятся из
  `crm_bindings`. Ручка статуса учитывает компанию/мастерскую, не расшифровывает токены,
  не обновляет их и не выдаёт секреты/детали аудита. Callback проверяет origin и окно-источник.
- DEP05: владелец выбрал временное хранение backup **на основном VPS**. Готовые сценарии
  уже используют `/opt/messengers2amo/backups`; политика записана в
  `ops/deploy/messengers2amo/BACKUP-POLICY.ru.md`. Их установка и расписание на сервере
  в этой работе не проверялись. Пункт вне VPS остаётся открытым; RPO 15 минут/RTO 2 часа
  не подтверждены владельцем и не заявляются.

Дополнение по сценарию администратора:

- Владелец уточнил приоритеты: простой мастер каналов, интеграция с CRM, сотрудники и роли
  из CRM, выбор воронки и этапа. Добавлена панель «Сотрудники и права каналов»:
  обновление Users/Role API, исходная роль CRM и явная роль выбранного канала.
- Импорт сохраняет идентичности по CRM ID, обрабатывает страницы с ограничением, не следует
  внешним ссылкам пагинации. Ошибка, JSON null или исчезнувшая обещанная страница не стирают
  реестр; полный новый снимок деактивирует отсутствующих. Параллельный старый запрос не
  перезаписывает новый. Пароли и административный доступ к шлюзу не создаются.
- Роли канала: менеджер отвечает по текущему ответственному сделки, руководитель — всем,
  контроль качества — без отправки, без доступа — запрет. Политика включается явным применением
  прав. CRM-администратор не получает доступ к каналу автоматически. Видимость в native-чате
  остаётся по правам amoCRM. Ответственный читается через API сделки; ответственный контакта
  интеграции не подменяет свободное «Неразобранное». Назначение людей в CRM не выполняется.
- Native-отправитель сопоставляется по amojo ID. Право проверяется при приёме и перед отправкой;
  отзыв после принятия задания блокирует вызов Telegram. Временный отказ чтения владельца
  оставляет событие/задание для безопасного повтора; неподтверждённая отправка не повторяется.
- Исправлена потеря роли администратора после F5: `/api/v2/auth/session` возвращает текущую
  серверную роль и область доступа с `no-store`, без секретов. В браузере проверены импорт,
  применение ролей и сохранение административной панели/настроек после перезагрузки.
  Использованы синтетические люди, канал и fake API; тестовый стенд остановлен.
- Ссылки на личный кабинет Wazzup не попали в репозиторий. Кабинет в доступном браузере
  не загрузился (таймаут), поэтому действующие режимы каналов пока не обследованы.

## Эксплуатационная подготовка

Перед развёртыванием нужны миграции **15** (`channel_alerts`, счётчик refresh), **16**
(`connection_name`) и **17** (CRM directory и явные права канала). Для секретов Telegram Bot используется настроенный серверный ключ
`AMOCRM_TOKEN_KEY`; изменение ключа требует отдельной процедуры ротации сохранённых конвертов.
Существующие подключения с прежними ссылками на credentials совместимы со старой конфигурацией.

Мастер требует заранее настроенный источник чатов amoCRM. Он не регистрирует webhook и не
включает канал автоматически. Источник должен быть привязан к выбранной воронке в amoCRM;
соответствие проверяется в RT08. Рабочие доступы и миграции на production в этой работе не менялись.

Источники протокола: [Chats API](https://www.amocrm.ru/developers/content/chats/chat-api-reference),
[webhook v2](https://www.amocrm.ru/developers/content/chats/chat-webhooks),
[контакты и связь чатов](https://www.amocrm.ru/developers/content/crm_platform/contacts-api).
