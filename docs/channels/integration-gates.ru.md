# Матрица ограничений подключения каналов (WhatsApp, MAX, VK)

Задача: TG13. Дата проверки: 21.10.2026; статусы кода сверены с репозиторием 22.10.2026.
Статус: desk verification по публичной первичной документации + реализованные адаптеры
(`apps/api/src/channels/{whatsapp-cloud,max,vk}.ts`) и их автотесты
(`apps/api/test/channels.*.test.ts`); **это не sandbox и не live-приёмка**.

Что проверено и как:

- **Подтверждено** — прямо прочитано в официальной документации провайдера 21.10.2026
  (Meta for Developers, dev.max.ru) или в официальном публичном JSON-схеме VK
  (`github.com/VKCOM/vk-api-schema`, файлы `callback/objects.json`, `messages/methods.json`,
  `messages/objects.json`).
- **Требует проверки** — не подтверждено первоисточником в этой сессии: либо страница недоступна
  reader'у, либо утверждение взято из общей практики. Числовые лимиты, которых нет в
  документации, здесь не выдумываются.
- **Заблокировано** — без внешнего доступа (аккаунт, регистрация, договор) проверить нельзя.

Ограничение доступа в этой сессии: `dev.vk.com` и `vk.com/dev` не отдавались web-reader'у
(ошибка загрузки). Поэтому VK-факты ниже опираются на официальный репозиторий схем VKCOM, а
не на HTML-документацию; расхождения с текущей страницей Callback API возможны и отмечены.

## 2. WhatsApp

### 2.1. Cloud API — подтверждено

**Отправка.** `POST https://graph.facebook.com/{version}/{phone-number-id}/messages`,
заголовок `Authorization: Bearer <token>`, `Content-Type: application/json`.
Поддерживаются типы `text`, `image`, `document`, `audio`, `video` и др.; медиа передаётся
объектом с `id` **или** `link` («Either `id` or `link` is required»). Успешный ответ 200
содержит `messages[].id` и `message_status` (`accepted`, `held_for_quality_assessment`,
`paused`). `accepted` означает «принято к обработке», а не «доставлено».
Источник: Cloud API Reference — Messages.

**Webhook.** Конверт `object: "whatsapp_business_account"` → `entry[].changes[].value`.
Входящее: `value.messages[]` c `from`, `id`, `timestamp`, `type`. Статусы: `value.statuses[]`
c `id`, `status`, `timestamp`, `recipient_id`. Документация прямо указывает, что на одно
исходящее сообщение может прийти **до трёх отдельных webhook** — `sent`, `delivered`, `read`.
Ошибки приходят в `value.errors`, `value.messages[].errors`, `value.statuses[].errors`.
Источник: Webhook payload examples.

**Подпись.** `X-Hub-Signature-256: sha256=<hex>`, HMAC-SHA256 по **сырому телу запроса** с
App Secret; сравнивать нужно часть после `sha256=`. Источник: Graph API Webhooks — Getting
Started (там же пример на Node с `createHmac("sha256", appSecret).update(buf)`).
Оговорка: страница именно WhatsApp Cloud API про подпись молчит, поэтому опора — общая
документация Graph webhooks. **Требует проверки:** поведение на реальном подписанном fixture
(пробелы, unicode escaping) — как и для amoCRM, нельзя пересериализовывать JSON.

**Медиа.** `POST /{phone-number-id}/media` (`file`, `type`, `messaging_product`) → `{id}`.
`GET /{media-id}` → `url`, `mime_type`, `sha256`, `file_size`; URL живёт 5 минут.
Медиа из webhook доступно 7 дней, загруженное — 30 дней. Задокументированные размеры:
изображения 5 MB, документы 100 MB, аудио/видео 16 MB, стикеры 100/500 KB. Свыше 100 MB —
ошибка `131052`. Источник: Cloud API Reference — Media.

**Окно и шаблоны.** Окно 24 часа открывается входящим сообщением/звонком и продлевается
новым; внутри можно отправлять сервисные сообщения любого поддерживаемого типа; после
закрытия — только заранее одобренные шаблоны. Согласие получателя требуется в любом случае.
Источник: Cloud API — Send messages.

**Лимиты и ошибки.** Документированы: пропускная способность по умолчанию до 80 сообщений/с
на номер; парный лимит «1 сообщение одному получателю каждые 6 секунд» (ошибка `131056`);
`130429` — достигнут throughput; `80007` — лимит WABA; `4` — лимит приложения; `131048`,
`131047`, `131049`, `131050` и др. Рекомендация документации — строить обработку на `code`
и `details`, а не на HTTP-статусе или тексте `message`. **HTTP 429 в этих разделах явно не
описан**; поэтому адаптер трактует 429 как retryable, но основной сигнал — код ошибки.
Источники: Cloud API Overview (Rate limits), Error codes.

**Наш адаптер** (`apps/api/src/channels/whatsapp-cloud.ts`):
- проверяет подпись по сырым байтам, constant-time сравнение;
- нормализует `text`/`image`/`document`/`audio`/`video`; остальные типы → `unsupported`
  (событие не теряется);
- `sent`/`delivered`/`read` из webhook — отдельные факты; `sent` не считается delivery;
- 429 и 5xx → `failed` + `retryable`; таймаут → `unknown`; 2xx без `messages[].id` → `unknown`;
- медиа-отправка разрешена только если передан `mediaResolver`; иначе `mediaReply=unknown`
  и отправка отклоняется `CapabilityNotAllowedError`.

Проверено автотестами (`apps/api/test/channels.whatsapp.test.ts`): неверная подпись
отклоняется до разбора (стр. 84), подпись считается по сырым байтам (стр. 115), порядок
`read` → `delivered` не понижает итоговый статус (стр. 175). Это проверка нашего кода, а не
поведения Meta на реальном аккаунте.

### 2.2. WhatsApp QR — не выбран

Официального серверного API для подключения по QR нет. Такие решения строятся на
неофициальном реверс-инжиниринге Web-протокола: нет договора, нет гарантий, высокий риск
блокировки номера и нарушения условий. **Заблокировано** до появления официального пути;
для проекта это означает: либо Cloud API, либо отказ от канала, но не «тихий» QR-мост.
**Не подтверждено:** любые цифры лимитов и стабильность — не проверялись и не заявляются.

## 3. MAX

### 3.1. Bot API — подтверждено

**Доступ.** HTTP API для ботов, домен `platform-api2.max.ru` (старый `platform-api.max.ru` —
нет), авторизация заголовком `Authorization: <access_token>`; передача токена через
query-параметры больше не поддерживается. Токен выдаётся при создании бота в разделе
«Чат-боты». Профиль организации/ИП/самозанятого и модерация бота — часть процедуры платформы.
Источник: dev.max.ru — Обзор API, POST /messages.

**Отправка.** `POST /messages`, адресация `user_id` или `chat_id`, текст до **4000**
символов, не более **двух сообщений в секунду** на один диалог/группу/канал; ответ 200
содержит объект `Message`. Коды: 401 — неверный токен, 500 — внутренняя ошибка.
Источник: dev.max.ru — POST /messages.

**Webhook.** `POST /subscriptions`: endpoint только HTTPS на 443, валидная цепочка от
доверенного CA, CN/SAN совпадает с доменом; ответ 200 **за 30 секунд**; при сбое — до
**10 повторов** с экспоненциально растущим интервалом (60 с, 150 с, 375 с, …); после
**8 часов** без успеха подписка снимается. `secret` опционален, но рекомендуется; проверяется
по заголовку `X-Max-Bot-Api-Secret`, формат `^[a-zA-Z0-9_-]{5,256}$`. Пока активна
webhook-подписка, Long Polling не работает. Источник: dev.max.ru — POST /subscriptions.

**Типы событий.** `message_created`, `message_edited`, `message_removed`, `message_callback`,
`bot_started`, `bot_added`, `bot_removed`, `chat_title_changed`, `dialog_*`, `comment_*` и др.
Объект `Update` содержит `update_type`, `timestamp` (мс), `chat_id`, `user`.
Источник: dev.max.ru — Объект Update.

**Чего документация в прочитанных разделах НЕ даёт:** структуру `Message.body` (`mid`, `seq`)
на странице Update нет — она на отдельной странице объекта Message, которую reader отдал
частично (поля `sender`, `recipient`, `timestamp`, `link`, `body`, `stat`, `url`, без
внутренней структуры `body`). Поэтому в адаптере извлечение `mid`/`text` сделано
защитно (отсутствие → событие пропускается, а не падает), и это **требует проверки** на
реальном webhook fixture.
Также **не подтверждены** read/delivery receipts: в просмотренных разделах полей статусов
нет. В `capabilities()` они `unknown`.

**Наш адаптер** (`apps/api/src/channels/max.ts`): проверка `X-Max-Bot-Api-Secret`
(constant-time, обязательна если настроена), разбор `message_created`, `dialog` → private,
`chat`/`channel` → group, текст ≤ 4000 до HTTP-вызова, 429/5xx retryable, таймаут → unknown.

Проверено автотестами (`apps/api/test/channels.max.test.ts`): неверный/пустой secret
отклоняется (стр. 38, 55), повторный update коммитится один раз (стр. 100), текст > 4000
отклоняется до HTTP (стр. 133), `capabilities()` не обещает receipts (стр. 184).

### 3.2. Обычный аккаунт и Open Client API

Open Client API существует как **отдельная программа** для альтернативных клиентских
приложений: нужны одобрение, сертификат и App-ID; архитектура — прямое взаимодействие
устройства пользователя с MAX, без backend/proxy/gateway разработчика и без передачи данных
на стороннюю инфраструктуру. Публично описанная программа **не обосновывает** серверный
CRM-шлюз для обычного аккаунта. Техническая документация обычного аккаунта публикуется ZIP-архивом;
в этой сессии архив не скачивался и не исполнялся.
Вывод: режим личного аккаунта — **UNKNOWN**, требует отдельного письменного подтверждения MAX.
Подменять требуемый personal-режим ботом нельзя молча — это меняет и адресата, и гарантии.

## 4. VK

### 4.1. Callback API — подтверждено схемой VKCOM

Официальная JSON-схема (`callback/objects.json`) описывает:

- `callback_base`: `type`, `group_id`, `event_id` («Unique event id. If it passed twice or
  more - you should ignore it»), `v`, `secret` (опционально).
- `type: "confirmation"` — отдельный тип; на него endpoint отвечает строкой confirmation-кода
  из настроек Callback API. До успешного handshake события не доставляются.
- `secret` — общий секрет в **теле** запроса, а не HMAC-подпись тела. Сравнение обязательно,
  если секрет задан в настройках.
- `message_new` → `object.message` (`id`, `peer_id`, `from_id`, `text`, `date`, `out`,
  `conversation_message_id`, `attachments`) + `object.client_info`.
- `message_reply` — ответ на сообщение; `message_read` содержит `peer_id`,
  `read_message_id`, `conversation_message_id` (это событие прочтения **нашим** сообщением,
  не receipt доставки).
- `messages.send` (`messages/methods.json`): `peer_id`, `message` (maxLength **9000**),
  `random_id` — «Unique identifier to avoid resending the message», `group_id`, `v`.
  `peer_id` для чата: `2000000000 + chat_id`; для сообщества: отрицательный ID.

**Ответ endpoint.** VK ожидает `ok` и короткий таймаут; при не-200/таймауте событие
переотправляется, поэтому обработка должна быть идемпотентной по `event_id`.
Точное число повторов и таймаут в этой сессии по первоисточнику **не подтверждены**
(HTML-документация недоступна) — **требует проверки**; в проекте считаем доставку
at-least-once и не полагаемся на конкретное число.

**Наш адаптер** (`apps/api/src/channels/vk.ts`): отвечает на `confirmation`, требует
`secret` для всех остальных событий, дедуплицирует по `event_id`, игнорирует `out: 1`
(эхо собственных сообщений), `peer_id ≥ 2 000 000 000` → group, `random_id` детерминирован
от idempotency key (повтор не создаёт второе сообщение), ошибки VK `{error:{error_code,...}}`
→ `failed`, коды 6/9/10 retryable.

Проверено автотестами (`apps/api/test/channels.vk.test.ts`): неверный/отсутствующий `secret`
отклоняется (стр. 54), повтор callback не дублирует историю (стр. 85), группа по умолчанию
отклоняется, `allow_crm` разрешает (стр. 101, 124).

### 4.2. Long Poll — резервный путь

Альтернатива callback: получение событий через Long Poll API сообщества. В этой сессии
**не проверено** (документация недоступна): ни лимиты, ни задержки, ни поведение при
перезапуске, ни совместимость с параллельными получателями. В production не выбираем, пока
не будет подтверждено; Callback API предпочтителен, т.к. даёт явный `secret` и `event_id`.

## 5. Sandbox-план проверок без массовых рассылок

Правила: только собственные тестовые аккаунты и номера; не более одного получателя на
сценарий; никаких рассылок, импорта контактов и рекламных шаблонов; все секреты — в
переменных окружения, не в репозитории и не в логах.

| # | Проверка | Шаги | Критерий приёмки | Каналы |
|---|---|---|---|---|
| S1 | Входящее сообщение | Один тестовый пользователь пишет в тестовый аккаунт | Событие в `inbox_events` с `provider_event_key`; сообщение и диалог созданы; CRM-задание создано (private) | WA Cloud, MAX bot, VK |
| S2 | Ответ | Ответить на S1 из системы | Провайдер вернул ID; операция `sent`; delivery/read **не** выставлены | все |
| S3 | Фото в обе стороны | Отправить фото пользователю и получить фото от пользователя | Входящее медиа: `attachment` + `mediaId`; исходящее: только при подтверждённом `mediaReply` (WA Cloud), иначе явный отказ | WA Cloud; MAX/VK — отказ до подтверждения |
| S4 | Рестарт | Перезапустить API/worker между приёмом и обработкой | Inbox не потерян; повторная доставка не создаёт дубль; outbox продолжает с места остановки | все |
| S5 | Фильтр групп | Сообщение в группе без правила; затем с `allow_crm` | Без правила: сообщение архивируется, CRM-задания нет; с правилом: задание есть | VK, MAX (группы), WA (группы не поддерживаются Cloud API для обычных номеров — проверить) |
| S6 | Native amoCRM actor | Ответ из интерфейса amoCRM | Автор определяется сервером из сессии amoCRM, а не из тела запроса; в messenger сообщение помечено как исходящее сотрудника | все |
| S7 | Unknown без blind retry | Оборвать ответ провайдера после отправки (таймаут) | Операция `unknown`; автоматического повтора нет; есть задача сверки | все |
| S8 | 429 | Искусственно превысить парный лимит (WA) / частоту (MAX, VK) | `failed` + `retryable`; job остаётся `pending` с backoff, не `completed` | все |
| S9 | Повтор webhook | Отправить тот же webhook дважды | `duplicates=1`, одна запись `inbox_events`, одна история сообщений | все |
| S10 | Out-of-order статусы | `read`, затем `delivered` | Итог остаётся `read`; `delivered` не понижает | WA Cloud |
| S11 | Неверная подпись/секрет | Подпись с чужим секретом; неверный `secret` VK; неверный `X-Max-Bot-Api-Secret` | Запрос отклонён до записи в БД, 401/403, без создания событий | все |

**Статус проверок на 22.10.2026.** Живые проверки S1–S8 и S11 (в части HTTP-кода ответа) не
выполнялись — нет аккаунтов и доступов, это `NOT RUN`, а не `PASS`. На уровне нашего кода
автотестами покрыты:

- S9 (повтор webhook) — `apps/api/test/channels.max.test.ts:100`, `channels.vk.test.ts:85`;
- S10 (out-of-order статусы) — `apps/api/test/channels.whatsapp.test.ts:175`; итог выводится из
  append-only `provider_receipt_evidence` (`apps/api/src/channels/inbox.ts:90-95`);
- S11 (неверная подпись/секрет) — проверка выполняется до любой записи в БД
  (`apps/api/src/channels/inbox.ts:53-55`), тесты: `channels.whatsapp.test.ts:84`,

## 6. Что реально требует живых доступов

Не проверяется кодом и unit-тестами; нужно внешнее окружение:

1. **WhatsApp**: Meta Business Portfolio и WABA, собственный номер, System User token,
   App Secret, публичный HTTPS endpoint; фактический tier пропускной способности и поведение
   при 429; реальный подписанный fixture webhook (включая unicode/пробелы); шаблоны для
   сообщений вне 24-часового окна.
2. **MAX**: создание бота и токен, профиль организации и модерация, HTTPS-443 с валидной
   цепочкой, реальный `message_created` fixture (структура `body.mid`), фактическое наличие
   receipts; для личного аккаунта — письменное подтверждение MAX о допустимости серверного
   шлюза.
3. **VK**: сообщество с правами администратора, токен группы, `confirmation_token`,
   `secret`, реальный callback; фактическая политика повторов и таймаут; решение по Long Poll.
4. **amoCRM**: зарегистрированный канал Chats, `scope_id`, виджет/Sources readiness —
   см. [проверку API amoCRM](../requirements/api-verification-2026-10-21.ru.md).
5. **Инфраструктура**: домен и TLS, доступ к секрет-хранилищу, место для медиа.

## 7. Принятые проектные решения

- **WhatsApp** — только Cloud API. QR-режим исключён из production-пути.
- **MAX** — только Bot API. Личный аккаунт и Open Client не заявляются как поддержанные.
- **VK** — только Callback API; Long Poll — резерв, не включён.
- **Честные capabilities**: `supported` только для того, что документировано **и**
  реализовано адаптером. Всё остальное — `unknown`; `unsupported` — когда провайдер явно
  не имеет функции. Отправка вне allowlist отклоняется `CapabilityNotAllowedError`, а не
  «пробуется тихо».
- **Provider delivery/read никогда не выводятся из успеха HTTP**: они приходят только
  отдельными событиями провайдера и хранятся в append-only
  `provider_receipt_evidence`; поздний `delivered` не понижает `read`.
- **Unknown без blind retry**: таймаут и 2xx без ID сообщения → `unknown`, задача не
  повторяется автоматически.
