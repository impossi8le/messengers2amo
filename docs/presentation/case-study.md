# Messengers2amo: от идеи до интеграции и открытого кода

Состояние материалов: 29 октября 2026 года. Автор публичного репозитория: [impossi8le](https://github.com/impossi8le).

## Проблема и цель

Задача проекта — создать собственный управляемый слой интеграции мессенджеров с amoCRM для одной компании, как альтернативу внешнему сервису интеграции. Менеджеры должны сохранить привычное рабочее место в нативных чатах CRM. Сообщения нужно связывать с контактом и сделкой, назначать ответственных и учитывать ожидание ответа.

Новый контур проверяется параллельно существующему. Экономия, окупаемость и выигрыш в скорости работы в этом кейсе не измерялись.

## Личная ответственность

Я вёл проект от идеи до результата: постановка задачи и границ запуска, ведение разработки серверного API, интерфейса и интеграций, получение доступов, согласование канала с поддержкой amoCRM, диагностика реальных ошибок, организация тестов и ограниченного пилота, подготовка документации и публикация исходного кода.

Результат можно проверить по коду, тестам, документации, эксплуатационным материалам и описанным сценариям пилота.

## Что получилось

- Серверный шлюз сообщений с API и фоновым обработчиком.
- Интеграция Telegram с нативными чатами, контактами и сделками amoCRM.
- Консоль операторов и администраторов: обращения, назначения, подключения и диагностика.
- Обработка файлов и профилей отправителей.
- Durable inbox/outbox, идемпотентность, отдельный статус неопределённой отправки и защита от устаревших действий.
- Адаптеры WhatsApp Cloud, MAX Bot и VK Community в исходниках; их сквозная готовность требует отдельных проверок.
- SQL-миграции, автоматические тесты, CI, инструкции развёртывания и восстановления.

## Технологии

| Слой | Технологии | Назначение |
| --- | --- | --- |
| Backend | Node.js 24, TypeScript, Fastify, Zod, Pino | HTTP API, проверка данных, фоновые обработчики и события |
| Хранилище | PostgreSQL 18, SQL-миграции | Доменная модель, inbox/outbox и аудит |
| Медиа | amoCRM Files API, поддержка S3 | Доставка, привязка и хранение вложений |
| Интерфейс | React 18, Vite, Redux Toolkit / RTK Query | Консоль управления |
| Эксплуатация | Docker Compose, Nginx | Разделение процессов, HTTPS и обновления |
| Проверки | Node test runner, Vitest, TypeScript, GitHub Actions | Регрессия и CI |

S3 поддерживается кодом, но не использовалось как отдельное хранилище в описанном реальном пилоте.

## Открытый код как преимущество

Публичный репозиторий делает устройство системы доступным для изучения и аудита. Собственное размещение даёт контроль над окружением и графиком обновлений. Архитектура допускает развитие адаптеров и правил под задачи компании, уменьшая организационную зависимость от готового сервиса.

Это не означает нулевую стоимость: остаются инфраструктура, сопровождение и ограничения внешних платформ. Формальная open-source лицензия для внешнего использования пока не выбрана.

## Работа с поддержкой amoCRM

OAuth для REST API и регистрация канала Chats API проходят отдельно. Для регистрации чатов [документация amoCRM](https://www.amocrm.ru/developers/content/chats/chat-start) требует обратиться в техническую поддержку и передать сведения о сервисе, HTTPS-webhook, аккаунтах, SVG-иконке и необходимых функциях. В ответ выдаются параметры доступа к API чатов.

В проекте 28 октября подана заявка с ответами по 16 пунктам и иконкой. Поддержка зарегистрировала канал и уточнила webhook v2, необходимость отдельных каналов для других мессенджеров и пользовательского Telegram, а также порядок изменения функций канала.

29 октября остался открытым вопрос загрузки PNG/TXT через редактор amoCRM: файл зависает до возникновения webhook. Поддержке передана диагностика и запрошены конкретные дальнейшие действия. Серверная передача файлов проверена отдельно; полный пользовательский путь через кнопку «Отправить» пока не подтверждён.

## Реальные инженерные эпизоды

1. **Профиль отправителя.** Вместо жёсткого имени «Клиент» добавлена передача фактического имени и защищённой ссылки на аватар. Имена и аватары двух тестовых профилей проверены визуально.
2. **Подпись обратного webhook.** На реальном запросе локализовано различие в HMAC. Обработчик проверяет исходные байты и допускает только ограниченную обработку внешних ASCII-пробелов. Изменение содержания JSON по-прежнему отклоняется.
3. **Вложения.** Разделены серверная обработка настоящих файлов amoCRM и зависание интерфейса до webhook. Серверный путь реализован и проверен; проблема редактора передана поддержке.
4. **Повторные и конкурирующие действия.** Уникальные ключи и fingerprint защищают от повторной обработки. CAS, lease, fence и binding epoch ограничивают конкурирующие и устаревшие операции. Неопределённый результат отправки сохраняется как `unknown` без слепого автоматического повтора.

## Проверенный результат

По протоколам 29 октября с обновлением в 16:18 МСК:

- Текстовый обмен прошёл в обе стороны в двух отдельных тестовых диалогах Telegram и amoCRM.
- Имена и аватары отправителей подтверждены визуально.
- Входящие JPEG и TXT скачаны из amoCRM; контрольные суммы проверены.
- Серверная исходящая передача фото и TXT проверена в двух диалогах. Для TXT проверены имя, размер и SHA-256. Telegram перекодирует фото, поэтому их побайтное совпадение не заявляется.
- Одна отдельная попытка отправки TXT осталась `unknown`; её состояние не сбрасывалось. Последующий успешный тест использовал новый явный ключ.
- Глобальная исходящая отправка вне ограниченного пилота не включалась.

Первоначальный публичный снимок `322d158` прошёл 919 локальных тестов. Отдельный изолированный кандидат исходящих вложений прошёл 616 API-тестов. Эти наборы относятся к разным состояниям проекта, пересекаются и не суммируются. Подробности текущих проверок смотрите в [GitHub Actions](https://github.com/impossi8le/messengers2amo/actions).
