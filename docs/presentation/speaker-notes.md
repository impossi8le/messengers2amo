# Заметки для выступления

Состояние проекта: 29 октября 2026 года.

## 01. Свой шлюз мессенджеров для amoCRM

Я вёл Messengers2amo от идеи до интеграции, тестового пилота и публикации исходников. Задача — создать собственную альтернативу сервису интеграции мессенджеров для одной компании. Менеджеры сохраняют привычное рабочее место в amoCRM, а наша система управляет связью с каналами, обработкой обращений и файлами. В рассказе покажу проблему, получившийся продукт, технологии, реальные препятствия и результаты проверок.
Источник: https://github.com/impossi8le/messengers2amo

## 02. Проблема и цель

Нужен был собственный управляемый слой интеграции рядом с действующим Wazzup. Сообщения разных каналов требуется связывать с контактом, сделкой и ответственным. Команде нужно понимать, какие обращения ждут реакции. Компании нужен контроль правил, размещения и исходного кода. Я не заявляю измеренную экономию или окупаемость: для них нужны отдельные данные.
Источник: docs/messenger-platform-requirements.ru.md

## 03. Мой вклад

Моя ответственность охватывала полный цикл: формулировку задачи и границ первого запуска, ведение разработки API, интерфейса и интеграций, организацию доступов и работу с поддержкой amoCRM, тестирование, диагностику, пилот и открытую публикацию. На техническом обсуждении могу разобрать конкретные решения, инструменты и способы проверки результата.
Источники: README.md; docs/requirements/access-request.ru.md

## 04. Получившийся продукт

Для менеджера результатом стал диалог Telegram в штатном чате amoCRM с контактом, сделкой и профилем отправителя. Для команды реализованы очередь, назначения, история и учёт ожидания ответа. Для администратора есть подключения, маршруты, роли и диагностика. Сквозной пилот подтверждён для Telegram. Другие адаптеры требуют собственных доступов и отдельных проверок.
Источник: README.md; docs/presentation/case-study.md

## 05. Открытый код и своё размещение

Публичный репозиторий позволяет изучить логику и проверить обработку данных. Собственное размещение даёт контроль окружения и обновлений. Архитектура допускает новые адаптеры и правила под задачи компании. При этом остаются расходы на инфраструктуру, сопровождение и ограничения внешних API. Формальная open-source лицензия для внешнего использования пока не выбрана.
Источник: https://github.com/impossi8le/messengers2amo

## 06. Технологии

Backend использует Node.js 24, TypeScript и Fastify. PostgreSQL хранит доменные данные и очереди. React, Vite и RTK Query поддерживают консоль управления. Docker Compose разделяет API, worker и БД, Nginx завершает HTTPS. Проверки используют Node test runner, Vitest, TypeScript и GitHub Actions. S3 поддерживается кодом; в описанном реальном пилоте файлы передавались через amoCRM Files API.
Источники: apps/api/package.json; apps/web/package.json; ops/deploy/messengers2amo/docker-compose.yml

## 07. Архитектура

Событие приходит через webhook или polling, сохраняется в inbox PostgreSQL и обрабатывается worker. Система связывает сообщение с доменом и CRM. Ответ из amoCRM попадает в очередь исходящих, после чего worker проверяет право отправки и вызывает адаптер. Это создаёт точку фиксации в нашей БД, но не даёт абсолютной гарантии exactly-once во внешней сети.
Источники: apps/api/src/telegram/inbox.ts; apps/api/src/telegram/send.ts; apps/api/src/worker.ts

## 08. Работа с поддержкой amoCRM

OAuth для REST и регистрация Chats API канала — разные этапы. Для канала нужно обратиться в техническую поддержку, передать название, HTTPS-webhook, список аккаунтов, SVG-иконку и ответы о функциях. В ответ предоставляются параметры доступа. В нашем проекте канал зарегистрирован 28 октября 2026. Уточнялись webhook v2 и отдельные каналы для разных мессенджеров. По зависанию загрузки вложений до webhook запрос на диагностику остаётся открытым.
Официальная документация: https://www.amocrm.ru/developers/content/chats/chat-start
Статус проекта: docs/presentation/case-study.md

## 09. Реальные проблемы и исправления

В импорте профиль отправителя отображался как «Клиент». После изменения проверены имена и аватары двух тестовых аккаунтов. Реальная подпись обратного webhook потребовала проверки исходных байтов с ограниченной обработкой внешних пробелов, без пересериализации JSON. Для вложений разделены серверная передача и зависание редактора amoCRM: backend проверен отдельно, внешняя проблема передана поддержке.
Источник: docs/presentation/case-study.md

## 10. Надёжность

Повторные события защищены уникальными ключами и fingerprint. Timeout с неясным результатом сохраняется как unknown и не вызывает слепой повтор. Версия назначения, lease и fence worker защищают от конкурирующих и устаревших действий. Эти механизмы решают разные задачи и не заменяют сквозную проверку провайдера.
Источники: apps/api/src/telegram/inbox.ts; apps/api/src/telegram/send.ts; apps/api/src/repo/assignment.ts

## 11. Проверенный результат

На 29 октября 2026 текст прошёл в обе стороны в двух отдельных тестовых диалогах Telegram и amoCRM. Профили отправителей подтверждены визуально. Входящие JPEG и TXT скачаны из amoCRM с проверкой SHA-256. Серверная исходящая отправка фото и TXT проверена в двух диалогах. Полный путь исходящего вложения через редактор CRM пока не подтверждён. 919 тестов относятся к первоначальному публичному снимку, 616 — к отдельному кандидату вложений. Эти наборы пересекаются и не суммируются.
Источник: docs/presentation/case-study.md

## 12. Следующие шаги

Нужно получить конкретный ответ поддержки по зависанию загрузки и повторить путь через кнопку «Отправить». Затем проверить другие каналы и полный цикл обработки обязательств. Для внешнего переиспользования исходников нужно оформить лицензию. Также остаются обновление зависимости Zod по npm audit и измерение нагрузки. Глобальная исходящая отправка вне ограниченного пилота не включалась.
Источники: docs/amocrm/outbound-files.ru.md; .github/workflows/security.yml; docs/presentation/case-study.md

## 13. Итог

Я взял потребность собственной интеграции мессенджеров с amoCRM и довёл её до проверяемого результата: серверного шлюза, интерфейса управления, пилота и публичного исходного кода. В работе были внешние доступы, согласование канала с поддержкой, реальные ошибки и повторные проверки. Могу открыть репозиторий и подробно разобрать один из этих эпизодов.
Репозиторий: https://github.com/impossi8le/messengers2amo
