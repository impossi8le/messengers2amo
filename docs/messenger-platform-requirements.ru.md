# Требования к функциональному аналогу Wazzup

Практический следующий шаг: [стек, доступы и параллельный запуск рядом с Wazzup](stack-and-parallel-rollout.ru.md). CRM подтверждена: amoCRM; в обследование входят WhatsApp, Telegram, VK и MAX, способы действующих подключений пока неизвестны.

Углубленная проработка бизнес-логики от 21.10.2026: [доменная спецификация](messenger-domain-logic.ru.md) и [сценарии приемки](messenger-logic-acceptance.ru.md). Эти материалы уточняют правила обработки и гонок; дата проверки внешних API в исходном исследовании остается прежней. Предложенные правила по умолчанию еще не являются утвержденной политикой компании.

Дата исследования: 20 октября 2026 года. Назначение: основа для оценки проекта и технического задания. Заказчик уточнил: это внутренний сервис для своей компании, а не SaaS для сторонних организаций. Факты ниже сопровождаются источниками; архитектура, приоритеты, сроки и показатели приемки — предложения для обсуждения. Изучены открытые страницы, без доступа к платному кабинету Wazzup.

Статус на 22.10.2026: production-ядро реализовано и развёрнуто, сквозные прогоны с реальными каналами ждут выдачи тестовых доступов. Требования ниже остаются основой объёма; реализованные части перечислены в [корневом README](../README.md).

## 1. Что разрабатываем

Внутренний сервис для общения сотрудников компании с клиентами из разных мессенджеров через единый интерфейс и amoCRM. Допускаются несколько своих номеров, ботов и отделов. Биллинг SaaS, самостоятельная регистрация сторонних компаний и массовый onboarding не входят в MVP. Повторяем полезные сценарии: переписка в карточке клиента, создание контакта/сделки из обращения, распределение диалогов, контроль ответов, вложения, быстрые ответы и автоматизации. Отдельно учитываем состояние «прочитано менеджером» и «клиент ждет ответа». Эти сценарии заявлены на [странице Wazzup](https://wazzup24.ru/whatsapp-for-amocrm/); фактическая работа закрытого продукта не проверялась.

Это функциональный аналог с собственными названием, дизайном и реализацией. Главная сложность — подключения, ограничения платформ и надежная доставка, а не внешний вид чата.

Предлагаемый основной контур: WhatsApp Business Platform, Telegram Bot, MAX Bot, VK и amoCRM. Telegram Secretary/Business — отдельный проверочный прототип. Instagram, Messenger и Viber — после подтверждения спроса и доступа. Это порядок разработки, а не рейтинг популярности.

Нельзя обещать для всех каналов одинаковые функции: первое сообщение по номеру, полную старую историю, группы, реакции и подтверждения прочтения. В продукте нужна таблица возможностей каждого подключения.

## 2. Каналы: доступы и ограничения

| Канал | Что получить | Что заложить в продукт |
|---|---|---|
| WhatsApp Cloud API | Meta business portfolio, WABA, бизнес-номер, доступ владельца, приложение, токен и необходимые permissions | Согласия, шаблоны, окно ответов, медиа, webhook и фактические статусы |
| Telegram Bot | Бот и токен BotFather | Пользователь обращается первым; архивируем поступающие события |
| Telegram Secretary/Business | Разрешенное владельцем подключение аккаунта и права бота | Проверяем connection, область чатов и `can_reply` |
| MAX Bot | Верифицированный профиль, одобренный бот, токен | Production webhook, контроль подключения и восстановление подписки |
| VK | Сообщество, администратор, сообщения и токен | Callback/Long Poll, разрешения получателя, дедупликация |

**WhatsApp.** Для собственного подключения требуются владение номером, регистрация, профиль бизнеса и способ оплаты. Основные permissions: `whatsapp_business_management` и `whatsapp_business_messaging`; дополнительные — по операциям. Для внутреннего MVP проверяем доступ приложения к собственному WABA. Embedded Signup для сторонних компаний и соответствующие App Review/Advanced Access становятся отдельной задачей при переходе к SaaS; их нельзя автоматически считать обязательной работой текущего MVP. [Cloud API](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api), [Embedded Signup](https://www.postman.com/meta/whatsapp-business-platform/documentation/du6gzjv/embedded-signup).

Хранить основание согласия и отказ, отсчитывать 24 часа от последнего сообщения клиента; вне окна использовать разрешенные утвержденные шаблоны. Учитывать отклонение шаблона и ошибки доставки. Прямое официальное API не равно подключению обычного WhatsApp сканированием QR. Совместное использование приложения и API, перенос номера и доступность для конкретной компании проверяются отдельно; автоматическую выгрузку всей истории телефона не включать в обещания. [Политика WhatsApp](https://whatsappbusiness.com/policy/), [webhook Meta](https://www.postman.com/meta/whatsapp-business-platform/folder/tduohwq/webhook-payload-reference).

**Telegram.** Обычный бот представляет бота, а не номер сотрудника, и не начинает личную переписку произвольно. Secretary/Business может отвечать от подключенного аккаунта в разрешенных чатах; право `can_reply` связано с входящими за последние 24 часа. Premium нельзя считать универсальным обязательным условием: актуальный Bot API разрешает Secretary Bots без него. События нужно своевременно сохранять; произвольный импорт старых личных диалогов через Bot API не предусмотрен. [Введение](https://core.telegram.org/bots), [Business Bots](https://core.telegram.org/bots/features#business-bots), [Bot API](https://core.telegram.org/bots/api).

Полноценный пользовательский клиент через MTProto/TDLib — отдельная разработка: собственные `api_id/api_hash`, авторизация, 2FA, защищенные сессии, восстановление событий и FloodWait. Доступ пользовательского клиента к истории не следует переносить на ботов. [Регистрация приложения](https://core.telegram.org/api/obtaining_api_id), [получение истории](https://core.telegram.org/method/messages.getHistory).

**MAX.** Базовый вариант — бот после верификации и модерации. Актуальная документация указывает `platform-api2.max.ru` и передачу токена заголовком Authorization. Для production требуется HTTPS webhook; контролировать его работоспособность и восстановление подписки после длительных ошибок. Наличие метода истории не означает доступ к прошлой личной переписке. [Платформа](https://dev.max.ru/docs), [обзор API](https://dev.max.ru/docs-api), [подписки](https://dev.max.ru/docs-api/methods/POST/subscriptions).

MAX публикует Open Client API для альтернативных клиентов; пригодность для серверного подключения личного аккаунта к CRM пока не подтверждена. Этот вариант оценивать отдельным исследованием, не включать как гарантированную функцию MVP. [Open Client API](https://dev.max.ru/docs/open-api).

**VK.** Использовать сообщения сообщества, а не личную переписку сотрудника. Нужны разрешения, токен, события и `messages.send`; сохранять `peer_id`, внешние ID и `random_id`. Не обещать исходящее любому пользователю: учитывать запреты, приватность и блокировки. [Официальный SDK VKCOM](https://github.com/VKCOM/node-vk-call), [методы сообщений](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/Actions/Messages.php).

**Дополнительные каналы.** Instagram требует профессиональный Business/Creator аккаунт, OAuth и разрешения сообщений; в варианте Instagram Login Facebook Page не обязательна. Клиент должен сначала написать бизнесу; полной истории и групп обещать нельзя. Доступ внешних клиентов и окно ответов подтвердить прототипом. [Instagram Login](https://www.postman.com/meta/instagram/folder/6raa77c/instagram-api-with-instagram-login), [Messaging](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api).

Messenger подключает Facebook Page с `pages_messaging` и Page token; стандартное окно ответа — 24 часа, исключения требуют предусмотренного основания. [Messenger Send API](https://www.postman.com/meta/messenger-platform-api/folder/vilwbh4/send-api).

Новые Viber-боты создаются на коммерческих условиях. Chatbot API работает с подписчиками; Business Messages по телефонной базе — отдельный партнерский продукт. До оценки получить предложение партнера и подтверждение географии. [Viber Bot API](https://developers.viber.com/docs/api/rest-bot-api/).

## 3. amoCRM

Нужны тестовый аккаунт администратора, интеграция, публичный endpoint и отдельная регистрация канала Chats API через поддержку. Для внутреннего сервиса сначала проверить приватный канал в своем аккаунте; массовая публикация не входит в MVP. Сохранять `amojo_id`, `scope_id`, ID канала и бота. Chats API подписывается на backend через HMAC-SHA1; секрет недопустим в браузере. Встроенный выбор шаблонов после окончания окна документация заявляет только для `.com`: для `.ru` подтвердить решение отдельно. [Начало работы](https://www.amocrm.ru/developers/content/chats/chat-start).

REST API контактов, сделок и пользователей использует OAuth. Проверять `state`, безопасно хранить и атомарно обновлять токены: refresh token одноразовый. Обрабатывать отзыв доступа и повторное подключение. [OAuth](https://www.amocrm.ru/developers/content/oauth/step-by-step).

Привязывать чат к существующему контакту либо создавать новое обращение по согласованным правилам. Получение истории CRM ограничено чатами интеграции и не заменяет исторический импорт мессенджера. Передавать фактические статусы и ошибки, корректно обслуживать ссылки вложений. [Возможности](https://www.amocrm.ru/developers/content/chats/chat-capabilities), [методы](https://www.amocrm.ru/developers/content/chats/chat-api-reference).

Учитывать квоты REST API, `429` и состояние подписки. Собственный виджет нужен для настроек и расширенного UX; публичная публикация требует модерации. [Ограничения](https://www.amocrm.ru/developers/content/api/recommendations), [WEB SDK](https://www.amocrm.ru/developers/content/web_sdk/start), [публикация](https://www.amocrm.ru/developers/content/integrations/upload).

## 4. Функциональные требования

- Сотрудники, отделы, роли, свои номера/боты и диагностируемые состояния подключений.
- Список диалогов, поиск, ответственный, передача, непрочитанные и ожидающие ответа.
- Текст, изображения, файлы; голосовые и цитирование согласно возможностям канала.
- Шаблоны, быстрые ответы, уведомления, рабочее время и простые автоответы.
- Связи с контактами/сделками, правила создания и обработка дублей.
- История новых сообщений, статусы отправки, понятные ошибки и повторная отправка с защитой от дублей.
- Раздельные идентификаторы клиентов по каналам; объединение только по проверенному правилу, без автоматического отождествления по имени.
- Журнал действий, экспорт/удаление данных, видимость очереди ошибок для поддержки.

## 5. Архитектура и эксплуатация

Предлагаемый поток: **API каналов → прием событий → надежная очередь → ядро диалогов → адаптер amoCRM / интерфейс операторов**. Исходящие проходят проверку возможностей, согласий, окна и лимитов перед отправкой.

Нужны БД сообщений и связей, объектное хранилище вложений, защищенное хранилище секретов, планировщик повторов, мониторинг и аудит. Стек выбирать после оценки команды и нагрузки; микросервисы не являются обязательным условием первой версии.

Подтверждать прием события после надежного сохранения, устранять дубли, учитывать нарушение порядка и неопределенный результат отправки. Не обещать абсолютное «ровно один раз» при внешних сбоях. Разграничить доступ сотрудников и отделов, проверять webhook, ограничивать доступ к файлам, шифровать секреты, исключать их из логов. Согласовать сроки хранения, резервирования, восстановления и удаления; отдельно проверить применимые требования к персональным данным, размещению и трансграничной передаче с ответственным специалистом.

До оценки мощности получить число отделов, подключений и операторов, сообщений/сутки, пиковый поток, объем медиа и срок хранения. Измерять задержки, ошибки, очереди, отключения и обновление токенов.

## 6. Этапы, команда, расходы

Предварительное допущение: 2 backend-разработчика, 1 frontend, 1 QA; частичная занятость аналитика/руководителя и DevOps. При готовых доступах: 1–2 недели на уточнение и прототипы; 6–10 недель на ядро, amoCRM и первый канал; еще 4–6 недель на дополнительные адаптеры, пилот и стабилизацию. Итого ориентир 3–5 месяцев для ограниченного MVP. Это наша оценка, не обязательство: согласования платформ и изменения объема считаются отдельно.

Оценка относится к нескольким адаптерам и собственному интерфейсу. Для внутреннего пилота с одним каналом и стандартным чатом amoCRM объем меньше; новую оценку даем после прототипа. Отдельный inbox, личные аккаунты и импорт истории нельзя считать включенными в тот же срок автоматически.

Первую вертикаль запускать с одним каналом и amoCRM. Затем добавлять остальные подтвержденные каналы. Отложить нативные приложения, универсальный конструктор ботов, массовые рассылки, сложную аналитику, другие CRM и пользовательские клиенты.

Бюджет разработки = трудозатраты × согласованные ставки + прототипы + резерв изменений. Ежемесячные расходы = инфраструктура + хранение/трафик/backup + мониторинг + поддержка + CRM + платежи каналам/партнерам. Стоимость сообщений рассчитывать по актуальным условиям страны, категории и провайдера; тарифы из старых примеров не фиксировать.

## 7. Что запросить до разработки

**У заказчика:** страны и юридическое лицо; приоритеты каналов; бот или личный аккаунт; свои номера/боты и их владельцы; обязательные сценарии; отделы и права сотрудников; нагрузка; CRM и правила дублей; хранение; согласия; пилотные аккаунты; бюджет и ответственный за приемку. Внутреннее назначение сервиса уже подтверждено.

**У платформ/провайдеров:** доступность подключения и оплаты; требования верификации; permissions и проверки приложения; договор и квоты; допустимые исходящие; медиа/история/статусы; перенос номера; условия поддержки и отключения. Получить подтверждение для реального клиента, не только developer sandbox.

**У команды:** прототип каждого обязательного канала; перечень неподдерживаемых функций; модель данных и угроз; план миграций/backup; мониторинг; инструкции подключения и восстановления; оценку после прототипов. Секреты передавать через защищенное хранилище, не документы и чат.

## 8. Критерии приемки и риски

Приемка проводится на аккаунтах пилота: входящий текст/вложение попадает в нужную карточку; ответ доходит в верный канал; повтор webhook не создает дубль; запрещенное исходящее блокируется с причиной; статусы отражают события платформы. Проверить отзыв доступа, обновление токенов, простой и восстановление, недоступные медиа, лимиты, права отделов и сотрудников, экспорт/удаление и восстановление backup. Согласовать численные показатели задержки, нагрузки и времени восстановления после прототипа.

Основные риски: одобрения и региональная доступность, изменения API, ограничения исходящих, потеря подписки, блокировка аккаунта и ошибочная склейка клиентов. Снижение риска: официальные API, прототипы до обещаний, журнал событий, диагностируемые подключения и ограниченный пилот.

Часть прямых страниц Meta возвращала HTTP 429, документация dev.vk.com была недоступна; использованы официальные коллекции Meta и SDK VKCOM. Проверку production-доступов, актуальных квот и спорных правил завершить до окончательной оценки. Подробности: основные каналы (внутренние исследовательские материалы; в репозиторий не включены), дополнительные каналы (внутренние исследовательские материалы; в репозиторий не включены).

## 9. Уточнения после архитектурной проработки

Примерная [архитектура внутреннего сервиса](messenger-platform-architecture.ru.md) описывает компоненты, потоки, данные и отказные сценарии. В первой версии рекомендуются единая кодовая база, отдельные процессы API/workers и надежное хранение состояния в БД. Конкретные технологии — кандидаты, а не утвержденный стек.

Обязательные требования к реализации:

- Webhook подтверждается после надежной записи; необработанное событие можно найти и без уведомления брокера.
- Изменение сообщения и задание на дальнейшую обработку фиксируются одной транзакцией. Повторы различают новое сообщение, правку, удаление и статус.
- Таймаут отправки может означать, что клиент уже получил сообщение. Состояние `unknown` требует сверки либо ручного решения; слепой повтор запрещен.
- Принятие нашим API, успех API канала, доставка и прочтение — разные состояния. Для неподдерживаемых статусов интерфейс не выдумывает подтверждение.
- Создание контактов и сделок при повторе или таймауте защищается связями и сверкой; универсальная идемпотентность внешнего API не предполагается.
- Оператор имеет доступ только к разрешенным диалогам, подключениям и файлам; отзыв прав действует и для скачивания вложений.
- Один исполнитель обновляет OAuth-токены подключения; неопределенный результат обновления передается в восстановление доступа.
- Файлы проходят ограничения и проверку; внутренние адреса и опасные перенаправления блокируются. Ссылки для CRM ограничены и проверяются на повторное скачивание.
- После восстановления backup сначала сверяют внешние отправки и согласия; старую очередь не выпускают автоматически.
