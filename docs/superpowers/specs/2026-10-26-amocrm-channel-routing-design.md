# Каналы → amoCRM: привязка и маршрутизация

Дата: 26.10.2026. Статус: проект, на согласовании. Основание — разбор
[Wazzup24](https://app.wazzup24.ru) и решение заказчика не переносить к себе матрицу ролей.

Дополняет [архитектуру](../messenger-platform-architecture.ru.md) и
[доменную логику](../messenger-domain-logic.ru.md); не отменяет их гарантий по inbox/outbox.

## 1. Решение

Наш продукт — **безголовый шлюз** между мессенджерами и amoCRM. Менеджеры работают в amoCRM,
своего клиента чатов у нас нет.

Следствие, определяющее всю модель: доступ к переписке — не наш предмет. Сотрудник видит
сделку в amoCRM — видит её чат; не видит сделку — не видит чат. **Матрицы ролей у нас нет**,
пользователи из CRM не выгружаются, права не синхронизируются. Единственный рычаг
сегментации — воронка, привязанная к каналу: заявка с канала «Любеция ТГ» попадает в воронку
«Любеция», и её видят те, у кого есть права на эту воронку.

Существующая таблица `channel_permissions` (read/send на подключение) — это ACL нашего
собственного API, а не модель доступа к чатам. Она остаётся как есть, не расширяется и в
расчёте видимости переписки не участвует.

Что у нас остаётся: канал, привязка канала к CRM, маршрутизация входящего, диагностика.
Чего нет и не будет: экрана чатов, композера, счётчиков «мои диалоги», шаблонов, автоответов,
рассылок, виджета на сайт, ролей, отделов как сущности доступа.

## 2. Границы ответственности

| Делаем мы | Делает amoCRM |
|---|---|
| Приём webhook мессенджера, проверка подлинности | Показ переписки менеджеру |
| Хранение сообщений и медиа | Права на воронки и сделки |
| Поиск/создание контакта и сделки | Ответственный, задачи, аналитика |
| Доставка сообщения в чат сделки | Ответ менеджера из интерфейса CRM |
| Обратная доставка ответа в мессенджер | Уведомления сотрудникам |
| Диагностика канала и алерты | |

## 3. Модель данных

Новых агрегатов не вводим. Привязка канала к CRM уже существует —
`connection_routes` (`packages/database/migrations/001-core.sql:255-265`) с полями
`workshop_id`, `crm_account_id`, `funnel_id`, `default_owner_id`, `technical_source_id`,
`version`. Это и есть то место, куда админка пишет «в какую воронку падают новые клиенты».

### 3.1 Что добавляем в `connection_routes`

| Поле | Смысл | Почему нет сейчас |
|---|---|---|
| `status_id` | Этап внутри воронки для новых сделок | Воронка есть, этап не выбирается |
| `alert_staff_id` | Кому шлём алерты по каналу (nullable) | Не было понятия алерта канала |
| `normalize_phone` | Нормализация 8→+7 для РФ-номеров | Нормализации нет вообще |

_Сделано 26.10.2026:_ миграция `apps/api/migrations/014-route-routing.sql` (версия 14 в
`platform/migrate.ts`). Поля необязательные в `setConnectionRoute`: существующие вызовы не
переписывались, умолчания — `null`, `null`, `false`. `status_id` с CHECK на непустоту,
`alert_staff_id` с внешним ключом на `staff(company_id, id)`. Потребитель этих полей —
маршрутизация (RT05); до неё поля хранятся, но на создание сделки не влияют.

Воронки и этапы справочником не храним — читаем из `/api/v4/leads/pipelines` и кэшируем,
обновление по кнопке в админке. Копия справочника означала бы поддержку расхождения.

### 3.2 Состояние канала

`connections` уже хранит подключение. Добавляем административное состояние
`active` / `disabled` / `deleted`. `deleted` не удаляет строку: история сообщений и связей
остаётся целой.

### 3.3 Ключ идемпотентности создания сделки

Сейчас `intentKey = lead:${conversationId}` (`apps/api/src/integrations/amocrm/sync.ts:413`).
При маршрутизации по контакту диалога недостаточно: клиент может писать в два канала, а сделка
должна привязаться к его контакту. Ключ становится
`lead:${conversationId}:${contactId}:${funnelId}`.

Старые записи `crm_intents` остаются валидными, новые пишутся в новом формате. Логика разбора
неопределённого исхода (`creation_unknown`) не меняется.

## 4. Маршрутизация входящего

```
входящее событие
  → durable inbox (существующий контур, не трогаем)
  → conversation по (connection, externalChatId)
  → телефон контакта из профиля канала, нормализованный если normalize_phone
  → нет телефона ............ ветка «без контакта»
  → findContacts(phone):
        0 контактов ......... создать контакт + сделку в воронке/этапе канала
        1 контакт ........... взять его сделки
        >1 контактов ........ приоритет контакту со сделкой в воронке канала,
                              иначе самый свежий; выбор пишем в routing_decision
  → сделки контакта:
        есть открытая ........ самая свежая по updated_at
        только закрытые ...... создать новую в воронке/этапе канала
        нет сделок ........... создать новую
  → привязать чат amoCRM к выбранной сделке
  → положить сообщение
```

Финальные этапы определяем по метаданным воронки (`type` этапа), а не хардкодом `142/143`:
в разных воронках финальные этапы разные.

_Сделано 26.10.2026._ `AmocrmSync` читает настройки маршрута соединения (`connection_routes`),
нормализует телефон при включённом `normalize_phone`, спрашивает у адаптера открытые сделки
контакта (`findOpenLeads`) и берёт самую свежую. Открытость адаптер вычисляет по `type` этапа
из `/api/v4/leads/pipelines`: рабочий этап — `0`, а этап, который не удалось опознать, считается
закрытым. Ключ идемпотентности сделки — `lead:<conversationId>:<contactId>:<funnelId>`.

Отклонение от проекта: отдельной таблицы `routing_decision` не заводили. Факт выбора пишется
событием `crm.lead_reused` в `audit_events` с числом открытых сделок в `diagnostic_code` —
этого достаточно, чтобы потом ответить «почему сообщение ушло именно сюда», без ещё одного
агрегата. Закрытая сделка по-прежнему не переоткрывается: создаётся новая в воронке канала.

### 4.1 Принятые по умолчанию решения

Выбраны мной как разумный дефолт, требуют подтверждения:

1. **Закрытая сделка не переоткрывается.** Клиент вернулся после «успешно реализовано» —
   создаём новую сделку. Переоткрытие ломает аналитику цикла сделки и статистику воронки.
2. **Несколько открытых сделок — самая свежая по `updated_at`.** Остальные не трогаем и не
   сливаем; факт выбора пишем в `routing_decision`, чтобы потом было видно, почему сообщение
   ушло именно туда.
3. **Ветка «без контакта»** (нет телефона — групповой чат, VK без номера): создаём контакт с
   именем из профиля канала без телефона и сделку в воронке канала. Если и имени нет — не
   создаём ничего, кладём событие в очередь разбора и показываем в диагностике.

### 4.2 Что не делаем

Не объединяем контакты по имени — неоднозначно и необратимо. Не ищем сделки по сумме или
товару. Из сделки читаем только статус и `updated_at`.

## 5. Исходящее: ответ менеджера

Менеджер отвечает в чате сделки → webhook `chats.message` с исходящим сообщением → находим
`conversation` по привязке чата → отправляем адаптером канала.

Существующий контур не переделываем: проверка подписи, дедупликация по ID сообщения,
подавление эха собственных отправок, `unknown` при неоднозначном результате
(`apps/api/src/integrations/amocrm/webhook.ts`). Новое — только резолв канала: сообщение из
сделки должно уйти в тот канал, откуда пришёл клиент, а не в первый подходящий.

Правило: канал берём из `conversation.connection_id` исходного диалога. Если сделка создана
менеджером вручную и чата клиента в ней нет — отправлять некуда, пишем в диагностику.

## 6. Админ-интерфейс

Дорабатываем существующие `connections-page.tsx`, `crm-page.tsx`, `diagnostics-page.tsx`;
новых разделов не заводим.

**Каналы.** Список: имя, тип, состояние, воронка, этап. Действия: добавить, отключить, открыть
карточку.

**Добавление канала.** Три шага: тип → авторизация (бот-токен / OAuth / ключ сообщества) → имя
и привязка к воронке. Проверка подключения до сохранения: запрос к API провайдера, при ошибке
канал не создаётся.

**Карточка канала.** Вкладки «Привязка» (воронка, этап, ответственный, алерты), «Дополнительно»
(нормализация телефона, API-ключ), «Диагностика» (последние события, ошибки, состояние токенов).

**Интеграция с CRM.** OAuth amoCRM, статус «подключено / истекло», кнопка «Обновить воронки»,
время последнего обновления.

## 7. Диагностика и алерты

Алерт уходит `alert_staff_id` по событиям: канал перешёл в `disabled` (отозван доступ, бот
заблокирован); обновление токена не удалось после всех повторов; отправка вернула
подтверждённый отказ; сообщение попало в очередь разбора.

Логи — существующий structured log без PII: телефоны и тексты сообщений не пишем, пишем
`conversation_id`, `connection_id`, `external_message_id` и исход.

### 8.1 Порядок работ

Порядок выбран так, чтобы каждый шаг давал проверяемый результат и не блокировал следующий.

1. **HTTP-клиент `AmocrmSyncClient`.** `findContacts`, `createContact`, `createChat`,
   `createLead` с `pipeline_id` и `status_id`. Проверяется на тестовом аккаунте amoCRM.
   _Сделано 26.10.2026:_ `apps/api/src/integrations/amocrm/sync-client.ts`, 12 тестов в
   `apps/api/test/amocrm-sync-client.test.ts`. Контракт `AmocrmSyncClient` расширен
   необязательными полями (имя, телефон, почта, воронка, этап, контакт). Что осталось
   непроверенным: состав тела запроса в Chats API (`createChat`) — эндпоинт и подпись
   подтверждены `packages/amocrm-protocol`, форма тела требует живого прогона. Хуки
   `findContactByIntentKey`/`findLeadByIntentKey` не реализованы: сверка после
   неопределённого исхода опирается на поиск по телефону и локальную таблицу `crm_intents`.
2. **Подключить `AmocrmSync` в worker.** Очередь `amocrm.projection` и
   `PROJECTION_JOB_KIND` уже определены (`sync.ts:765`) — не хватает только запуска.
   _Сделано 26.10.2026:_ `apps/api/src/worker.ts` поднимает `AmocrmSync` + `OutboundQueue`
   при полной конфигурации amoCRM и вычитывает очередь пачкой (`WORKER_PROJECTION_BATCH`,

4. **Маршрутизация.** Поиск открытой сделки контакта до создания новой; нормализация телефона;

6. **Алерты по каналу.**

## 9. Критерии приёмки

1. Новый клиент без контакта пишет в Telegram — сделка появляется в воронке из привязки канала,
   на выбранном этапе, чат открывается в сделке.
2. Клиент с открытой сделкой пишет снова — сообщение в существующей сделке, новая не появляется.
3. Клиент с закрытой сделкой пишет снова — создаётся новая сделка в воронке канала.
4. Повторная доставка того же webhook не создаёт второго контакта, второй сделки и второго
   сообщения.
5. Менеджер отвечает в чате сделки — сообщение приходит клиенту в тот мессенджер, откуда он писал.
6. Отзыв доступа к каналу переводит канал в `disabled` и шлёт алерт указанному получателю.
   _Покрыто 26.10.2026 (RT07):_ отзыв доступа отключает канал (`state = 'disabled'`,
   входящие и отправка выключены) и шлёт алерт получателю из `alert_staff_id`. Правила
   для `unknown` сохранены: неизвестный исход отправки остаётся `unknown` и ждёт
   человека, отключение канала его не переводит и не переотправляет.
7. Смена воронки в админке применяется к следующим новым сделкам, существующие не переносятся.

## 10. Решения владельца и оставшиеся вопросы

- 26.10.2026 владелец подтвердил: новые обращения поступают в **«Неразобранное»**,
  без автоматического назначения сотрудника. Подтверждение в рабочем чате:
  «Неразобранное. Никак она свободна». `status_id = null` использует этот режим;
  явный рабочий этап в маршруте остаётся отдельной настройкой канала.
- В режиме по умолчанию новую рабочую сделку через `POST /leads` не создаём.
  Входящее сообщение передаётся в Chats API с `silent: false` и внешним идентификатором
  источника. Воронка источника должна быть настроена в amoCRM; это проверяется при живой приёмке.
  Шлюз не передаёт `responsible_user_id` и не назначает сотрудника.
- 26.10.2026 владелец отложил живые сообщения и переключение: сначала завершить разработку,
  затем предупредить сотрудников и согласовать окно тестирования. Локальные проверки
  используют изолированные данные и подменённые API; новые подключения сохраняются выключенными.
- 26.10.2026 владелец подтвердил: **«Наше хранилище + вложения в чате amoCRM»**.
  Отдельная очередь `telegram.media` сохраняет оригинал в нашем приватном объектном
  хранилище, даже если CRM-проекция или OAuth выключены. После проверки MIME/размера/хеша
  Chats API получает временную HTTPS-ссылку. Обязательную копию каждого файла в файловом
  хранилище amoCRM не создаём. Ссылка выдаётся на час заново при каждой попытке импорта;
  токен Telegram и исходный URL провайдера в amoCRM не передаются. Поведение исторических
