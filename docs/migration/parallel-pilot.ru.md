# Наблюдательный параллельный пилот рядом с Wazzup

Задача: [#18](https://github.com/lenremont2/analog_whatsapp-for-amocrm/issues/18). Дата: 21.10.2026.

Цель — убедиться, что новый контур принимает и обрабатывает события не хуже действующего, **не отключая Wazzup** и не создавая второго отправителя на том же номере.

## Главное ограничение

Один рабочий номер (или бот, или сообщество) не может иметь двух владельцев отправки. Параллельный пилот допустим только в одном из двух режимов:

1. **Раздельные тестовые активы** — отдельный тестовый бот/номер/сообщество. Новый контур работает полностью, включая отправку. Риск для производства нулевой, но проверяется не реальный трафик.
2. **Shadow на рабочем активе** — новый контур получает копию входящих событий, но **отправка и CRM-эффекты выключены**. Wazzup остаётся единственным владельцем отправки.

Смешивать нельзя: если новый контур получил право отправки на рабочем номере, Wazzup должен быть остановлен. Это уже не пилот, а переключение (#19).

## Режим 1: тестовые активы

Порядок:

1. Создать отдельный тестовый бот/номер/сообщество для каждого канала, который проверяем.
2. Зарегистрировать webhook нового контура на тестовый актив.
3. Включить `ingress_enabled = true`, `send_enabled = true` **только** для тестового подключения.
4. Прогнать контрольные сценарии (ниже).
5. Сверить результаты вручную, зафиксировать расхождения.

Что проверяется: реальная доставка, реальная подпись, реальные ограничения провайдера, реальные статусы. Чего не проверяется: поведение на реальном объёме и реальных клиентских диалогах.

## Режим 2: shadow на рабочем активе

Порядок:

1. Подтвердить у владельца канала, что чтение событий вторым получателем допустимо по правилам провайдера и не ломает Wazzup.
2. Настроить копирование входящих событий в новый контур.
3. **Жёстко выключить** на новом контуре: `send_enabled = false`, `OUTBOUND_ENABLED=false`, отключить CRM-эффекты и автоответы.
4. Сравнивать входящий поток с эталоном.

Что проверяется: полнота приёма, отсутствие потерь и дублей, корректность нормализации, поведение при перезапуске. Чего не проверяется: отправка (её в этом режиме нет).

**Риск, который нужно принять явно:** если провайдер допускает только одного получателя событий, второй подписчик может отобрать события у Wazzup. Тогда режим 2 неприменим — только режим 1.

## Контрольные сценарии

Одинаковые для обоих режимов:

| Сценарий | Что должно быть |
|---|---|
| Текстовое входящее | Событие сохранено до ACK, отображается в диалоге |
| Ответ оператора | Ровно одна отправка, статус `sent` только после подтверждения провайдера |
| Вложение в обе стороны | Медиа привязано к исходному событию, права наследуются |
| Повторная доставка события | Нет дубля в истории |
| Перезапуск сервиса | Сохранённые события не теряются, unknown не отправляется повторно |
| Недоступность провайдера | Понятная ошибка, нет слепого повтора |
| Внутренняя группа | Исключена до создания CRM-сущностей |
| Чужой/неверный scope | Отклонено, нет утечки состояния |

## Сверка

Для каждого события фиксируется:

- совпало ли наличие события в старом и новом контуре;
- совпало ли содержимое (тип, автор, направление, время);
- совпало ли сопоставление с диалогом и контактом;
- совпало ли состояние ожидания ответа;
- для расхождений — объяснение: задержка, фильтр, ошибка нормализации или реальная потеря.

Критерий приёмки пилота: **каждое расхождение объяснено**, дублей нет, конфликтующих получателей событий нет, отправка на рабочем активе остаётся у одного владельца.

## Что должно быть готово до старта

- Развёрнутый контур (#29–#31) с работающими health/readiness.
- Выключенные внешние эффекты по умолчанию.
- Подтверждённые доступы к тестовым активам (см. `docs/requirements/access-request.ru.md`).
- Реестр подключений (#17) — хотя бы для тех каналов, которые идут в пилот.

## Текущее состояние

Состояние на 22.10.2026: новый контур **развёрнут** в production (HTTPS, health/readiness
отвечают), поэтому первый пункт «что должно быть готово» выполнен. Пилот при этом
**не запускался**: тестовые активы и подтверждённые доступы к ним не получены, сверка
старого и нового контура не выполнялась. Этот документ описывает процедуру, а не результат.

Логика сверки и ограждения «один владелец отправки» реализована и покрыта автотестами
(`apps/api/src/migration/pilot.ts`, `apps/api/test/pilot.test.ts`), но это проверка нашего
кода, а не прохождение пилота.
