# Нагрузочные и эксплуатационные проверки API

Набор для задачи #21: фиксирует поведение шлюза под конкурентной нагрузкой и
защищает инварианты, которые нельзя проверить одиночными функциональными тестами
(ровно-одна обработка, отсутствие дублей, fence воркеров, состояние пула).

Файлы:

| Файл | Что проверяет |
|---|---|
| `ingest-load.test.ts` | 500 входящих webhook, 25 одновременно, 50 чатов. Полнота, дедупликация, уникальные ключи, целостность связей. |
| `send-worker.test.ts` | 100 команд отправки, 8 воркеров, fake-транспорт с задержкой 5 мс. Ровно-одна отправка, fence, отсутствие дублей. |
| `operator-api.test.ts` | 200 одновременных запросов списка work-items от 200 разных сессий (100 company-wide, 100 в рамках цеха). 5xx, p95, состояние пула соединений. |
| `support.ts` | Перцентили, ограниченный параллелизм, форматирование отчёта. Не тест. |

## Запуск

Нужен PostgreSQL с тестовой БД (по умолчанию
`postgres://testuser:testpass@127.0.0.1:55440/m2a`, переопределяется
`TEST_DATABASE_URL`). Каждый файл создаёт изолированную схему и удаляет её после
прогона.

```bash
cd apps/api

# Весь набор; последовательно — так цифры стабильнее и не мешают друг другу.
node --test --test-concurrency=1 test/load/*.test.ts

# Один файл
node --test test/load/ingest-load.test.ts
```

`npm test` эти файлы не запускает: его glob — `test/*.test.ts`, а нагрузочный
набор сознательно вынесен в отдельную команду, чтобы обычный прогон оставался
быстрым. Запускать параллельно (`node --test test/load/*.test.ts` без
`--test-concurrency=1`) можно, но файлы будут конкурировать за одну БД и p95
вырастет; пороги это переживают, однако для сравнения цифр используйте
последовательный режим.

Весь набор укладывается в 4–8 секунд (лимит — 2 минуты).

## Зафиксированные пороги

Пороги — это регрессионные ворота для локального PostgreSQL, а не обещание
production-SLO. Они выбраны по фактическим прогонам и с запасом на шумную
машину.

| Проверка | Факт (локально) | Порог | Обоснование |
|---|---|---|---|
| ingest: p95 | 29–276 мс | ≤ 500 мс | Целевой p95 сохранения webhook из `docs/messenger-platform-architecture.ru.md`. Верхняя граница диапазона — прогон при параллельно работающих тестах на той же машине. |
| ingest: p99 | 46–535 мс | ≤ 1000 мс | Двукратный запас к p95: 25 писателей делят пул из 10 соединений. |
| ingest: max | 53–580 мс | ≤ 3000 мс | Ловит единичный патологический стоп (ожидание блокировки, пропавший индекс). |
| ingest: общее время | 0.44–1.65 с | ≤ 60 с | Остаётся место на остальные файлы в бюджете 2 минуты. |
| send: общее время | 0.3–1.1 с | ≤ 15 с | Теоретический минимум 100 × 5 мс / 8 воркеров ≈ 63 мс; 15 с ловит сериализацию всего батча, а не транспорт. |
| operator: p95 | 149–534 мс | ≤ 750 мс | 200 одновременных запросов — жёстче ровного production-потока: на пике 190 запросов ждут пул из 10 соединений (это и есть узкое место, а не сам запрос). Половина сессий ограничена цехом и идёт через `EXISTS connection_routes`. Запас ~1.4× к худшему локальному прогону. |
| operator: max | 151–563 мс | ≤ 3000 мс | Хвост очереди за пулом. |
| operator: общее время | 0.16–0.56 с | ≤ 30 с | Бюджет набора. |

Пороги не ослаблялись под результат: каждый из них либо взят из проектного
документа, либо оставляет запас к измеренному максимуму и при этом падает при
регрессии на порядок (полный скан, запрос на каждый элемент, отсутствие
индекса).

## Что именно утверждается

### Приём (`ingest-load.test.ts`)

- 500 webhook приняты, 500 сохранены в `inbox_events`, дублей нет, потерь нет.
- `provider_event_key` и `provider_message_id` уникальны; ровно 50 диалогов на
  50 чатов (конкурентный upsert не создаёт лишних).
- На каждое сообщение — одна версия контента и одно задание `crm.project`;
  `intent_key` заданий уникальны, задания не отправляются сами.
- Нет «сирот»: inbox → connection identity, message → conversation,
  outbox payload → message/conversation, obligation → work item.
- Замеряются p50/p95/p99/max и общая пропускная способность.

### Отправка (`send-worker.test.ts`)

- 100 логических команд приняты в outbox, 8 воркеров разбирают очередь
  параллельно.
- Транспорт вызван ровно 100 раз, тексты не повторяются; у каждой операции
  ровно одна попытка и свой `provider_message_id`.
- `fence = 1` и `attempt_count = 1` у каждого задания: конкурентные воркеры не
  захватили одно задание дважды.
- `send_attempts.dispatch_fence` совпадает с fence задания, аренда не осталась
  висеть.

### Операторский API (`operator-api.test.ts`)

- 200 запросов от 200 разных сессий: ни одного 4xx/5xx и ни одной ошибки
  клиента.
- Каждая страница полная (`limit=50`), элементы внутри страницы не повторяются.
- После всплеска `pool.waitingCount = 0`, `totalCount ≤ max`, пул продолжает
  обслуживать запросы. Отсутствие ошибок получения соединения — главный
  признак того, что пул не исчерпан.
- В отчёт выводится `peakPoolWaiting`: на пике за пулом из 10 соединений
  стоят до 190 запросов. Это ожидаемо для всплеска 200/10 и означает, что при
  таком профиле латентность определяется размером пула, а не стоимостью
  запроса. Для большего числа одновременных операторов нужно поднимать `max`
  пула (и лимит соединений PostgreSQL), а не оптимизировать SQL списка.

## Что эти тесты НЕ доказывают

- **Не заменяют нагрузку на реальном железе.** Всё выполняется на одной
  локальной PostgreSQL без лимитов CPU/RAM, без сети и без реальных
  провайдеров (WhatsApp/Telegram/MAX/VK). Задержки и пропускная способность
  реальных API, их rate limit и таймауты здесь не измеряются.
- **HTTP-слой операторского API проверяется через `app.inject`**, а не через
  сокет и reverse proxy. Стоимость TLS, keep-alive, прокси и сетевых задержек
  не входит в цифры.
- **Нет soak-теста.** Проверяется всплеск, а не деградация за часы: утечки
  памяти, рост bloat, автовакуум и накопление очереди не измеряются.
- **Нет медиа и больших payload.** Входящие — короткий текст; загрузка
  вложений, S3 и SSRF-политика не нагружаются.
- **Нет проверки нескольких инстансов API.** Конкуренция идёт между воркерами и
  запросами внутри одного процесса; поведение при нескольких подах и общем
  пуле соединений (например, PgBouncer) не покрыто.
- **Числа зависят от машины.** Пороги подобраны с запасом, но абсолютные
  значения p95 на другом железе будут отличаться; сравнивать прогоны имеет
  смысл только на одинаковой конфигурации.
- **Проверяется отсутствие дублей в рамках одного прогона**, а не
  идемпотентность на уровне провайдера: fake-транспорт не воспроизводит
  повторную доставку после таймаута.

## Зафиксированный прогон 22.10.2026

Набор прогнан целиком, последовательно (`--test-concurrency=1`), все три файла прошли.

**Профиль машины:** Intel Core i5-12400F (12 потоков), 34 ГБ RAM, Windows 10 (10.0.19045), Node v24.20.0, PostgreSQL 18.6 на localhost. Машина разработчика, не выделенный стенд: числа годятся для сравнения прогонов между собой и для регрессии, но не как обещание production-производительности.

| Проверка | Факт | Порог | Запас |
|---|---|---|---|
| ingest: 500 webhook, 25 параллельно | p50 28.6 мс, p95 **67.4 мс**, p99 73.7 мс, max 84.9 мс, 691.6 событий/с | p95 ≤ 500 мс | 7.4× |
| send: 100 команд, 8 воркеров | p50 25.6 мс, p95 **101.8 мс**, p99 135.2 мс, max 142.0 мс, 264.2 команд/с | общее ≤ 15 с | 0.48 с |
| operator: 200 запросов, 200 сессий | p50 199.8 мс, p95 **433.2 мс**, p99 453.2 мс, max 458.3 мс, 420.3 запросов/с | p95 ≤ 750 мс | 1.7× |

Состояние под нагрузкой: `http5xx=0`, `requestFailures=0`, пик ожидания пула — 190 запросов, после прогона `waiting=0`, `total=10`, `idle=10`. Соединения не утекают, пул возвращается в исходное состояние.

**Что это доказывает:** под конкурентной нагрузкой сохраняются инварианты — ровно одна обработка события, отсутствие дублей, fence воркеров (одна отправка на команду), отсутствие 5xx и утечек соединений. Именно эти инварианты и проверяются assertions, а числа выше — ориентир для сравнения.

**Что это не доказывает:** поведение под реальным сетевым транспортом провайдеров (используются fake-транспорты с задержкой 5 мс), работу нескольких инстансов API на одной базе, деградацию при переполнении диска или памяти. Для этих сценариев нужен отдельный стенд.
