# Руководство администратора

Кому: администратору платформы и руководителю эксплуатации шлюза мессенджеров.
Где: `https://messengers.example.com`.
Технические процедуры: [DEPLOY-RUNBOOK](../deploy/messengers2amo/DEPLOY-RUNBOOK.md),
[MONITORING](../deploy/messengers2amo/MONITORING.md),
[ROLLBACK](../deploy/messengers2amo/ROLLBACK.md),
[BACKUP-RESTORE](../deploy/messengers2amo/BACKUP-RESTORE.md).

## 0. Что настраивается через интерфейс, а что через платформенного администратора

В текущем срезе через HTTP-API и консоль настраиваются:

- мастерские и маршруты подключений;
- правила групп;
- жизненный цикл подключений и ссылки на credentials;
- роли и область сотрудников;
- политика владельцев CRM, ручная ресинхронизация, диагностика;
- OAuth amoCRM.

Пока **нет HTTP-маршрута** и выполняется платформенным администратором напрямую в БД:

- создание компании, сотрудника и пароля;
- членство сотрудника в мастерской (`workshop_staff`);
- права чтения и отправки по каналу (`channel_permissions`);
- включение CRM-проекции для подключения (`channel_policies`);
- привязка сотрудника к пользователю amoCRM (`staff_crm_refs`);
- технический источник CRM (`crm_sources`).

Это ограничение текущего среза, а не ошибка настройки. Если действие нельзя выполнить в
консоли, не ищите скрытую кнопку — оформляйте заявку платформенному администратору.

## 1. Роли сотрудников

Роли складываются: каждая следующая включает права предыдущей.

| Роль | Что даёт |
|---|---|
| `read` | Смотреть обращения, карточку, историю сообщений, подключения и их здоровье, уведомления, доступность сотрудников, мастерские, маршруты, правила групп, права, политику и конфликты CRM, диагностику; читать вложения. |
| `send` | Всё из `read` + брать и передавать обращения, создавать снимок, отвечать, закрывать обращение без открытых вопросов, оформлять ручное покрытие, загружать вложения. |
| `manage` | Всё из `send` + создавать подключения (только в масштабе компании), менять жизненный цикл и credentials, задавать правила групп, запускать ресинхронизацию CRM, закрывать обращение с открытыми вопросами. |
| `admin` | Всё из `manage` + создавать мастерские и маршруты, менять роли, область и доступность сотрудников, отзывать сессии, менять политику владельцев CRM, отзывать OAuth amoCRM. |

Важно:

- роль проверяет сервер, а не интерфейс; скрытая кнопка не означает отсутствие права;
- область действия — компания или одна мастерская. Сотрудник с `workshopId` видит только
  подключения, привязанные к его мастерской;
- изменение роли или области немедленно завершает все активные сессии сотрудника;
- `manage` и `admin` в масштабе мастерской не могут создавать подключения: создание
  подключения доступно только сотруднику с областью «вся компания».

## 2. Как заводится сотрудник

Отдельного экрана «Создать сотрудника» в текущем срезе нет. Учётную запись создаёт
платформенный администратор. Нужны четыре факта:

1. **Сотрудник** — запись в `staff` (`company_id`, `id`, `display_name`, `capacity`).
   `capacity` — сколько обращений сотрудник может держать одновременно. По умолчанию `0`,
   и с нулевой вместимостью «Взять в работу» всегда будет отклоняться.
2. **Пароль** — запись в `staff_credentials`: соль и scrypt-хеш. Пароль в открытом виде не
   хранится и никуда не передаётся. Хеш формируется тем же способом, что в
   `apps/api/src/platform/auth.ts` (`createPasswordRecord`); эталон заполнения —
   `apps/api/test/helpers/seed.ts`.
3. **Право доступа** — запись в `staff_access`: роль (`read`/`send`/`manage`/`admin`) и
   мастерская (`workshop_id`; `NULL` — вся компания).
4. **Членство в мастерской** — запись в `workshop_staff`, если сотрудник работает в конкретной
   мастерской. Без неё права на каналы мастерской не действуют.

После создания сотрудник входит через `POST /api/v2/auth/login` с `companyId`, `staffId` и
паролем. Сервер выдаёт HttpOnly-cookie; срок сессии по умолчанию 8 часов
(`SESSION_TTL_SECONDS`).

### Изменить роль или область

```
POST /api/v2/operator/staff/{staffId}/access
{
  "role": "send",
  "workshopId": "workshop-id" | null,
  "expectedVersion": 3
}
```

Требуется роль `admin`. `expectedVersion` — текущая версия доступа; при расхождении сервер
вернёт `409 VERSION_CONFLICT`. Успешный ответ содержит новую версию. Все сессии сотрудника
при этом отзываются: ему нужно войти заново.

### Отозвать сессии

```
POST /api/v2/operator/staff/{staffId}/sessions/revoke
{ "reason": "смена роли" }
```

Требуется `admin`. Возвращает число отозванных сессий. Используйте при увольнении, подозрении
на компрометацию пароля или сразу после смены роли.

### Увольнение

1. Отзовите сессии (см. выше).
2. Удалите или понизьте `staff_access`.
3. Уберите сотрудника из `workshop_staff` и `channel_permissions`.
4. Обращения, которые были на нём, верните в очередь. В коде есть процедура
   `revokeStaffAccess` (снимает владельца, освобождает слот и пишет историю), но HTTP-маршрута
   для неё в текущем срезе нет — это делает платформенный администратор.

## 3. Мастерская

**Мастерская** — точка обслуживания. Это не отдел и не очередь: отдел — функция сотрудников,
мастерская — место обслуживания и учёта. Одно и то же имя в разных сущностях не является
ключом.

Создание (роль `admin`):

```
POST /api/v2/operator/workshops
{ "id": "workshop-id", "displayName": "Название" }
```

`id` — неизменяемый ключ. `displayName` можно менять, он не используется как ключ.

Список: `GET /api/v2/operator/workshops`. Сотрудник с областью мастерской видит только её.

## 4. Маршрут подключения

Маршрут связывает подключение с мастерской и задаёт параметры проекции в CRM.

```
POST /api/v2/operator/workshops/{workshopId}/routes
{
  "connectionId": "conn_...",
  "crmAccountId": "account-id",
  "funnelId": "funnel-id",
  "defaultOwnerId": "staff-id",
  "technicalSourceId": "source-id",
  "expectedVersion": 0
}
```

Требуется `admin`. Для первого маршрута `expectedVersion` = `0`; для изменения — текущая
версия. У одного подключения может быть только один маршрут. Попытка перенести маршрут через
другую мастерскую вернёт `404`, а не «переместит» его.

Что означают поля:

- **crmAccountId** — аккаунт amoCRM, в который проецируются обращения;
- **funnelId** — воронка, в которой создаётся сделка;
- **defaultOwnerId** — ответственный по умолчанию (сотрудник платформы);
- **technicalSourceId** — технический источник в `crm_sources`. Он должен существовать
  заранее; это отдельная сущность от рекламного источника.

До создания маршрута должны существовать аккаунт CRM, сотрудник для `defaultOwnerId` и
технический источник. Иначе запрос вернёт `404`.

Что даёт маршрут:

- подключение становится видимым сотрудникам мастерской;
- входящие события получают мастерскую, воронку и ответственного;
- без маршрута подключение не видно сотруднику с областью мастерской, а входящая маршрутизация
  не находит мастерскую.

Проверить маршруты: `GET /api/v2/operator/workshops/{workshopId}/routes`.

## 5. Права чтения и отправки

Маршрут — это ещё не право. Для работы с каналом нужны три независимых факта:

1. подключение привязано к мастерской (`connection_routes`);
2. сотрудник состоит в этой мастерской (`workshop_staff`);
3. у сотрудника есть право на канал (`channel_permissions.can_read` и/или `can_send`).

Чтение и отправка раздельны: можно видеть переписку, но не иметь права отвечать. Отзыв одного
права не отзывает второе.

В текущем срезе `workshop_staff` и `channel_permissions` не имеют HTTP-маршрута. Их заполняет
платформенный администратор. Консоль показывает права только для чтения:
`GET /api/v2/operator/workshops/{workshopId}/permissions`.

Если сотрудник «не видит диалог», сначала проверьте все три пункта, а не только роль.

## 6. Исключение внутренних групп из CRM

По умолчанию группы **не попадают** в CRM. Правило работает так:

- нет строки политики подключения — запрещено;
- `crm_projection_enabled = false` — запрещено;
- тип чата `unknown` — запрещено всегда;
- приватный чат — разрешён только при `private_import_enabled = true`;
- группа — разрешена только при явном правиле `allow_crm`;
- `exclude` — исключить;
- `archive_only` — только архив, без CRM.

Правило задаётся по неизменяемому ключу: подключение + эпоха привязки + внешний ID чата.
Название группы ключом не является и может меняться.

```
POST /api/v2/operator/workshops/{workshopId}/groups
{
  "connectionId": "conn_...",
  "bindingEpoch": 0,
  "externalChatId": "...",
  "decision": "exclude",
  "displayName": "Внутренняя группа"
}
```

Требуется `manage`. Подключение должно быть привязано к этой мастерской, иначе `404`.

Посмотреть правила: `GET /api/v2/operator/workshops/{workshopId}/groups`.

Если группа всё равно попадает в CRM:

1. Проверьте, что для подключения есть строка `channel_policies` и в ней
   `crm_projection_enabled = true`. Без строки политики запрещено всё.
2. Проверьте, что правило задано для **текущей** эпохи привязки. После переподключения
   `binding_epoch` меняется, и старые правила к новой эпохе не применяются.
3. Проверьте `chat_kind` в `conversations`: если чат определён как `private`, правило группы
   не используется.
4. Проверьте, что сообщение не было спроецировано до появления правила: уже созданные задания
   и связи задним числом не отменяются.

Проверка через функцию БД:

```sql
SELECT "messengers2amo".channel_crm_import_allowed(
  '<company>', '<connection>', <epoch>, '<external-chat-id>', 'group'
);
```

`false` — проекция запрещена, `true` — разрешена явным правилом `allow_crm`.

## 7. Подключения

Создание (роль `manage`, область «вся компания»):

```
POST /api/v2/operator/connections
{
  "idempotencyKey": "unique-key",
  "channelMode": "telegram_bot",
  "credentialRef": "credref_..."
}
```

Допустимые режимы: `telegram_bot`, `telegram_personal`, `telegram_business`,
`whatsapp_cloud`, `whatsapp_qr`, `max_bot`, `vk_community`.

`credentialRef` — ссылка на секрет, а не сам секрет. В ответе секрет не возвращается.
Новое подключение создаётся в состоянии `setup` с выключенными приёмом и отправкой.

Жизненный цикл:

```
POST /api/v2/operator/connections/{connectionId}/lifecycle
{
  "idempotencyKey": "unique-key",
  "expectedVersion": 1,
  "desiredState": "active"
}
```

- `active` — включает приём и отправку;
- `paused` — выключает и приём, и отправку;
- `disabled` — выключает подключение.

Ротация ссылки на credentials:

```
POST /api/v2/operator/connections/{connectionId}/credentials-reference
{ "idempotencyKey": "unique-key", "expectedVersion": 2, "credentialRef": "credref_..." }
```

Увеличивает `credentialsVersion`, но не меняет адресата и не отменяет уже начатые отправки.

Состояния подключения в консоли: «Настройка», «Активно», «Сбои», «Требуется авторизация»,
«Приостановлено», «Отключено». Ошибки здоровья: `AUTH_REQUIRED`, `POLLING_CONFLICT`,
`UPSTREAM_TIMEOUT`, `UPSTREAM_UNAVAILABLE`, `CONFIGURATION_REQUIRED`, `INTERNAL_ERROR`.

Подключение без маршрута не принадлежит ни одной мастерской. Не забывайте про шаг 4.

## 8. Внутренний CRM-адаптер (`INTERNAL_SERVICE_TOKEN`)

Внутренние маршруты — отдельная identity для сервиса-адаптера CRM. Это **не** оператор: cookie
сессии здесь не читается вообще, даже если сотрудник с ролью `admin` откроет тот же путь в
браузере.

| Маршрут | Назначение |
|---|---|
| `GET /api/v2/internal/crm/bindings` | Список привязок диалог ↔ CRM для адаптера. |
| `POST /api/v2/internal/crm/outbound` | Исходящее сообщение от адаптера по привязке. |

Авторизация — только заголовок `Authorization: Bearer <INTERNAL_SERVICE_TOKEN>`. Сравнение
токена постоянное по времени; пустой или отсутствующий заголовок даёт `401`.

Когда нужен: если внешний адаптер должен читать привязки или отправлять сообщения через шлюз.
Если адаптера в установке нет — токен оставляют пустым.

Как выпустить:

1. Сгенерируйте значение на сервере: `openssl rand -hex 32`.
2. Запишите его в `.env` как `INTERNAL_SERVICE_TOKEN=` (файл `0600`, владелец root).
3. Перезапустите API: `docker compose -p messengers2amo up -d api`.
4. Передайте то же значение адаптеру по согласованному каналу. В чат, заявку и Git токен не
   попадает.

Что будет без токена: **группа маршрутов не регистрируется**, и оба пути отвечают `404`, а не
`401`. Пустой токен означает «адаптера в этой установке нет», а не «доступ открыт». В отчёте
`npm run readiness` это необязательный пункт, а не блокер.

Проверка после настройки:

```bash
API=https://messengers.example.com
# без заголовка: 401, если токен задан; 404, если группа отключена
curl -s -o /dev/null -w '%{http_code}\n' "$API/api/v2/internal/crm/bindings"
# с токеном: 200
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $INTERNAL_SERVICE_TOKEN" \
  "$API/api/v2/internal/crm/bindings"
```

Коды `POST /api/v2/internal/crm/outbound`: `202` — команда принята (но не доставлена);
`401` — токен не совпал; `404` — привязка не найдена; `422 CAPABILITY_BLOCKED` — привязка не в
состоянии `bound`, эпохи не совпадают, канал не `active` или отправка выключена;
`409 IDEMPOTENCY_CONFLICT` — тот же ключ идемпотентности с другим телом.

Не путайте с операторским `GET /api/v2/operator/crm/bindings`: он читает cookie сессии и
показывает привязки вашей компании. Внутренний маршрут — только для сервиса.

## 9. Каналы WhatsApp, MAX и VK

Каждый канал включается только когда заданы **все** обязательные переменные блока. Частично
заполненный блок означает выключенный канал: маршрут отвечает `503`, а не «работает наполовину».

| Канал | Обязательные переменные | Необязательные | Вебхук |
|---|---|---|---|
| WhatsApp Cloud | `WHATSAPP_APP_SECRET`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` | `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_API_BASE` | `POST /webhooks/whatsapp/{connectionId}` + GET-рукопожатие |
| MAX | `MAX_ACCESS_TOKEN`, `MAX_WEBHOOK_SECRET` | `MAX_API_BASE` | `POST /webhooks/max/{connectionId}` |
| VK | `VK_GROUP_ID`, `VK_ACCESS_TOKEN`, `VK_SECRET`, `VK_CONFIRMATION_CODE` | `VK_API_BASE`, `VK_API_VERSION` | `POST /webhooks/vk/{connectionId}` + GET-рукопожатие |

Проверка подписи входящего:

- WhatsApp — заголовок `X-Hub-Signature-256`, HMAC от точных полученных байтов с
  `WHATSAPP_APP_SECRET`;
- MAX — заголовок `X-Max-Bot-Api-Secret` со значением `MAX_WEBHOOK_SECRET`;
- VK — поле `secret` в теле события со значением `VK_SECRET`.

Рукопожатия:

- WhatsApp (Meta hub-challenge): `GET /webhooks/whatsapp/{connectionId}` с query-параметрами
  `hub.mode=subscribe`, `hub.verify_token=<WHATSAPP_VERIFY_TOKEN>`, `hub.challenge=<число>`.
  При верном токене — `200` и тело-эхо `hub.challenge`; при неверном — `403`; без challenge —
  `400`; канал не настроен — `503`.
- VK Callback API: `GET /webhooks/vk/{connectionId}?type=confirmation` для существующего
  подключения возвращает `200` и тело `VK_CONFIRMATION_CODE`; если подключения нет — `404`,
  любой другой `GET` — `403`.

Пример проверки рукопожатия WhatsApp:

```bash
API=https://messengers.example.com
curl -sS -o /dev/null -w '%{http_code}\n' \
  "$API/webhooks/whatsapp/<connectionId>?hub.mode=subscribe&hub.verify_token=$WHATSAPP_VERIFY_TOKEN&hub.challenge=12345"
# ожидается 200; тело ответа — 12345
```

Коды входящего вебхука: `401` — подпись/секрет не совпал (проверка идёт до обращения к БД);
`404` — подключение не найдено или принадлежит другому каналу; `409` — найдено несколько
подключений с таким id; `400` — некорректное тело; `413` — тело больше 1 МиБ; `503` — блок
канала не настроен.

Вебхук у провайдера настраивается вне этой системы. Наличие маршрута в API не означает, что
подписка у провайдера включена: это проверяется отдельно в кабинете провайдера и по
`health.lastInboundAt` подключения.

## 10. Подключение amoCRM (OAuth)

Параметры в `.env` (см. `ops/deploy/messengers2amo/.env.example`):

- `AMOCRM_CLIENT_ID`;
- `AMOCRM_CLIENT_SECRET`;
- `AMOCRM_REDIRECT_URI` — публичный HTTPS-callback, тот же, что в приложении amoCRM;
- `AMOCRM_ACCOUNT_DOMAIN` — поддомен аккаунта без `.amocrm.ru`.

Если блок amoCRM не заполнен, маршруты OAuth и webhook не регистрируются. Полный состав
переменных и требований к ним — в `.env.example` и `apps/api/src/platform/config.ts`;
включение блока выполняет платформенный администратор.

Подключение:

1. Войдите как `admin`.
2. Откройте `GET /api/v2/integrations/amocrm/oauth/authorize` в браузере.
3. Разрешите доступ в amoCRM.
4. Дождитесь страницы «Интеграция подключена». Токены сохраняются в зашифрованном виде.

Проверка состояния:

```sql
SELECT id, state FROM "messengers2amo".crm_accounts;
```

- `setup` — интеграция создана, но владелец ещё не авторизовал;
- `active` — авторизация пройдена;
- `revoked` — доступ отозван;
- `disabled` — интеграция отключена.

Если доступ отозван:

- в журнале будет событие `amocrm.auth_revoked`;
- обновление токена завершится ошибкой, синхронизация и проекция перестанут работать;
- повторите авторизацию по шагам выше;
- если отзыв повторяется, проверьте в amoCRM, не отозвано ли приложение и не истекли ли
  разрешения.

Отозвать интеграцию вручную:

```
POST /api/v2/integrations/amocrm/oauth/revoke
```

Требуется `admin`. Токены после отзыва не используются.

Не передавайте `client_secret`, access/refresh-токены в заявки, чат и скриншоты. В журналах
эти значения редактируются, но в переписке — нет.

## 11. Конфликты владельцев между CRM и платформой

В системе два независимых факта:

- **владелец обращения на платформе** (`work_items.owner_id`) — кто отвечает в шлюзе;
- **ответственный в amoCRM** (`crm_contact_owners.crm_owner_ref`) — что observed из CRM.

Они никогда не перезаписывают друг друга молча. Расхождение записывается как конфликт.

Политика (кто главный) — на компанию, версионная:

```
GET  /api/v2/operator/crm/policy
POST /api/v2/operator/crm/policy
{ "sourceOfTruth": "platform" | "crm", "expectedVersion": 0 }
```

Читать может `read`, менять — только `admin`. По умолчанию, если строки нет, действует
`platform`.

Конфликт создаётся, когда ответственный в CRM не совпадает с CRM-пользователем, привязанным к
локальному владельцу. Победитель (`winner`) фиксируется по политике на момент обнаружения;
последующая смена политики историю не переписывает.

Посмотреть конфликты:

```
GET /api/v2/operator/crm/conflicts?accountId=...&conversationId=...
```

Как разрешать:

1. Определите, кто должен быть ответственным — платформа или CRM.
2. Приведите назначение в соответствие: передайте обращение нужному сотруднику или измените
   политику.
3. Запустите ресинхронизацию, чтобы перечитать состояние CRM.
4. Зафиксируйте решение в заявке или журнале эксплуатации.

Отдельной кнопки «закрыть конфликт» в текущем срезе нет: запись хранится как история, а
счётчик открытых конфликтов в диагностике может оставаться ненулевым. Это известное
ограничение; не пытайтесь «исправить» его удалением строк из БД.

Проекция владельца в CRM работает только при политике `platform` и при наличии подтверждённой
привязки сотрудника к пользователю amoCRM (`staff_crm_refs`). Без привязки проекция
завершается ошибкой `crm_user_mapping_missing` и не делает внешний вызов.

## 12. Диагностика

### В консоли

- **Диагностика** — проверка операции отправки, неопределённые операции, подключения с
  ошибками, спорные связи с CRM.
- **CRM** — политика, ручная ресинхронизация, диагностика по диалогу, конфликты.
- **Мастерские** — маршруты, права, правила групп.
- **Подключения** — состояние, здоровье, включение и выключение приёма/отправки.

### Ошибки синхронизации

Состояние последней синхронизации хранится в `crm_sync_state`:

| `last_status` | Значение | Действие |
|---|---|---|
| `ok` | Синхронизировано | Ничего. |
| `lead_missing` | Сделка не найдена в amoCRM | Проверьте сделку и привязку; при необходимости создайте/свяжите вручную. |
| `failed` | Синхронизация не удалась | Смотрите `last_error_code`. |
| `in_progress` | Синхронизация ещё идёт | Не запускайте вторую с тем же ключом; дождитесь результата. |

Частые коды ошибок: `crm_binding_missing` (нет привязки диалога к CRM), `upstream_unavailable`
(amoCRM недоступен), `crm_lead_missing`, `sync_in_progress`.

Ручная ресинхронизация:

```
POST /api/v2/operator/crm/resync
{ "accountId": "...", "conversationId": "...", "idempotencyKey": "unique-key" }
```

Требуется `manage`. Повтор с тем же ключом возвращает сохранённый результат и не делает второй
внешний запрос.

### Неопределённые операции

`send_operations.state = 'unknown'` означает, что провайдер мог принять сообщение. Правило
одно: **не повторять автоматически**. Сверяйте с провайдером и чатом клиента. Подробно —
[ROLLBACK §5](../deploy/messengers2amo/ROLLBACK.md).

### Зависшие задания

- `outbox_jobs` в `pending`/`leased` — очередь не разбирается;
- `inbox_events` в `pending`/`processing` — входящие не обрабатываются;
- `crm_create_intents` в `creation_unknown` — сущность CRM могла быть создана, повторное
  создание запрещено до сверки.

Обработчик отправки — отдельный сервис `worker` в `docker-compose.yml` (запускает
`apps/api/src/worker.ts`), без опубликованных портов. Если очередь растёт, проверьте
`docker compose -p messengers2amo ps` и логи воркера. Отсутствие воркера в конкретной
установке — ограничение развёртывания, а не сбой PostgreSQL.

### Проверка готовности (`npm run readiness`)

Перед запуском и после каждого изменения `.env`:

```bash
cd apps/api
npm run readiness
```

Команда читает конфигурацию, при доступной базе сверяет журнал миграций и печатает отчёт на
русском. Код завершения: `1` — есть блокеры, `0` — блокеров нет. Значения секретов в отчёт не
попадают, только имена незаданных переменных, поэтому отчёт можно приложить к заявке.

- **БЛОКЕРЫ** — нет строки подключения к базе, база недоступна, применены не все миграции,
  нет или слишком короткий `SESSION_SECRET`, нет токена или секрета webhook Telegram, нет
  доступов amoCRM.
- **ПРЕДУПРЕЖДЕНИЯ** — запуск возможен, но часть функций выключена: не настроены WhatsApp,
  MAX, VK, S3 (медиа в памяти) или `METRICS_TOKEN`.
- **НЕОБЯЗАТЕЛЬНОЕ** — на запуск не влияет: закрытый исходящий шлюз
  `OUTBOUND_ENABLED=false` и выключенный внутренний CRM-адаптер (пустой
  `INTERNAL_SERVICE_TOKEN`).

Если база недоступна, команда не падает: это фиксируется как блокер. Перед запуском также
убедитесь, что `DB_SCHEMA` совпадает с `M2A_SCHEMA` — иначе API читает пустую схему `public`.

### Подключения и медиа

- `connections.state` + `health.errorCode` — здоровье канала;
- `media_assets.state` — `pending_upload`, `ready`, `quarantined`, `rejected`;
- `quarantined` требует ручного разбора, `rejected` — файл не принят политикой.

## 13. Инцидент: порядок действий

1. **Определите масштаб.** Один диалог, один канал или все пользователи.
2. **Не перезапускайте всё подряд.** Сначала снимите состояние: логи, health, метрики.
3. **Проверьте живость и готовность.**
   ```bash
   curl -fsS -m 5 https://messengers.example.com/health/live
   curl -fsS -m 5 https://messengers.example.com/health/ready
   ```
4. **Проверьте контейнеры и журналы.**
   ```bash
   cd /opt/messengers2amo
   docker compose -p messengers2amo ps
   docker compose -p messengers2amo logs --tail=100 api postgres
   ```
5. **Проверьте метрики.**
   ```bash
   cd /opt/messengers2amo
   set -a; . ./.env; set +a
   curl -fsS -H "Authorization: Bearer $METRICS_TOKEN" \
     https://messengers.example.com/metrics | \
     grep -E 'm2a_(up|outbox_overdue|open_obligations|send_operations|inbox_events)'
   ```
6. **Не удаляйте строки очереди и не повторяйте `unknown` вручную.** Это создаёт дубли и
   разрушает доказательства.
7. **Остановите внешние эффекты, если есть риск дублей.** Процедура —
   [ROLLBACK §4](../deploy/messengers2amo/ROLLBACK.md).
8. **Эскалируйте по согласованному каналу дежурства:**
   - платформенный администратор / on-call — контейнеры, БД, nginx, TLS, очередь;
   - администратор amoCRM — OAuth, права приложения, сделки и ответственные;
   - владелец канала — блокировки, лимиты и статусы провайдера.
9. **Зафиксируйте инцидент:** время, симптом, номер запроса, номер операции, что проверяли,
   что меняли. Секреты и персональные данные в заявку не включайте.

Команды для чтения очередей и возраста строк — в
[MONITORING §3](../deploy/messengers2amo/MONITORING.md). Резервное копирование и
восстановление — в [BACKUP-RESTORE](../deploy/messengers2amo/BACKUP-RESTORE.md).
Откат приложения — в [ROLLBACK](../deploy/messengers2amo/ROLLBACK.md).

## 14. Резервное копирование: расписание, свежесть, действия при устаревшем бэкапе

Предлагаемые цели (ещё не подтверждены владельцем): **RPO 1 час, RTO 1 час**.
Полные замеры, методика и оговорки — в
[BACKUP-RESTORE §8](../deploy/messengers2amo/BACKUP-RESTORE.md).
Здесь — то, что нужно дежурному.

### 14.1 Что запускается и когда

Расписание лежит в репозитории: `scripts/messengers2amo-backup.cron`, ставится
drop-in'ом в `/etc/cron.d/messengers2amo-backup`.

| Время (UTC) | Что | Зачем |
|---|---|---|
| каждый час в `:07` | почасовой дамп | это и есть RPO 1 час |
| каждый день в `03:07` | суточный дамп | запасной уровень, если почасовой сломался |
| каждый час в `:22` | `backup-freshness.sh` | проверка, что RPO соблюдается |

Хранятся последние 72 почасовых и 14 суточных дампа; всё старше 14 дней
удаляется независимо от уровня. Почасовые — `messengers2amo_<UTC>.dump`,
суточные — `messengers2amo_daily_<UTC>.dump` в `/opt/messengers2amo/backups`.

### 14.2 Как проверить свежесть

```bash
/opt/messengers2amo/src/ops/deploy/messengers2amo/scripts/backup-freshness.sh
```

- код возврата `0` и строка `FRESH ...` — бэкап свежий, RPO соблюдается;
- код возврата `1` и строка `STALE ...` — бэкап старше 65 минут (или его нет
  вовсе). Это уже нарушение RPO, действовать по 14.3;
- код возврата `2` — ошибка в переменных (`MAX_AGE_MINUTES`, `PG_DB`), а не
  состояние бэкапа.

Порог меняется переменной: `MAX_AGE_MINUTES=65` по умолчанию (RPO 1 час плюс
5 минут на длительность самого дампа). Для ручной проверки конкретного каталога:

```bash
BACKUP_DIR=/opt/messengers2amo/backups MAX_AGE_MINUTES=65 \
  /opt/messengers2amo/src/ops/deploy/messengers2amo/scripts/backup-freshness.sh
```

Посмотреть, что реально лежит и когда снято:

```bash
ls -lt --time-style=long-iso /opt/messengers2amo/backups/*.dump | head
tail -n 20 /var/log/messengers2amo-backup.log
```

Строка успешного запуска выглядит так:

```
2026-10-23T08:37:59Z backup ok level=hourly file=messengers2amo_20261023T083755Z.dump size=7331981 hourly_keep=72 daily_keep=14 max_age=14d
```

### 14.3 Что делать, если бэкап устарел

Порядок — от самого вероятного к самому плохому.

1. **Посмотрите журнал.** `tail -n 50 /var/log/messengers2amo-backup.log` —
   ошибка `pg_dump`, `docker`, нехватка места или `backup too small` названы
   прямо в строке.
2. **Проверьте место на диске.** `df -h /opt`. Дампы не пишутся, когда диск
   полон; почасовые копии добавляют примерно размер базы в сжатом виде каждые
   72 часа.
3. **Проверьте, что cron жив.** `systemctl status cron`, `ls -l /etc/cron.d/messengers2amo-backup`.
4. **Снимите дамп вручную, не дожидаясь расписания:**
   ```bash
   /opt/messengers2amo/src/ops/deploy/messengers2amo/scripts/backup.sh
   ```
   Успех — строка `backup ok ...` и код возврата `0`. Скрипт сам проверит дамп
   через `pg_restore --list` и только потом удалит старые копии.
5. **Убедитесь, что свежесть восстановилась:**
   ```bash
   /opt/messengers2amo/src/ops/deploy/messengers2amo/scripts/backup-freshness.sh
   ```
6. **Если дамп не снимается вообще** — это инцидент уровня «данные не защищены».
   Эскалируйте платформенному администратору немедленно; не перезапускайте
   контейнеры и не меняйте `.env`, пока причина не найдена.
7. **Зафиксируйте в журнале инцидента**: время последнего хорошего дампа, окно
   без бэкапа, причину, что сделали. Это и есть фактическая оценка потерь.

Важно: пока не появился внешний приёмник, **все** копии лежат на том же
сервере. Потеря VPS означает потерю и данных, и бэкапов — RPO/RTO 1 ч
действуют только при живом сервере. Подробнее — «Известный риск» в
[BACKUP-RESTORE §8.3](../deploy/messengers2amo/BACKUP-RESTORE.md).

## 15. Чек-лист типовых изменений

**Новый сотрудник**

- [ ] создан `staff` с `capacity > 0`;
- [ ] создан `staff_credentials` (scrypt, пароль не хранится открыто);
- [ ] создан `staff_access` с ролью и областью;
- [ ] при необходимости добавлен в `workshop_staff`;
- [ ] при необходимости выданы `channel_permissions`;
- [ ] сотрудник вошёл и видит свои обращения.

**Новая мастерская**

- [ ] создана мастерская;
- [ ] создан маршрут подключения;
- [ ] сотрудники добавлены в мастерскую;
- [ ] выданы права чтения/отправки;
- [ ] проверено, что входящее создаёт обращение и видно оператору.

**Новый канал**

- [ ] создано подключение с корректным `channelMode` и `credentialRef`;
- [ ] настроен приём (webhook/поллинг) у провайдера;
- [ ] подключение переведено в `active`;
- [ ] создан маршрут в мастерскую;
- [ ] при необходимости настроена политика CRM и правила групп;
- [ ] проверены health, входящее и один контролируемый ответ.
