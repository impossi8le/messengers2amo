# Размещение шлюза messengers2amo

Дата адаптации: 21.10.2026. Домен: https://messengers.example.com.
Репозиторий: https://github.com/lenremont2/analog_whatsapp-for-amocrm.
Задачи: https://github.com/users/impossi8le/projects/7/views/1; инфраструктурный этап — #9.

## Результат и текущие ограничения

Разместить шлюз мессенджеров для amoCRM на существующем VPS в отдельном
Docker Compose-проекте за существующим nginx. Основное рабочее место менеджера —
штатные чаты amoCRM; сайт шлюза обслуживает согласованные API, callbacks,
webhooks и административные функции. Это не доска задач и не старый kanban.

Сейчас есть локальный Telegram/SQLite-стенд и отдельные модули production-ядра.
Готовый production API, авторизация, обработчики и образы ещё требуют реализации
и приёмки. Нельзя выставлять `local-telegram` в интернет: многопользовательская
авторизация в нём отсутствует. Его loopback-порт 3210 не является production upstream.
Контракты и чистый модуль подписи не подтверждают работающую интеграцию amoCRM.

21.10.2026 внутренний браузер при открытии целевого HTTPS-домена сообщил
`net::ERR_CERT_COMMON_NAME_INVALID`. Сертификат для этого имени не подтверждён;
ошибка не доказывает готовность DNS, правильность virtual host или наличие приложения.
Проверку сертификата не отключать. Живой осмотр VPS в рамках адаптации не выполнялся.

## Зафиксированная схема

| Параметр | Значение |
|---|---|
| Публичный URL | `https://messengers.example.com` |
| Каталог VPS | `/opt/messengers2amo` |
| Compose project | `messengers2amo` |
| Вход | существующий nginx на 80/443; второй Caddy/nginx на этих портах не запускать |
| Предлагаемый upstream | `http://127.0.0.1:18767` — только после проверки занятости |
| Публикация API | `127.0.0.1:18767:<РЕАЛЬНЫЙ_ПОРТ_API>`; внутренний порт берётся из релиза |
| БД | собственная PostgreSQL 18, отдельные пользователь/пароль/том, без host port |
| Файлы | приватное S3 по контракту медиа; временные файлы имеют ограниченный бюджет |
| Backup | защищённое хранилище за пределами VPS; отдельная репетиция восстановления |

18765 зарезервирован в инструкции MCP, 18766 — в исходной инструкции taskboard.
Не переиспользовать их без отдельного решения. Если 18767 занят, выбрать свободный
и одинаково изменить Compose, nginx, manifest и эксплуатационную документацию.
Сети, контейнеры, тома и учётные записи принадлежат только `messengers2amo`.
Не использовать каталоги, `.env`, базы, сети или секреты других приложений.

Это изменение прежнего предположения об отдельном VPS: теперь целевой вариант —
изоляция на существующем сервере, допустимая только после проверки его ресурсов.
При недостатке ресурсов согласовать другой сервер/размер до запуска.

## Доступ и публикация в Git

Реквизиты SSH и файлы подключения находятся только в локальном закрытом пакете
`messengers.example.com/Taskboard-taskboard.example.com/ACCESS.txt`.
Старое имя вложенной папки — только имя локального пакета доступа, не имя сервиса.
Его inventory — исторический
снимок от 20.10.2026, а не актуальная проверка. Использовать проверенный known_hosts;
при несовпадении отпечатка не отключать StrictHostKeyChecking.

Приватный ключ не переносить на VPS, в образ, CI, issue или Git. Доступ отзывается
владельцем отдельно, после проверки резервного входа; адаптация инструкции не
является поручением менять SSH, firewall или ключи. Не публиковать весь локальный
каталог доступа. В Git передаются только явно выбранные документы и шаблоны из
`ops/deploy/messengers2amo/`, без ACCESS, ключей, known_hosts, рабочих `.env` и данных.
Перед публикацией проверить список файлов и содержимое diff на секреты.

## Что получить до запуска

1. Commit SHA релиза, неизменяемые image digests API/воркеров/БД, проверенные CI,
   Dockerfile и Compose, команды сборки, внутренний порт API и реальные endpoints
   liveness/readiness. Сейчас такой законченный комплект не подтверждён.
2. Реальный контракт переменных окружения: внешний URL, доверенные proxy,
   подключение к собственной БД, секреты сессий/шифрования, S3, интеграции.
   Имена переменных и webhook-пути не придумывать; зафиксировать их в manifest.
3. Отдельные тестовые активы и полномочия. Для amoCRM REST OAuth и Chats channel
   secret/scope/account bindings — разные механизмы. Секреты вводятся локально
   в защищённой среде; пример `.env` содержит только пустые значения.
4. Для каждого канала — подтверждённый режим, webhook или polling и единственный
   владелец получения/отправки. Личный Telegram/MAX не считать подтверждённым по
   тесту бота. WhatsApp проходит отдельный официальный PoC.
5. Согласованный бюджет RAM/CPU/PIDs/диска всех новых сервисов вместе, лимиты
   вложений, хранения, ротации логов, retention резервных копий и численные RPO/RTO.
   Старые 1.6 GiB available — не гарантия ресурсов для PostgreSQL и воркеров.
6. Контракт Архива файлов и права amoCRM. До подтверждения архивный адаптер
   отключён; прямой записи в чужую БД нет. Входящие webhooks и отправка в CRM
   включаются только по этапу пилота #17–#19, а не просто при старте контейнеров.

`RELEASE-MANIFEST.example.md` содержит перечень обязательных сведений. Неизвестный
endpoint, порт, образ или секрет — блокер релиза, а не повод запустить заглушку.

## 1. Повторная проверка VPS и домена (без изменений)

```sh
docker ps
docker compose version
ss -lntp
free -h
df -h /
nginx -t
getent ahostsv4 messengers.example.com
nginx -T
certbot plugins
certbot certificates
```

Вывод с чужими конфигурациями не публиковать. Проверить авторитетные A/AAAA и
доступность снаружи: локальный resolver не доказывает внешнее разрешение имени.
Не переносить утверждение «поддомен уже добавлен» с taskboard на этот домен.
При неверных DNS подготовить точное изменение для владельца; другие записи не менять.
Если есть AAAA — IPv6 должен вести на правильный сервер и обслуживать этот сайт.

Найти `server_name messengers.example.com` во всей конфигурации nginx.
Не создавать второй конфликтующий блок. Существующий блок сначала исследовать,
сохранить его защищённую копию и определить назначение. Проверить сертификат/SAN,
правильный SNI и принадлежность существующего certificate lineage этому домену.
Снять исходные показатели и доступность соседних сайтов для сравнения после запуска.

## 2. Подготовить релиз и Compose

Создать только `/opt/messengers2amo`. Сборку по возможности выполнять вне VPS.
Node.js 24 и зависимости ставить в образе; системный Node 20 с исторического
снимка не обновлять ради приложения. Не запускать dev-сервер.

API, обработчики и PostgreSQL имеют фиксированные версии, свои тома, healthchecks,
restart policy, лимиты RAM/CPU/PIDs и ротацию логов. Запуск от непривилегированного
пользователя, если поддерживается образом. Без privileged, Docker socket,
host network и монтирования чужих каталогов. БД/метрики/служебные API не публиковать.
Приложение должно слушать интерфейс контейнера, доступный Docker NAT; host bind
при этом остаётся только `127.0.0.1`. Сервисы без HTTP не получают host port.

Рабочий `.env` закрыть правами 600. Задать внешний URL текущего домена, доверять
только нужному proxy, настроить secure cookies, CSRF/CORS и redirect/callback URLs
по реальному контракту. Не оставлять стандартные пароли или открытую регистрацию.
Внешние эффекты нового контура по умолчанию отключены до согласованного пилота.

До миграции существующей собственной БД сделать backup. Запускать migration runner
ровно одним заданием для БД messengers2amo; не выполнять миграции других проектов.
Новая пустая БД не требует импорта старых CRM/канальных данных.

Из `/opt/messengers2amo` после подготовки фактического Compose:

```sh
docker compose -p messengers2amo config --quiet
# Отдельный migration job выполняется командой из проверенного релиза.
docker compose -p messengers2amo up -d
docker compose -p messengers2amo ps
docker compose -p messengers2amo logs --tail=100
```

Логи просмотреть локально без выгрузки токенов/телефонов/переписок. Проверить реальный
readiness на loopback upstream. Readiness должна отражать доступность нужных
зависимостей; liveness не заменяет готовность принимать и сохранять события.
Не запускать при нехватке ресурсов, провале миграции или readiness.

## 3. nginx и HTTPS

Шаблон `templates/messengers2amo.http.nginx.conf` — только HTTP bootstrap, не готовый
TLS-конфиг и не реализация авторизации. После проверки конфликтов разместить его
отдельным файлом `/etc/nginx/sites-available/messengers.example.com` и включить
ссылкой с тем же именем в `sites-enabled`. Не заменять `nginx.conf`, default и чужие сайты.
20m/60s в шаблоне — стартовые лимиты: сверить с media-контрактом и подтверждением
durable inbox; длительная обработка выполняется в воркере после сохранения события.

Публичные callback/webhook URL должны соответствовать manifest. Они не закрываются
общим Basic Auth/операторской сессией: приложение проверяет подпись/секрет по
конкретному протоколу, raw body и scope/account. Неподписанные и неверные события
отклоняются. Административные API, диагностика и медиа требуют отдельной авторизации.
Не считать Referer/Origin заменой криптографической проверки webhook.
Сквозной тест через nginx проверяет, что подписанный payload доходит без изменения.

В шаблоне нет ненужного `Connection: upgrade`. WebSocket включать только если
фактический административный интерфейс его использует, с проверенной конфигурацией.
Access log намеренно не содержит query string, IP клиента и тела: в callback URL
могут встречаться коды/секреты. Если добавляются иные логи, проверить отсутствие
Authorization, токенов, тел сообщений, client IDs и секретных URL.

После каждого изменения выполнить `nginx -t`; только при успехе —
`systemctl reload nginx`. Затем проверить выбранный virtual host:

```sh
curl -I -H 'Host: messengers.example.com' http://127.0.0.1/
```

Для выдачи TLS сначала подтвердить DNS и HTTP-доступность. Если есть действующий
сертификат с этим SAN — использовать его без лишнего дубликата. Перед nginx-плагином
сохранить резервную копию затрагиваемых конфигураций. Команда при наличии плагина:

```sh
certbot --nginx -d messengers.example.com --redirect
```

Не применять standalone с остановкой общего nginx. При отсутствии nginx-плагина
выбрать установленный подходящий способ с владельцем, не обновлять весь сервер.
Проверить итоговый конфиг, HTTP→HTTPS, SAN/SNI, цепочку сертификата и внешний HTTPS
обычным браузером/curl без `-k`. Проверить timer/cron и выполнить dry-run только
этого lineage: `certbot renew --cert-name ФАКТИЧЕСКОЕ_ИМЯ --dry-run`.
Имя брать из `certbot certificates`, не угадывать и не трогать чужие сертификаты.

## 4. Приёмка инфраструктуры и затем тестового пилота

Для каждого пункта фиксировать PASS / FAIL / NOT RUN и обезличенное доказательство.
Документы не являются доказательством выполненного развёртывания.

- [ ] HTTPS соответствует домену; HTTP ведёт на HTTPS; нет чужого сайта или mixed content.
- [ ] Проверены реальный readiness, отказ зависимости и восстановление воркера;
      метрики задержки inbox/outbox и безопасные уведомления об отказах работают.
- [ ] Неавторизованный пользователь не получает админ-API, переписки, медиа и диагностику.
- [ ] Подписанный тестовый webhook через HTTPS сохраняется до ACK; неверная подпись
      и чужой scope/account отвергаются; повтор не создаёт дубли.
- [ ] Loopback upstream и БД недоступны извне; остальные сайты и MCP работают как до запуска.
- [ ] После перезапуска только messengers2amo сохраняются история, checkpoint,
      inbox/outbox и файлы; unknown не вызывает слепую переотправку.
- [ ] Backup собственной PostgreSQL и нужных конфигураций/ключей восстановления хранится
      защищённо вне VPS. Restore выполнен на отдельной тестовой БД/томе, проверены
      целостность и фактические RPO/RTO. Тестовый restore не запускает внешние эффекты.
- [ ] Приватные S3-объекты сохраняют контрольные суммы и происхождение. Политика backup
      медиа проверена отдельно; успех БД backup не подтверждает сохранность S3/Архива.
- [ ] На разрешённых тестовых активах: входящее → нативный чат amoCRM → ответ → канал,
      права мастерских, фильтр групп и доступ к медиа; неизвестные API-возможности
      остаются блокерами соответствующих функций.
- [ ] Зафиксированы версия, manifest, команды обновления/остановки/отката, результаты
      проверок и ответственные. Секреты переданы владельцу только закрытым способом.

Живое переключение канала не входит в инфраструктурный запуск. Перед ним выполнить
`ops/runbooks/channel-cutover.ru.md` и #17–#19: один владелец исходящих/CRM-проекции,
проверенный возврат, сохранённые неизвестные результаты. Wazzup до приёмки не отключать.

## Обновление и откат

Перед обновлением сохранить текущие digests, manifest, затрагиваемый nginx-конфиг
и backup только собственных данных. При смене версии остановить выдачу новых
исходящих/CRM-эффектов, учесть pending/in-flight/unknown; одного отката контейнера
недостаточно для возврата канального маршрута. Процедуру ограждения брать из релиза.
После миграции откат образа допустим только при совместимой схеме; иначе нужен
проверенный откат схемы или согласованное восстановление с учётом новых записей.
Проверить smoke и наблюдение после каждого обновления.

Для остановки только нового проекта из `/opt/messengers2amo`:

```sh
docker compose -p messengers2amo down
```

Без `-v`: данные сохранить. Если отключается сайт — менять только его файл/ссылку,
выполнить `nginx -t` и reload. Восстановить только конфигурации этой установки.
Не останавливать nginx/Docker/VPS; не менять SSH/firewall/fail2ban; не запускать
prune, глобальные stop/remove и удаление томов. Не переносить старые базы и
приложения из `/var/www` или чужих `/opt`. Новая инфраструктура не разрешает
переопределять рабочие webhooks, принимать условия провайдеров или менять DNS других сайтов.
